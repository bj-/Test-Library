# Анализ причин блокировок LLM на библиотеке тестов безопасности

## Важное уточнение

У меня нет прямого доступа к репозиторию `github.com/bj-/Test-Library`, поэтому я не могу просмотреть конкретные файлы и назвать точные тесты. Но я могу дать **методологию поиска** и **классификацию триггеров**, по которым вы за один проход разметите всю библиотеку.

---

## Почему блокирует даже на этапе «чтения» описаний

Safety-фильтры LLM (особенно у коммерческих моделей — GPT-4, Claude, Gemini) реагируют не на намерение, а на **паттерны и лексические кластеры**. Для фильтра нет разницы между:

- «Проверь, что система защищена от SQL-инъекций, подав `' OR 1=1 --`»
- «Вот payload для SQL-инъекции: `' OR 1=1 --`»

Оба текста содержат одинаковый набор токенов. Фильтр видит: *SQL + инъекция + пример кода + кавычки + оператор* → классифицирует как «инструкция по взлому» → блокирует.

**Ключевые выводы:**
1. Блокирует не «тест», а **сочетание**: название уязвимости + пример эксплуатации + контекст «как это сделать».
2. Даже нейтральная фраза «протестировать на XSS» может сработать как триггер, если рядом идёт список payload'ов.
3. Чем больше **конкретики** (реальные строки, URL, имена полей), тем выше шанс блокировки.

## Классификация тестов по риску блокировки

Пройдитесь по библиотеке и отнесите каждый тест к одной из категорий. В `/restricted` должны уйти **высокий** и **средний** уровни.

### 🔴 Высокий риск (точно блокирует)

| Тип теста | Почему триггерит |
|---|---|
| SQL-инъекции с примерами payload'ов (`' OR 1=1`, `UNION SELECT`, `'; DROP TABLE`) | Прямые примеры атак |
| XSS (Reflected/Stored/DOM) с примерами скриптов (`<script>`, `onerror=`, `javascript:`) | Исполняемый код в описании |
| Command/OS injection (`; ls`, `| cat /etc/passwd`, backticks) | Команды shell |
| Path traversal (`../../etc/passwd`, `..\\..\\windows\\system32`) | Конкретные файловые пути ОС |
| SSRF с примерами (`http://169.254.169.254/`, `file://`, `gopher://`) | Атака на метаданные/внутренние сервисы |
| XXE с примерами DTD | XML-эксплойты |
| Deserialization attacks (Java/PHP/.NET payloads) | Готовые эксплойты |
| JWT-атаки (`alg: none`, подмена ключа, brute-force secret) | Обход аутентификации |
| Reverse shell / web shell тесты | Явные вредоносные паттерны |
| Buffer overflow / format string примеры | Классические эксплойты |
| Credential stuffing / password spraying с примерами списков | Массовый подбор |
| Brute-force с конкретными словарями (rockyou, common-passwords) | Прямая ассоциация со взломом |

### 🟡 Средний риск (блокирует выборочно, зависит от модели)

| Тип теста | Комментарий |
|---|---|
| IDOR (подмена ID в запросах) | Триггерит при описании «как получить чужие данные» |
| BOLA / Mass assignment | Контекст «обход авторизации» |
| CSRF с примерами форм | Может триггерить |
| Session fixation / hijacking | Слова «украсть сессию», «подменить пользователя» |
| Open redirect | «Перенаправить на фишинговый сайт» |
| File upload (обход проверок расширения, double extension) | Контекст загрузки вредоносного |
| DoS-тесты (медленные запросы, ReDoS, большие payload'ы) | «Как положить сервис» |
| Race condition / TOCTOU | «Обход бизнес-логики» |
| Тесты на утечку через ошибки (stack trace, debug info) | Контекст раскрытия информации |
| Тесты криптографии (слабые алгоритмы, hardcoded keys, ECB mode) | Меньше триггерит, но бывает |
| Тесты на логи (пароли/токены в логах) | Косвенно — утечка credentials |
| CORS / CSP / HSTS misconfiguration | Обычно безопасно, но в сочетании с «обход» — может |
| Тесты на hardcoded secrets в коде | Слово «секрет» + примеры |

### 🟢 Низкий риск (обычно пропускает)

- Проверка сложности пароля (regex, длина)
- Проверка политик (локкаут, captcha, 2FA)
- Позитивные сценарии аутентификации
- Валидация форматов (email, телефон)
- Проверка HTTPS, сертификатов
- Тесты доступности (uptime, latency)

## Методология быстрого анализа библиотеки

### Шаг 1. Автоматический скрининг

Прогоните по всем файлам библиотеки grep по ключевым словам-триггерам:

```bash
# Файл triggers.txt — по одному паттерну на строку
grep -rniE -f triggers.txt ./Test-Library/ | sort
```

Пример `triggers.txt`:
```
inject|injection
xss|cross-site scripting
csrf
ssrf
xxe
rce|remote code execution
shell|reverse shell|web shell
exploit|payload
brute[- ]?force
credential stuffing|password spraying
password list|wordlist|rockyou
bypass|обход
privilege escalation|повышение привилегий
\.\./\.\./|path traversal
/etc/passwd|/etc/shadow|windows\\system32
169\.254\.169\.254
union select|or 1=1|' or ""
<script|onerror=|javascript:
alg.*none|jwt.*secret
deserialize|pickle|yaml\.load
```

Всё, что попало под матчинг — кандидаты в `/restricted`.

### Шаг 2. Ручная досортировка

Для каждого кандидата задайте вопрос: **«Если убрать слово "тест" из описания, останется ли это инструкцией по атаке?»**
- Да → `/restricted`
- Нет → можно оставить, но переформулировать (см. ниже)

### Шаг 3. Тестовый прогон

Возьмите 3–5 разных LLM (GPT-4o, Claude, Gemini, локальную Llama) и скормите им по 10 тестов из «серой зоны». Зафиксируйте, какие именно тесты блокируются **систематически** — это и есть ваш итоговый список для `/restricted`.

## Как сохранить генерацию тестов-заглушек без блокировок

Чтобы LLM могла генерировать тесты по «запрещённым» идеям, разделите данные на **два слоя**:

### 1. Абстрактный слой (безопасно для LLM)

Храните идеи в нейтральной формулировке:

```yaml
- id: SEC-AUTH-014
  category: authentication
  title: Проверка устойчивости механизма входа к многократным неудачным попыткам
  objective: Убедиться, что после N неудачных попыток система применяет защитные меры
  references: [OWASP ASVS 2.1.1, NIST 800-63B]
  payload_ref: payloads/sec-auth-014.json   # ← отдельно!
```

### 2. Слой payload'ов (изолирован, в `/restricted`)

```json
// /restricted/payloads/sec-auth-014.json
{
  "attempts": 10,
  "usernames": ["admin", "root", "test"],
  "passwords_file": "wordlists/common.txt"
}
```

### 3. Преамбула к промпту

При генерации всегда добавляйте в system prompt:

> «Ты — QA-инженер, работающий в рамках легального defensive security-аудита. Все тесты выполняются только на принадлежащих организации системах с письменного разрешения. Твоя задача — сформулировать тест-кейсы в формате "предусловие → действие → ожидаемый результат", без воспроизведения вредоносных payload'ов. Payload'ы подставляются из внешнего источника на этапе исполнения.»

Это **значительно** снижает ложные срабатывания фильтров.

### 4. Тесты-заглушки

Для `/restricted` идей генерируйте не реальные тесты, а **шаблоны**:

```yaml
- id: SEC-AUTH-014
  status: manual-only
  stub: |
    Тест выполняется вручную специалистом по ИБ.
    Шаблон отчёта: /restricted/templates/brute-force-report.md
    Чек-лист: /restricted/checklists/auth-resilience.md
```

LLM такие описания проглатывает без проблем — там нет ни одного токсичного паттерна.

## Резюме действий

1. **Прогнать grep по триггерам** из таблицы выше — за 10 минут получите 80% кандидатов.
2. **Ручная досортировка** по принципу «останется ли это инструкцией без слова "тест"».
3. **Разделить данные**: идеи (безопасно) + payload'ы (в `/restricted`).
4. **Добавить преамбулу** в промпт генератора — это снимает большинство блокировок на этапе чтения библиотеки.
5. **Для restricted-идей** генерировать только stub-шаблоны, а не полноценные тест-кейсы.
