## Что стоит разбить, объединить или вынести за пределы API

1. Идея 1 — разбить на две записи. Инъекция в генерируемый исходный код и инъекция в DDL имеют разные механизмы, последствия и способы проверки. Оставить общий принцип обработки идентификаторов, но завести отдельные записи для code generation и SQL/DDL injection. `RES-DB-OBJECT-NAMES` сохранить как позитивную проверку допустимых имён.
2. Идея 2 — объединить четыре GHSA в одну запись с вариантами: callable в виде массива, bare-функция под denylist, статический метод `Class::method`, косвенный вызов через другую функцию. Не объединять с `INJ-USER-CODE-EXECUTION`.
3. Идеи 3–5 — сохранить как самостоятельные инварианты либо расширение существующей записи. Идею 5 лучше реализовать через `extends SEC-ALT-REPRESENTATION-ACCESS`.

Все пять идей потенциально пригодны для API-тестирования, но не все их аспекты можно проверить только HTTP-ответами: №1 — состояние БД и файловой системы стенда; №2 — наблюдение за стендом; №3 — внешний HTTP-приёмник; №4 — тестовый IdP; №5 — API поиска с разными уровнями доступа.

Общий вывод: главная ошибка кластеризации — объединение разных уязвимых механизмов по общему последствию (RCE) и смешение нормализации пользовательских логинов с точным сопоставлением внешней идентичности. Кроме того, идея 1 объединяет два независимых sink, а идея 5 уже близка к существующему инварианту доступа через альтернативные представления.
