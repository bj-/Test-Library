# 0004. Пополнение библиотеки идеями из открытых баг-трекеров

- **Статус:** принято
- **Дата:** 2026-10-13
- **Участники:** bj, Claude

## Контекст

Библиотеку нужно сильно расширить качественными идеями. Источник — открытые баг-трекеры (GitHub Issues, Apache JIRA,
Launchpad, GitLab, GHSA): реальные дефекты API-продуктов, найденные тестировщиками и пользователями. Нужно было
решить, чем обрабатывать тысячи багов, куда складывать кандидатов, как хранить доказательство происхождения идеи
и где держать инструменты. План — `Api/docs/BUG_MINING_PLAN.md`.

## Решение

1. **LLM — Claude Code, партиями**, без отдельного ключа Claude API. Расход — **не больше 5 % недельного лимита
   Claude в день** (на все машины вместе). Норма определяется калибровкой по `/usage`, расход ведётся в
   `Api/mining/budget.md`; партия, которая не укладывается в дневную норму, не начинается.
2. **Кандидаты — в `Api/ideas/mined/<batch>.md`**, а не в `inbox.md`. Это исключение из правила «любая идея сразу
   в inbox»: правило остаётся для идей, возникших в работе; машинные кандидаты из выгрузки идут в свой файл, чтобы
   ручные идеи не утонули. Разбор тот же: запись в `checks/`, дополнение существующей или отказ с причиной.
3. **Происхождение — метка и ссылка на трассировку.** Запись, основанная на реальном баге или подтверждённая им,
   получает метку `real-world-bug` и в `references` — `Real-world bug: RWB-NNNN`. Сами источники (URL бага и
   фикса, продукт, краткая суть своими словами) — в `Api/traceability/real-world-bugs.yaml`. Обычные инструменты
   этот файл не читают; он нужен, чтобы при вопросах «да как такое возможно?» показать пруфы. Валидатор проверяет,
   что ID существует.
4. **Скрипты — `Api/tools/mining/`** в этом репозитории; конфиг, промпты и журнал расхода — `Api/mining/`; сырые
   выгрузки — `Api/build/mining/`, не в git.
5. **Область — black-box поведение API.** Баги сборки, интерфейса, утечки памяти и внутренняя деградация в
   библиотеку пока не идут, но сохраняются с классом в корзину `out-of-scope` для будущего разбора.
6. **Пилот** — GitHub под наш стек (NestJS, Express и его body-parser/session/cookie, Keycloak, Strapi, Directus) и
   GHSA для npm, 300–500 багов; масштабирование — по метрикам пилота.

## Альтернативы

- **Claude API с Batch.** Быстрее и параллельнее, но нужны ключ и отдельный бюджет. Отказались: хватает лимита
  подписки при дневной норме.
- **Кандидаты в общий `inbox.md`.** Сотни машинных идей утопили бы ручные и смешали разные потоки разбора.
- **Только URL в `references`.** Это шумит в записях при обычной работе, а один баг часто подтверждает несколько
  записей. Отдельное поле `evidence` в схеме потребовало бы менять схему ради редкого сценария.
- **Отдельный репозиторий для выгрузки.** Промпты и скрипты завязаны на таксономию и каталог библиотеки; держать
  их рядом проще.

## Последствия

- Новая группа меток `origin` с меткой `real-world-bug` в `taxonomy/tags.yaml`, новый файл трассировки, проверка
  в `validate_library.py`.
- Шаги LLM растягиваются на календарные дни из-за нормы; конвейер обязан быть возобновляемым.
- Тексты чужих issue в git не попадают: только ссылки и краткая суть своими словами.
