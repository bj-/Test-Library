# 0012. Баги без исправления — кандидаты в идеи тестов

- **Статус:** принято
- **Дата:** 2026-10-23
- **Участники:** bj, Claude

## Контекст

`filter.py` отбрасывает issue, закрытые как COMPLETED без PR или коммита с исправлением (причина «нет PR/коммита
с исправлением»). Исключение — источники с `allow_no_fix` (nestjs-nest, express, grpc-gateway, graphql-js,
apollo-server), где мейнтейнеры не привязывают PR.

Эксперимент на kong (2026-10-23, сессия «Выгрузка багов — kong b-02», `Api/mining/nofix-review-kong.md`): из 142
отброшенных багов ценность как идея теста есть у 85 (60 %): 41 в 12 семействах (F1–F12), 35 пруфов к существующим
записям, 1 новая проверка, 6 DB, 2 UI; 6 — повторы уже разобранных с исправлением; 51 — не тест. В пачке kong b-02
с исправлениями доля API — 49 из 73 (67 %). Среди найденного есть серьёзное: чужой ответ под нагрузкой,
client_credentials с пустыми client_id и secret, принятие недоверенного сертификата бэкенда, неприменение ACL.

Отсутствие фикса не значит, что это не баг: часть исправлена без привязки PR, часть не исправлена, потому что
некому. По ADR 0002 разработчик — лишь одно из мнений, ожидание берётся из стандартов, практики и здравого смысла.

Масштаб — по `filter_stats.json`: kong 142, strapi 109, supabase-auth 85, kubernetes 73, keycloak 67,
postgrest 59, directus 53, grpc-go 48, grpc-java 24, grpc-node 6 — около 670 багов (~9 пачек по 80), у grpc-go
больше после сбора всей истории (решение bj 2026-10-23).

## Решение

1. **`allow_no_fix: true` — во всех источниках** (`defaults` в `sources.yaml`, решение bj). Для GHSA ничего не
   меняется: advisory и так сохраняется как опубликованное. Выключить у источника — явным `allow_no_fix: false`.
2. **Собирается вся история источника, а не до предела** (решение bj): `max_items: 100000` в `defaults` — баги
   вне API тоже пригодятся (нагрузка, Web, Desktop). Источникам с малой отдачей идей понижается приоритет в
   очереди (`mining/sessions.md`, `mining/metrics.md`), а не предел. У grpc-go кроме `Type: Bug` собираются
   `Type: Performance` и `Type: Security`. При смене меток `collect.py` сбрасывает курсор и собирает заново
   (сохранённые пропускаются).
3. **Триаж — тот же промпт, один проход, отдельные правила для `fix_evidence: closed-completed`:**
   - вопрос не «воспроизводится ли дефект», а «хорошая ли это идея теста»: стоит ли проверять такое поведение
     у любого API;
   - ожидание — из стандартов (RFC, OWASP), практики и здравого смысла, не из тестов фикса (их нет);
   - подтверждение разработчиком не пишет LLM: его выводят скрипты из `fix_evidence` (`pr`, `commit`, `published`
     — подтверждено; `closed-completed` — нет), в трассировке RWB и в пруфе записи это видно; `expected_source` —
     стандарт, «практика» или «здравый смысл»;
   - **подтверждение специально не отслеживаем** (решение bj): если при следующих сборах найдётся баг с
     исправлением на ту же проблему, он привяжется к той же записи обычным пруфом. Пруфы нужны прежде всего,
     чтобы показать, что проблема встречается в реальном мире и на неё жалуются пользователи;
   - в `out_of_scope` по-прежнему уходят вопросы и проблемы настройки (`usage`), установки и сборки (`build`),
     «мало данных» (`insufficient-data`).
4. **Семейства — на шаге 6, а не в триаже.** Триаж разбирает баги по одному, семейства видны только по
   нескольким багам сразу. В триаже — необязательное поле `family_hint` (короткий ключ, общий для похожих багов
   пачки, промпт — поле `family`). На шаге 6 `cluster.py` группирует по нему; в `review.yaml` у кластера — `variants:` (матрица вариантов)
   и баги не только `new`, но и `extends`. Одна запись с матрицей вместо нескольких похожих записей.
5. **Отбор по сигналам `comments` и `reactions` не делаем.** На эталоне kong они не отличают ценное: у «не тестов»
   комментариев больше (медиана 7 против 4), реакции редки в обеих группах (6 % и 18 %); порог «комментариев > 3»
   отрезал бы 34 ценных из 85.
6. **Эталон и пересбор kong.** 142 бага kong прогоняются новым промптом как обычные пачки (b-03, b-04) — это и
   калибровка: сверка с `nofix-review-kong.md`, спорные расхождения — bj. Строки inbox #366–#421 помечаются
   «→ kong b-03/b-04» и при разборе inbox не берутся: их идеи и пруфы идут через `out.jsonl`, `cluster.py`
   и `apply_proofs.py`.
7. **Пруфы из inbox (метка «П») в целом** — через новый триаж (п. 6), а не вручную. Пруфы «П», заведённые в inbox
   вне выгрузки, переносятся шагами при разборе inbox, как сейчас.
8. **Порядок:** остановить сессии сбора → промпт триажа и `cluster.py` → калибровка на kong → `allow_no_fix` в
   `defaults` → `filter.py` по собранным источникам (добавит только записи без фикса, обработанные остаются в
   `*.out.jsonl`, `batch.py make` возьмёт только необработанные) → пачки в сессиях сбора.

## Альтернативы

- **`allow_no_fix` по списку источников** — по отдаче на эталоне; отказались: эталон один, а включить на всех и
  выключить по метрикам дешевле, чем каждый раз оценивать вручную.
- **Отдельный промпт для багов без фикса** — отказались: формат ответа и сопоставление те же, расходятся только
  вопрос триажа и источник ожидания; два промпта рассинхронизируются.
- **`allow_no_fix` только для github-источников** — отказались (bj): правило одно для всех источников.
- **Поле `confirmed` в ответе LLM** — отказались: признак выводится из `fix_evidence`, а LLM могла бы ошибиться
  и признак всё равно должен совпадать с данными сбора.
- **Отдельный проход «семейства» по пачке в триаже** — отказались: пачка 80 багов одного источника, семейства
  складываются по всему источнику; дешевле на шаге 6, где источник виден целиком.
- **Ручная оценка, как в эксперименте kong** (заголовок + ~500 символов) — не масштабируется и не даёт `out.jsonl`
  для пруфов.

## Последствия

- ~670 багов (~9 пачек) без фикса и вся остальная история источников — пачек станет в разы больше; шаги 6–7 снова открываются у источников,
  где они уже пройдены.
- Записи и пруфы без подтверждения — ожидание не подтверждено разработчиком; падение теста по такой записи —
  находка для разбора, а не автоматически баг продукта.
- Меняется промпт триажа — только при остановленных сессиях сбора; `batch.py check` проверяет новые поля.
- `mining/metrics.md` — отдача отдельно по `fix_evidence` (исправленные и без фикса).
