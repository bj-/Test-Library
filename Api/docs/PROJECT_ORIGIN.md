# 1. Исходная идея проекта

## Цель

Создать версионируемую библиотеку проверок API, из которой можно автоматически подбирать и генерировать тестовые сценарии для конкретного контракта (в первую очередь OpenAPI/REST, с возможностью расширения на gRPC).

Библиотека должна быть источником повторно используемых проверок, а не набором тестов, безусловно применяемых ко всем сервисам. Генератор обязан учитывать контракт, бизнес-правила, модель доступа, риск и назначение запуска.

## Основные принципы

1. **Каталог проверок как данные.** Проверка хранится в структурированном YAML и проверяется JSON Schema.
2. **Одна запись — один инвариант/риск.** Это упрощает трассируемость, выборку, отчётность и устранение дубликатов.
3. **Разделение измерений.** Тип сценария (positive/negative/boundary), категория, приоритет, теги, профиль запуска и протокол — разные атрибуты.
4. **Контракт прежде предположений.** Ожидаемый статус, тело ошибки, nullability, правила неизвестных полей, права и бизнес-поведение не должны выдумываться генератором.
5. **Явная применимость.** Проверка включается только при выполнении предусловий; неприменимость и недостаток информации фиксируются отдельно.
6. **Проверка последствий.** Для запрещённых/изменяющих запросов важно проверять не только HTTP/gRPC-ответ, но и состояние ресурса после операции.
7. **Управляемый объём.** Smoke, PR/CI, Regression, Nightly и Release — профили выполнения, а не разновидности positive/negative.
8. **Безопасная генерация.** Сгенерированные проверки являются кандидатами до ревью и не вызывают целевой API сами по себе.

## Ожидаемый процесс

`API-контракт + модель доступа → инвентаризация операций → оценка применимости → выбор проверок → генерация кандидатов → валидация → ревью неопределённостей → тестовый раннер → отчёт о покрытии`.

## Критерий успеха

Для каждой операции можно объяснить, какие проверки применимы, почему они выбраны/исключены, к какому риску относятся, в какой профиль входят и какие решения требуют подтверждения владельца API.
