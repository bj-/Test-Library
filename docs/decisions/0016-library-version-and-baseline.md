# 0016. Версия библиотеки и база подбора без git

- **Статус:** принято
- **Дата:** 2026-10-30
- **Участники:** bj, Claude

## Контекст

Библиотека растёт, тесты нужно дополнять только по новым и изменённым записям. Сейчас это невозможно: в описании
коллекции стоит HEAD клона на момент сборки (`git_head()`), а не на момент подбора; реальный коммит подбора записан
вручную в `analysis-*.md`; у записей нет версии; неприменимые записи описаны группами, а не по одной. Сравнение с прошлым
коммитом (`Process/collections.md`) делается вручную.

Библиотекой пользуются и без репозитория (выгрузки `export_for_llm.py`, веб-LLM), поэтому опираться на коммиты нельзя.

## Решение

1. **Версия - в данных библиотеки.** `Api/manifest.yaml` генерируется инструментом и хранится в библиотеке: версия
   `<дата>-<хеш>`, охват (`full` / `partial`), по каждой записи статус, хеш записи и хеши шагов. Хеш - от разобранного
   YAML, а не от байтов; в него входят `steps`, `expected`, `preconditions`, `applicability`. Описание и теги не входят:
   их правка не требует новых тестов. Версию вручную не меняют.
2. **Выгрузка несёт свой манифест** только с записями архива. Закрытые записи в него не попадают. Частичная выгрузка -
   `scope: partial`: запись вне её считается «нет в поставке», а не «удалена».
3. **База подбора - в проекте тестов:** `docs/modules/<Модуль>/library-baseline.yaml`: версия библиотеки и по каждой
   записи решение (`applied`, `needed` - применима, тестов нет, `not_applicable` с причиной, `human`, `pending`), хеш
   записи и хеши шагов.
4. **Сравнение без git:** база + манифест или каталог библиотеки дают новые записи, изменённые записи и шаги, записи,
   ставшие `approved`, и удалённые. Есть инструмент; без него сравнение делается по двум YAML.
5. **База обновляется только при подборе и после генерации.** Решения вносит `apply`; `sync` после сборки переводит
   `needed` с тестами в `applied` и версию подбора не меняет. В описании коллекции две версии: «подбор» из базы и
   «сборка» из манифеста. Порядок догенерации - `Process/collections.md`, п. 4; хвост `needed` в неё не входит.
6. **Первая база BFF-Mobile:** скрипт отсекает записи по протоколу и переносит применённые из тестов; остальное решает
   модель: сначала сокращённый проход, спорные записи - полным текстом. Функциональные записи и записи групп
   безопасности - в разных сессиях (`claude-sonnet-5-5`, решение bj 2026-10-30 на эту задачу; `executors.child.model` не
   меняется). `sg-restricted` и записи с `automation.ai_generation.restricted` модель не разбирает: решение `human`.

## Альтернативы

- Коммит библиотеки как версия: не работает без репозитория.
- Поле `version` в каждой записи вручную: правка 631 записи и риск забыть поднять номер.
- ID у каждого шага: точнее показывает правку шага, но требует разметки всех шагов. Хеш шага показывает правку как
  удаление и добавление; шаг всё равно нужно пересмотреть.

## Последствия

- Манифест нужно пересобирать при правке записей; `validate_library.py` падает на устаревшем манифесте.
- Закрытые записи сравниваются только на полной копии библиотеки у человека.
- `Process/collections.md`: вместо коммита библиотеки - версия из манифеста и база подбора.
- Метка в уже собранной коллекции сменится при следующей генерации.
