Анализ текущего состояния репозитория показывает, что он уже начал эволюционировать в сторону многопрофильной библиотеки (например, ADR 0006 добавил `checks/ui/` и `checks/db/`). Однако корневая папка `Api/` и текущая группировка создают концептуальное ограничение: библиотека позиционируется как "API-библиотека", хотя вы хотите сделать её универсальным генератором для всех видов тестирования.

Ниже представлен **новый вариант структуры**, который снимает это ограничение, систематизирует направления и закладывает фундамент для масштабирования (включая генерацию тестов и мобильную специфику, которой вы интересуетесь).

### 🏗 Предлагаемая новая структура репозитория

```text
Test-Library/
├── docs/                       # Управление знаниями (без изменений)
│   ├── decisions/              # ADR (архитектурные решения)
│   ├── STATUS.md               # Текущий статус, блокеры, журнал
│   ├── ideas.md                # Бэклог идей
│   └── CATALOG.md              # Агрегированный каталог всех проверок
│
├── Process/                    # Процессы и регламенты (без изменений)
│   ├── collections.md          # Правила создания коллекций
│   ├── running-tests.md        # Правила запуска
│   ├── bugs.md                 # Оформление багов
│   └── templates/              # Шаблоны багов и отчётов
│
├── core/                       # Ядро библиотеки (бывшее Api/, обобщённое)
│   ├── schema/                 # JSON Schema для валидации записей и профилей
│   ├── taxonomy/               # Словари: категории, метки, приоритеты, протоколы
│   ├── profiles/               # Профили запуска (smoke, ci, regression, nightly, performance)
│   ├── selection-rules/        # Правила отбора и ранжирования проверок
│   ├── validation/             # Критерии качества библиотеки и метрики покрытия
│   └── tools/                  # Скрипты: assign_profiles.py, валидаторы, генераторы каталога
│
├── checks/                     # 🌟 Каталог проверок (основная реорганизация)
│   ├── common/                 # Протокольно-независимые проверки: бизнес-логика, конкурентность, 
│   │                           # обработка ошибок, совместимость, наблюдаемость, async
│   ├── api/                    # Проверки уровня API (перенесено из Api/checks)
│   │   ├── rest/
│   │   ├── grpc/
│   │   ├── graphql/
│   │   └── websocket/
│   ├── ui/                     # Проверки пользовательского интерфейса
│   │   ├── web/                # Кроссбраузерность, адаптивность, DOM-состояния
│   │   ├── mobile/             # iOS/Android специфика, жесты, прерывания (звонки, push), 
│   │   │                       # ориентация экрана, парк устройств (связь с вашими интересами в Xcode/Android Studio)
│   │   └── desktop/            # Desktop-приложения (при необходимости)
│   ├── database/               # Проверки данных и БД (развитие checks/db)
│   │   ├── sql/                # SQL-запросы, транзакции, миграции
│   │   ├── integrity/          # Целостность данных, консистентность, каскадные удаления
│   │   └── nosql/              # MongoDB, Redis, Elasticsearch (на вырост)
│   ├── security/               # Пентест и безопасность (расширение checks/security)
│   │   ├── auth/               # Аутентификация и сессии (JWT, OAuth, cookies, Bearer)
│   │   ├── injection/          # Инъекции (SQL, NoSQL, XSS, Command, LDAP)
│   │   ├── access-control/     # IDOR, RBAC, ABAC, горизонтальный/вертикальный доступ
│   │   └── hardening/          # Заголовки безопасности, шифрование, приватность (OWASP Top 10)
│   ├── performance/            # Нагрузочные и стресс-тесты (новое направление)
│   │   ├── load/               # Нагрузочное тестирование (RPS, throughput, целевые метрики)
│   │   ├── stress/             # Стресс-тестирование (за пределами возможностей, восстановление)
│   │   ├── endurance/          # Тестирование на выносливость (soak testing, утечки памяти)
│   │   └── spike/              # Спайк-тестирование (резкие скачки нагрузки)
│   ├── accessibility/          # Доступность (a11y): скринридеры, контрастность, навигация с клавиатуры
│   └── generated/              # Кандидаты из реальных контрактов (статусы: draft / needs_clarification)
│
├── generators/                 # 🌟 Инструменты генерации (новое направление)
│   ├── api/                    # Генерация из OpenAPI/Swagger, gRPC proto, Postman Collections
│   ├── ui/                     # Генерация сценариев для Playwright, Cypress, Appium (с учётом устройств)
│   ├── db/                     # Генерация SQL-скриптов для проверки целостности или тестовых данных
│   ├── performance/            # Генерация скриптов для k6, JMeter, Gatling
│   └── data/                   # Генерация синтетических тестовых данных (faker, граничные значения)
│
└── README.md                   # Главный файл с обзором новой структуры и быстрым стартом
```

### 💡 Обоснование ключевых изменений

1. **Уход от названия `Api/` к `core/` и `checks/`**: Это снимает психологический и архитектурный барьер. Теперь очевидно, что библиотека универсальна. Ядро (`core`) отвечает за *как* мы храним и валидируем правила, а `checks` отвечает за *что* мы проверяем.
2. **Детализация `ui/` и `database/`**: Выделение `mobile/` внутри `ui/` позволит вам применять знания о тестировании мобильных приложений (устройства, Xcode, Android Studio) напрямую в структуру проверок (например, добавляя проверки на прерывания или специфичные жесты).
3. **Выделение `performance/` и `security/`**: Это не просто "ещё один вид проверок", а целые дисциплины со своей таксономией, инструментами и метриками. Их выделение в отдельные папки упрощает интеграцию со специализированными генераторами (например, k6 для нагрузки или ZAP для безопасности).
4. **Появление папки `generators/`**: Поскольку вы хотите "сильный инструмент по генерации", логично отделить *декларативные правила* (папка `checks/`) от *исполняемого кода генераторов* (папка `generators/`). Это позволяет генерировать тесты для разных фреймворков (Postman, Playwright, JMeter) из одних и тех же исходных правил.
5. **Сохранение `common/`**: Бизнес-логика и конкурентность часто проверяются одинаково, независимо от того, делается запрос через API или через UI. Эта папка предотвращает дублирование правил.

### 🔄 План безопасной миграции (с сохранением истории Git)

Чтобы не потерять историю коммитов и не сломать текущие процессы, миграцию нужно делать через `git mv`:

1. **Создайте новую структуру папок** в локальном репозитории.
2. **Переместите файлы с сохранением истории**:
   ```bash
   git mv Api/schema core/schema
   git mv Api/taxonomy core/taxonomy
   git mv Api/profiles core/profiles
   git mv Api/selection-rules core/selection-rules
   git mv Api/validation core/validation
   git mv Api/tools core/tools
   
   git mv Api/checks/common checks/common
   git mv Api/checks/rest checks/api/rest
   git mv Api/checks/grpc checks/api/grpc
   # ... и так далее для всех папок
   ```
3. **Обновите ссылки в документации**: Найдите и замените все упоминания `Api/` на `core/` или `checks/` в файлах `CLAUDE.md`, `docs/STATUS.md`, `docs/decisions/` и `README.md`.
4. **Обновите скрипты**: Проверьте `core/tools/assign_profiles.py` и другие утилиты, чтобы они указывали на новые пути (`checks/` вместо `Api/checks/`).
5. **Сделайте коммит с понятным сообщением**: `refactor: reorganize repository structure to support multi-domain test generation (API, UI, DB, Security, Performance)`.

### 🚀 Рекомендации по развитию генераторов (с учётом ваших интересов)

1. **Для Mobile UI**: В генераторе `generators/ui/` можно добавить конфигурацию парка устройств (device farm), чтобы при генерации тестов для Appium или Playwright автоматически подставлялись нужные `deviceName`, `platformVersion` и разрешения экранов.
2. **Для чек-листов**: Поскольку вы уделяете внимание правильным практикам составления чек-листов, скрипт в `core/tools/` может генерировать Markdown- или PDF-чеклисты (аналогично вашему `complete-web-application-testing-checklis.pdf`) напрямую из структурированных данных папки `checks/`, фильтруя их по тегам (например, "только security" или "только mobile").
3. **Для SQL и БД**: Генератор `generators/db/` может брать правила из `checks/database/integrity/` и автоматически создавать SQL-запросы для проверки каскадных удалений или триггеров, что особенно полезно при ограниченных правах доступа, так как позволяет готовить скрипты заранее.

Эта структура сделает библиотеку по-настоящему модульной: добавление нового направления (например, `blockchain/` или `iot/`) сведётся к созданию одной новой папки в `checks/` и описанию правил в `taxonomy/`, без необходимости переписывать ядро системы.
