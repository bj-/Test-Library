# 0005. Итог пилота выгрузки багов: масштабирование после проверки точности

- **Статус:** принято
- **Дата:** 2026-10-14
- **Участники:** bj, Claude

## Контекст

Пилот выгрузки из баг-трекеров (ADR [0004](0004-bug-tracker-mining.md), этапы 1–6 `Api/docs/BUG_MINING_PLAN.md`)
обработан полностью: 1022 собрано → 696 после фильтра → 360 API-багов → 50 новых записей `draft` и пруфы у 129
существующих (47,5 % записей библиотеки с `real-world-bug`). Расход — ≈ 0,8 % недельного лимита на 100 багов,
≈ 0,11 % на принятую идею. Этап 7 — решение go/no-go. Метрики и выводы — раздел «Оценка пилота»
`Api/build/mining/pilot/REPORT.md`.

Точность LLM-шагов не измерена: ревью кандидатов было целиком по предложению Claude, без независимой проверки.

## Решение

1. **Go при условии точности.** Масштабирование начинается после ручной разметки выборки
   `Api/ideas/mined/pilot.accuracy.xlsx` (50 решений триажа, 30 сопоставлений; сборка и расчёт — `tools/mining/accuracy.py`): верных не меньше 85 % в каждой
   части. Ниже порога — сначала правка промпта и повторная выборка на новой партии.
2. **Источники при масштабировании** — по выходу идей пилота: GHSA (другие экосистемы: PyPI, Maven, Go, RubyGems),
   Keycloak глубже по истории, Directus и Strapi за прошлые годы, продукты-API из плана (Kubernetes apiserver,
   GitLab, Supabase/PostgREST, Hasura, Kong), для пробелов библиотеки — gRPC (`grpc/grpc-*`, `grpc-gateway`) и
   GraphQL (`graphql-js`, Apollo Server).
3. **NestJS, Express и их пакеты** — только инкрементальная докачка с предфильтром по заголовку (`exclude_title`
   в `Api/mining/sources.yaml`): доля API 22–24 %, 2,5 идеи на 100 собранных при ≈ 37 % расхода пилота.
4. **Промпт и инструменты** (сделано вместе с решением): корзина `other` разделена на `framework-internal`,
   `usage`, `insufficient-data`, `client-lib`; правило «отложенное проявление в ответах API — это `api`»; в `match`
   отдельное поле `variant` — шаг в повелительной форме, `batch.py check` его проверяет.
5. **Ревью следующих партий** — решения по кластерам принимает человек до применения, а не «принять всё».

## Альтернативы

- **Go сразу по рекомендациям.** Быстрее, но доля принятых 94 % при ревью «целиком» ничего не говорит о точности;
  ошибки триажа масштабировались бы вместе с объёмом.
- **Пауза до вычитки всех 50 draft.** Вычитка нужна для перевода в `approved`, но не для оценки конвейера;
  выборки точности достаточно.

## Последствия

- Блокер масштабирования — разметка `pilot.accuracy.xlsx` человеком: первый проход Claude по первоисточникам, человек — строки «обязательно» и «выборочно» (≈ 25 из 80).
- Результаты пилота, полученные старым промптом, остаются как есть; новые поля и классы действуют с первой партии
  после пилота. `cluster.py` берёт `variant`, если он есть, иначе вырезает вариант из `note` (пилот).
- Метрики следующих партий считает `tools/mining/evaluate.py`; расход шагов 6–7 замерять по `/usage` отдельно.
