# Архитектура и процессы автономной системы тестирования (QualityOps AI)

## 1. Цели и философия
*   **Главная цель:** Полное исключение человека из цикла тестирования (Generative Testing & Autonomous Execution).
*   **Побочная цель:** Исключение разработчика из первичного анализа багов. Система должна предоставлять исчерпывающий, структурированный контекст (артефакты, логи, гипотезы, диффы), достаточный для другого AI-Агента или разработчика для мгновенного внесения фикса (Zero-Touch Triage).
*   **Принцип:** "Тест — это исполняемая спецификация". Каждый тест должен быть напрямую связан с требованием и объяснять, *почему* он существует.

## 2. Структура проекта и репозиториев

Рекомендуется использовать подход "QualityOps Monorepo" или строго линкованный полирепозиторий, чтобы отделить инфраструктуру качества от кода продукта, но иметь к нему прямой доступ.

```text
quality-ops-repo/
├── docs/                          # Исходные и нормализованные требования
│   ├── raw/                       # Оригинальные PDF/DOCX/MD (ФТТ, ОТЗ, ЧТЗ, ПМИ, ПСИ)
│   └── normalized/                # Единый машиночитаемый формат (например, JSON/YAML граф требований)
├── tests/                         # Сгенерированные и ручные тесты
│   ├── api/                       # Postman коллекции (файловая система, см. ниже)
│   ├── ui/                        # Playwright/Cypress скрипты
│   ├── e2e/                       # Сценарии взаимодействия модулей
│   └── non_functional/            # k6 (нагрузка), chaos (стабильность), zap (безопасность)
├── framework/                     # Обертки и утилиты
│   └── postman-scripts-wrapper/   # Интеграция с https://github.com/bj-/PostmanScripts/
├── config/                        # Конфиги стендов, переменные окружения, маппинг модулей
├── reports/                       # Локальные кэши отчетов (основное хранение в S3/MinIO)
└── knowledge_base/                # Векторное хранилище (RAG) исторических багов и решений
```

### 2.1. Структура хранения Postman коллекций
Для обеспечения контроля версий и точечных запусков, коллекции не должны храниться как один бинарный файл. Используйте инструмент вроде `postman-to-json` или нативные возможности Postman для экспорта в файловую систему:
```text
tests/api/
├── module_a/
│   ├── collection.json            # Метаданные коллекции
│   ├── endpoints/
│   │   ├── GET_users/
│   │   │   ├── request.json       # Тело запроса, заголовки
│   │   │   ├── tests.js           # Скрипт проверки (использует bj-/PostmanScripts)
│   │   │   └── metadata.yaml      # Ссылка на требование: req_id: "OTZ-2.1.3", description: "Проверка..."
```

## 3. Процесс генерации и управления тестами

### 3.1. Нормализация требований (Requirement Graph)
Прежде чем генерировать тесты, Агент должен создать "Граф требований":
1. Парсинг ФТТ, ОТЗ, ЧТЗ, ПМИ, ПСИ.
2. Присвоение уникальных ID каждому атомарному требованию (например, `REQ-MOD1-PSI-004`).
3. Выявление противоречий между документами (если ФТТ говорит одно, а ЧТЗ другое) и запрос уточнения у пользователя *до* генерации тестов.

### 3.2. Принцип генерации тестов (Traceability First)
Каждый сгенерированный тест (Postman, UI, E2E) обязан содержать метаданные:
*   `requirement_id`: Ссылка на узел в Графе требований.
*   `test_intent`: Описание на естественном языке: "Что проверяем, зачем, как и почему".
*   `generation_context`: Хэш коммита кода продукта и версия документа, на основе которых тест создан.
*   `dependencies`: Какие модули или данные нужны для запуска.

### 3.3. Расширение видов тестирования (Идеи для внедрения)
*   **Контрактное тестирование (Pact):** Для взаимодействия модулей. Если модуль А меняет API, тесты модуля Б должны падать мгновенно.
*   **Мутационное тестирование:** Агент намеренно вносит мелкие ошибки в код (или в моки), чтобы проверить, действительно ли сгенерированные тесты способны обнаружить эту поломку. Если нет – тест считается бесполезным и перегенерируется.
*   **Chaos Engineering:** Для проверки "стабильности работы". Внедрение задержек сети, падение БД во время E2E прогона для проверки отказоустойчивости.

## 4. Оркестрация и запуск тестов

Система должна поддерживать динамический выбор тестов (Test Impact Analysis), чтобы не гонять всё подряд:
1. **Pre-commit / PR:** Только модульные и API тесты затронутых модулей.
2. **Nightly Build:** Полная регрессия + тесты безопасности (базовые).
3. **Release Candidate (Stage):** Полный прогон ПМИ/ПСИ. Генерация итогового протокола.
4. **Production:** Синтетические мониторинговые тесты (Smoke) каждые N минут.

**Механизм запроса ресурсов:**
Если для генерации или выполнения теста нужен доступ к БД, специфичный мок или переменная стенда, Агент на этапе генерации создает файл `resource_request.yaml`:
```yaml
test_id: "TEST-E2E-001"
requires:
  - type: "database"
    target: "module_b_db"
    access: "read_only"
    purpose: "Проверка корректности записи транзакции после вызова API"
  - type: "env_variable"
    name: "FEATURE_FLAG_X"
    value: "true"
```
CI/CD система читает этот файл и подготавливает окружение перед запуском.

## 5. Хранение отчетов и артефактов

Отчеты должны быть машиночитаемыми для последующего анализа другими Агентами.

### 5.1. Форматы хранения
*   **Allure Report:** Для визуального анализа (если человек все же заглянет).
*   **Markdown + JSON:** Основной формат для AI. JSON содержит структурированные данные (статус, время, ошибки), MD – человекочитаемое резюме.
*   **Артефакты:** Скриншоты, видео (для UI), HAR-файлы (сетевые запросы), дампы логов приложения и БД в момент падения.

### 5.2. Стратегия хранения (S3/MinIO)
Строгая иерархия папок для легкого поиска:
`s3://quality-artifacts/{project_name}/{module_name}/{build_hash}/{timestamp}/{test_type}/`
*Важно:* В корне папки прогона должен лежать файл `manifest.json`, описывающий, какой именно срез кода и требований тестировался.

## 6. Автономный жизненный цикл бага (Zero-Touch Triage)

Это ключевой блок для достижения побочной цели. При падении теста запускается **Bug Analysis Agent**:

1. **Анализ падения:** Агент читает лог ошибки, HAR-файл, состояние БД.
2. **Дедупликация (Semantic Deduplication):** Агент делает векторный поиск по существующим багам в Jira/YouTrack/Redmine. Сравнивает не только текст, но и стек-трейс, и контекст требования.
   * *Если дубликат найден:* Агент добавляет комментарий в существующий баг: "Воспроизведено снова в билде {X}. Ссылка на прогон: {URL}. Статус: Активен".
   * *Если баг новый:* Переходит к шагу 3.
3. **Обогащение баг-репорта (AI-Generated Bug Report):**
   * **Заголовок:** Четкий, технический.
   * **Связь:** Ссылка на требование (ПМИ/ЧТЗ), которое нарушено.
   * **Шаги воспроизведения:** Автоматически извлеченные из теста.
   * **Артефакты:** Прямые ссылки на логи, скриншоты, HAR.
   * **Гипотеза корневой причины (Root Cause Hypothesis):** Агент анализирует стек-трейс и, имея доступ к коду, указывает: *"Вероятная причина: в файле `src/service.py` строка 45 не обрабатывает null-значение, приходящее из модуля А"*.
   * **Предлагаемый фикс (Optional):** Агент генерирует Git Diff с исправлением и прикрепляет его к тикету.
4. **Работа с "Мигающими" (Flaky) тестами:** Если тест падает нестабильно, Агент автоматически помещает его в карантин (`quarantine`), создает задачу на исследование стабильности теста и исключает его из блокирующих релиз проверок до выяснения обстоятельств.

## 7. Инфраструктурные и процессные идеи для расширения

1. **RAG (Retrieval-Augmented Generation) для тестирования:** 
   Создать векторную базу данных, в которую загружаются: все требования, история всех багов, документация по API и архитектура. При генерации нового теста Агент сначала опрашивает эту базу: *"Какие баги уже были в этом модуле? Как мы их проверяем?"*, чтобы не повторять ошибок прошлого.
2. **Динамическая адаптация тестов (Self-Healing):**
   Если UI-тест упал из-за смены CSS-селектора, Агент анализирует DOM-дерево, находит наиболее похожий элемент по атрибутам (текст, роль, расположение) и автоматически обновляет тест, создавая PR с пометкой "Auto-healed".
3. **Генерация синтетических данных:**
   Вместо хардкода данных, Агент должен генерировать валидные, но уникальные данные (например, через библиотеки типа Faker или LLM-генерацию) для каждого прогона, чтобы избежать зависимостей от состояния БД.
4. **Валидация документации:**
   Если Агент не может сгенерировать тест, потому что требование в ЧТЗ сформулировано неоднозначно ("система должна работать быстро"), он автоматически создает задачу на уточнение требований и блокирует генерацию до получения ответа.

## 8. Резюме для исполняющего Агента

При реализации данной системы:
1. Начните с создания **Графа требований** (нормализация документов). Без этого невозможна прослеживаемость.
2. Интегрируйте `bj-/PostmanScripts` как ядро для API-проверок, но оберните его в мета-уровень управления (генерация `.json` файлов из шаблонов с привязкой к ID требований).
3. Реализуйте пайплайн **Bug Analysis Agent** как отдельный сервис, который срабатывает на webhook от CI/CD при статусе `FAILED`.
4. Не бойтесь запрашивать у пользователя доступы (read-only к БД, к репозиторию кода) на этапе инициализации. Это критически важно для глубокого анализа и предложения фиксов.
5. Постоянно ведите лог решений: почему был выбран тот или иной инструмент или структура. Это поможет в дальнейшей само-оптимизации системы.
