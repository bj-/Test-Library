## 3\. Что выносить в общее ядро, а что оставлять в направлениях

Это, на мой взгляд, самое важное решение всей реорганизации. Ошибка здесь обычно приводит либо к дублированию кода, либо к слишком абстрактному ядру, которое мешает развитию направлений.

| Компонент | Общее ядро | Специфика направления |
|--------|--------|--------|
| AI/LLM | Подключение провайдеров, retry, structured output | Инструкции и стратегии генерации |
| Контекст | Общие интерфейсы, нормализация, метаданные | OpenAPI, DOM, схема БД, мобильное приложение |
| Генерация | Pipeline, управление этапами, обработка ошибок | Типы тестов, алгоритмы и правила |
| Шаблоны | Реестр, версии, загрузка, общие переменные | Доменные промпты и шаблоны |
| Модели | Общие метаданные, статусы, происхождение | API request, UI action, SQL assertion |
| Валидация | Проверки структуры, обязательных полей | Семантическая корректность и исполнимость |
| Исполнение | Общие контракты запуска и результаты | Playwright, Appium, SQL engine, security tools |
| Отчёты | Общий формат результатов и метрики | Специфические метрики направления |

Например, в ядре может существовать общий контракт результата генерации\:

```python
class GeneratedTest:
    id: str
    domain: str
    test_type: str
    title: str
    steps: list
    expected_result: str
    metadata: dict
```

Это только иллюстрация: реальные типы лучше делать типизированными и расширяемыми, а не сводить всё к универсальному набору полей.

API-тесту могут понадобиться HTTP-метод и ожидаемый статус, UI-тесту - локаторы и действия, SQL-тесту - запрос и ожидаемые данные. Поэтому я бы предусмотрел общий envelope и специализированные модели\:

```text
GeneratedTest
├── ApiTest
├── WebUiTest
├── MobileUiTest
├── SqlTest
└── SecurityTest
```

Общая модель нужна для каталога, отчётов, метрик и управления жизненным циклом теста. Доменные модели нужны для семантики и исполнимости.

## 4\. Отдельный уровень: типы тестов и стратегии генерации

Есть ещё одно измерение, которое важно не перепутать с направлениями.

Направление отвечает на вопрос: *что тестируем?*

Тип теста отвечает на вопрос: *что именно хотим проверить?*

Стратегия отвечает на вопрос: *как генерируем проверки?*

Например\:

НАПРАВЛЕНИЕ

**API Testing**

REST, GraphQL, gRPC

---

ТИПЫ ТЕСТОВ

(Positive) (Negative) (Boundary) (Contract) (Security) (Resilience)

---

СТРАТЕГИИ

(Equivalence partitioning) (Boundary value analysis) (Pairwise) (Property-based) (Risk-based)

При этом стратегии не обязательно должны быть полностью общими. Например, boundary value analysis применим к API, UI-формам и данным, но конкретные способы получения границ и построения проверок будут отличаться.

Поэтому полезно разделить\:

- общие концепции тест-дизайна;
- реализации стратегий для конкретных доменов;
- генераторы, которые применяют эти стратегии к конкретному контексту.

Так в будущем можно добавлять новый тип тестирования без копирования всех существующих алгоритмов.

## 5\. Унифицированный pipeline генерации

Я бы сделал единый жизненный цикл генерации, но позволил бы каждому направлению подключать собственные этапы.

Ключевое преимущество - не нужно разрабатывать собственную архитектуру pipeline для каждого направления.

Например, API и Web UI могут использовать одинаковые этапы контекста, планирования, генерации и валидации. Но Web UI может добавлять этап анализа DOM, а SQL - проверки диалекта, доступности тестовой схемы и ограничений транзакций.

Ещё я бы разделил два независимых действия\:

1. **Generate** - создать тест-кейсы или код.
2. **Execute** - исполнить полученные тесты.

Это особенно важно для Pentest: генерация плана проверки не должна автоматически означать запуск потенциально разрушительных действий.

## 6\. Как обеспечить расширяемость новыми направлениями

Чтобы библиотека не превратилась в цепочку условий вроде `if domain == "api"`, я бы ввёл контракт направления и реестр модулей.

Упрощённая иллюстрация\:

```python
from typing import Protocol, Any

class TestDomain(Protocol):
    name: str

    def build_context(self, source: Any) -> Any: ...
    def generate(self, context: Any, options: Any) -> Any: ...
    def validate(self, result: Any) -> Any: ...

class DomainRegistry:
    def __init__(self):
        self._domains = {}

    def register(self, domain: TestDomain):
        self._domains[domain.name] = domain

    def get(self, name: str) -> TestDomain:
        return self._domains[name]
```

Тогда использование платформы будет выглядеть примерно так\:

```python
domain = registry.get("web_ui")

context = domain.build_context(source)
result = domain.generate(context, options)
validated = domain.validate(result)
```

Это демонстрация принципа, а не готовая реализация: в production потребуются типизированные контракты, регистрация зависимостей, обработка ошибок, управление версиями и тесты совместимости.

### Что должен предоставлять каждый домен

- `manifest` - имя, версия, возможности и зависимости.
- `models` - модели входных данных и результата.
- `context builder` - преобразование источников в контекст.
- `generators` - доступные типы генерации.
- `validators` - проверки корректности.
- `exporters` - поддерживаемые форматы.
- `capabilities` - доступные функции, например генерация кода, анализ покрытия или исполнение.

В дальнейшем это позволит подключать даже сторонние расширения. Но я бы начинал с внутренних модулей в одном репозитории и переходил к независимым пакетам только тогда, когда появится реальная потребность в отдельном релизном цикле.

Если библиотека активно использует LLM, я бы сразу предусмотрел отдельную архитектуру шаблонов.

Это поможет отслеживать, почему новая версия генератора стала создавать другой результат и не снизила ли она качество.

## 8\. Что делать с API-модулем, который уже существует

Не стал бы начинать с полного переписывания.

Оптимальный вариант - **постепенный рефакторинг с сохранением обратной совместимости**\.

1. Зафиксировать текущие публичные интерфейсы, форматы результатов и тесты API-генератора.
2. Выделить повторно используемые компоненты: LLM-клиенты, общие модели, обработку ошибок, конфигурацию и работу с шаблонами.
3. Перенести API в `domains/api/`, сохранив старые импорты через compatibility wrappers, если они используются внешними потребителями.
4. Ввести контракт домена и подключить API через реестр.
5. На примере Web UI проверить, действительно ли абстракции ядра позволяют добавить новое направление без дублирования и специальных обходных решений.
6. После этого подключать SQL и Security Testing, уточняя общие контракты на основании реальных потребностей.

Не стоит сначала проектировать универсальную платформу на все возможные случаи. Первое новое направление поможет понять, какие абстракции действительно общие, а какие были бы преждевременными.

## 9\. Какой вариант я бы выбрал в итоге

Я бы зафиксировал пять архитектурных принципов\:

1. **Domain-first\:** каждое направление - самостоятельный модуль со своими моделями и логикой.
2. **Shared core\:** общее ядро содержит инфраструктуру, а не доменные сценарии.
3. **Pluggable generation\:** новые генераторы подключаются через контракты и реестр.
4. **Generate ≠ Execute\:** создание теста отделено от его запуска.
5. **Common lifecycle, domain-specific behavior\:** общий pipeline при сохранении специфики каждого направления.

Есть и альтернативы. Можно построить библиотеку вокруг отдельных пакетов по типам технологий, например `api-generator`, `ui-generator`, `sql-generator`\. Это проще на старте, но общие механизмы быстро начнут дублироваться. Полностью плагинная архитектура с отдельными пакетами, в свою очередь, добавит лишнюю сложность, пока направлений мало.

Поэтому на текущем этапе я рекомендую **модульный монолит с доменными пакетами и чёткими контрактами**\. Он даст большую часть преимуществ расширяемости без преждевременного усложнения инфраструктуры.

## 2\. Целевая архитектура репозитория

Моя рекомендация - **единый репозиторий, разделённый на каталог знаний, движок генерации, доменные модули и адаптеры исполнения**\.

Не нужно сразу переходить к нескольким устанавливаемым пакетам. Сейчас важнее определить границы ответственности. Если позднее отдельные направления начнут развиваться независимо, их можно будет выделить в пакеты без повторного проектирования всей системы.

Предлагаемая структура\:

## Test-Library/

Это целевая модель, а не инструкция перенести все существующие файлы за один коммит. Особенно важно не смешать каталог проверок с Python-кодом движка.

### Почему я предлагаю отдельный `catalog/`

Текущие YAML-записи - самостоятельный продукт библиотеки. Они содержат проверяемые риски, предусловия, действия, ожидаемые результаты, применимость, статусы, приоритеты и ссылки на доказательства.

Они не должны зависеть от того, каким инструментом будет сгенерирован или запущен тест.

Например, одна проверка может породить\:

- ручной чек-лист;
- тест-кейс в структурированном JSON;
- исполняемый тест на Python и Playwright;
- тест на TypeScript и Playwright;
- сценарий для другого UI-фреймворка.

Если каталог отделён от движка, развитие генераторов не потребует менять всю библиотеку проверок.

### Как организовать доменные модули

Внутри `src/test_library/domains/` я бы использовал единый шаблон\:

```text
domains/
├── api/
│   ├── context/
│   ├── generators/
│   ├── strategies/
│   ├── validators/
│   └── exporters/
├── web_ui/
│   ├── context/
│   ├── generators/
│   ├── strategies/
│   ├── validators/
│   └── exporters/
├── mobile_ui/
├── data/
└── security/
```

Необязательно, чтобы каждый модуль сразу содержал все эти каталоги. Их стоит создавать по мере реализации функциональности.

Для API останутся специфические механизмы работы с OpenAPI, GraphQL-схемами и protobuf. Для Web UI появятся анализ DOM, пользовательских потоков и локаторов. Для Mobile UI - анализ экранов, жестов, разрешений и состояния приложения. Для Data - схемы БД, SQL-диалекты, транзакции и проверки целостности.

Security будет иметь собственные генераторы сценариев и адаптеры специализированных инструментов. При этом общие правила безопасности, применимые к API, UI и БД, не нужно дублировать: их можно хранить в каталоге общих проверок или в тематическом каталоге security с корректной моделью применимости.

## 4\. Главный архитектурный вопрос: единая модель проверок или разные модели?

В текущей библиотеке уже есть полезное решение: единая схема `check.schema.json`, которая позволяет хранить API-, UI- и DB-проверки в одном формате. Я бы это решение сохранил, но не пытался бы сделать единую схему, описывающую абсолютно все особенности всех видов тестов.

Предлагаю использовать **общую модель каталога + доменные модели генерации + общую оболочку результата**\.

### Check Definition

ID, описание риска, применимость, предусловия, шаги, ожидания, приоритет, статус, traceability

**API Context**

OpenAPI, схемы, операции, модель доступа

**UI Context**

DOM, экраны, элементы, пользовательские потоки

**Data Context**

Схема БД, диалект, ограничения, данные

**Security Context**

Активы, границы доверия, разрешённые проверки

### Generated Artifact

Общие метаданные, источник, трассировка, статус валидации и доменная полезная нагрузка

### Общая модель записи в каталоге

Существующие поля `id`, `category`, `priority`, `applicability`, `steps`, `expected`, `profiles` и другие стоит сохранить, насколько это возможно.

Для дальнейшего развития полезно постепенно стандартизировать\:

- `domain` - `api`, `web_ui`, `mobile_ui`, `data`, `security`;
- `kind` - positive, negative, boundary и другие типы проверок;
- `applies_to` - протоколы, платформы и характеристики системы;
- `source_refs` - ссылки на требования, стандарты, спецификации и другие источники;
- `automation` - уровень автоматизации и детерминированность;
- `capabilities_required` - необходимые инструменты, доступы и инфраструктура.

Это предложение по целевой модели, а не утверждение, что все эти поля нужно немедленно добавить в текущую JSON Schema. Перед изменением схемы следует проверить, какие поля уже есть и какие дублировали бы существующие.

Для доменных особенностей лучше использовать расширения схемы, а не перегружать общий формат\:

```yaml
id: UI-WEB-FORM-REQUIRED-FIELD
domain: web_ui
kind: negative

applies_to:
  protocols:
    - ui-web

preconditions:
  - "Форма доступна пользователю"

steps:
  - action: "Оставить обязательное поле пустым"
  - action: "Отправить форму"

expected:
  - "Пользователь получает сообщение о необходимости заполнить поле"
  - "Некорректная форма не принимается"

automation:
  level: full
  deterministic: true

profiles:
  - Regression
```

Это лишь иллюстрация: конкретные поля и значения нужно согласовать с действующей схемой и таксономией.

А вот данные, необходимые для исполнения, лучше хранить в специализированной модели\:

```yaml
ui:
  platform: web
  locator_strategy: accessible_role
  expected_navigation: stay_on_form
```

В реальном проекте я бы выбрал один строго определённый формат расширений, а не разрешал произвольные YAML-поля без валидации.

## 5\. Интерфейсы движка генерации

Поскольку существующие инструменты написаны на Python, я бы реализовал новые контракты на Python с помощью `Protocol`, `dataclass` и типизированных моделей. Для примеров ниже можно использовать Pydantic или аналогичную библиотеку валидации.

### Общая модель результата

```python
from dataclasses import dataclass, field
from typing import Any, Literal

@dataclass
class GeneratedArtifact:
    id: str
    domain: str
    artifact_type: Literal[
        "test_case",
        "test_code",
        "checklist",
        "test_plan",
    ]
    source_check_ids: list[str]
    content: dict[str, Any]
    status: Literal[
        "generated",
        "validated",
        "needs_review",
        "rejected",
    ] = "generated"
    metadata: dict[str, Any] = field(default_factory=dict)
```

Здесь `content` - не замена типизированным моделям конкретных доменов. Это общий контейнер для хранения и передачи артефакта. На границе домена содержимое должно валидироваться соответствующей моделью.

### Контракт домена

```python
from typing import Any, Protocol

class TestDomain(Protocol):
    name: str

    def build_context(self, source: Any) -> Any:
        ...

    def generate(
        self,
        context: Any,
        checks: list[dict],
        options: dict,
    ) -> list[GeneratedArtifact]:
        ...

    def validate(
        self,
        artifacts: list[GeneratedArtifact],
    ) -> list[GeneratedArtifact]:
        ...
```

В этом интерфейсе намеренно нет методов `execute()` и `run_pentest()`\. Исполнение - отдельная ответственность, с отдельными разрешениями и ограничениями.

### Реестр направлений

```python
class DomainRegistry:
    def __init__(self) -> None:
        self._domains: dict[str, TestDomain] = {}

    def register(self, domain: TestDomain) -> None:
        if domain.name in self._domains:
            raise ValueError(f"Domain already registered: {domain.name}")
        self._domains[domain.name] = domain

    def get(self, name: str) -> TestDomain:
        try:
            return self._domains[name]
        except KeyError:
            raise ValueError(f"Unknown domain: {name}") from None
```

Регистрация API, Web UI, Mobile UI и SQL происходит независимо. При добавлении нового направления не нужно изменять селектор или общий pipeline, если новое направление соблюдает контракт.

Для реального production-кода я бы дополнил этот интерфейс версиями доменов, capabilities, конфигурацией и строгими типами входного контекста.

### Общий pipeline

```python
class GenerationPipeline:
    def __init__(self, registry, validator, exporter):
        self.registry = registry
        self.validator = validator
        self.exporter = exporter

    def generate(self, domain_name, source, checks, options):
        domain = self.registry.get(domain_name)

        context = domain.build_context(source)
        artifacts = domain.generate(context, checks, options)
        validated = domain.validate(artifacts)

        return self.exporter.export(validated, options)
```

Это иллюстрация границ ответственности, а не законченный production-код. В реальной реализации обработка ошибок, асинхронность, типизация, журналирование и экспорт должны быть самостоятельными компонентами.

И ещё одно важное уточнение: общий pipeline не должен навязывать каждому направлению одинаковый алгоритм. Он задаёт последовательность этапов, а конкретный домен определяет, как построить контекст и сгенерировать содержимое.

## 6\. Как разделить генерацию, экспорт и исполнение

Я бы предусмотрел три независимых интерфейса. Это особенно важно, поскольку ты хочешь генерировать не только сценарии, но и исполняемый код.

### Generator

Принимает контекст и набор проверок, возвращает структурированные тест-кейсы или план тестирования.

---

### Exporter / Code Generator

Преобразует тест-кейс в код конкретного фреймворка: pytest, Playwright, Appium и другие поддерживаемые форматы.

---

### Runner

Запускает готовый тест в разрешённом окружении, собирает результаты, логи и артефакты.

У каждого этапа должны быть свои критерии качества.

Например, генератор может создать корректный тест-кейс, но кодогенератор ошибиться с локатором. Или код будет синтаксически корректным, но тест не пройдёт из-за неверных предусловий. Такие ошибки необходимо диагностировать отдельно.

Для Security Testing разделение ещё важнее: генерация тестового сценария, проверка допустимости действия, исполнение и оценка доказательств уязвимости - разные этапы. Активный Pentest должен требовать явно заданной области разрешения, безопасного профиля и контроля потенциально разрушительных операций.

## 7\. Переход от текущего репозитория к целевому

Я бы выполнял реорганизацию в пять этапов. Поскольку существующий каталог уже содержит большую библиотеку проверок и инструменты анализа, нет смысла начинать с массового перемещения файлов.

1. **Этап 1. Зафиксировать существующий контракт**
   
   - Зафиксировать текущие результаты `validate_library.py`, `select_checks.py` и `build_catalog.py`\.
   - Добавить автоматические тесты для этих инструментов.
   - Зафиксировать количество проверок по статусам, категориям и протоколам.
   - Зафиксировать формат YAML и совместимость текущих CLI-команд.
   
   Критерий завершения: изменения структуры не приводят к незаметной потере проверок или изменению правил отбора.
2. **Этап 2. Выделить исполняемый Python-пакет**
   
   - Вынести общие функции из `Api/tools/library.py` в `src/test_library/`\.
   - Разделить CLI-команды и библиотечные функции.
   - Добавить `pyproject.toml`, зависимости и единый механизм запуска инструментов.
   - Оставить прежние команды рабочими через временные совместимые обёртки.
   
   Критерий завершения: инструменты используют общий пакет, а не импортируют функции друг у друга по случайным путям.
3. **Этап 3. Создать общий движок генерации**
   
   - Ввести типизированные модели входа и результата.
   - Реализовать реестр доменов.
   - Ввести общий pipeline и интерфейсы валидации и экспорта.
   - Подключить существующую логику отбора проверок.
   
   Критерий завершения: API-генератор работает через новый контракт, не ломая существующий каталог.
4. **Этап 4. Реализовать первый новый домен - Web UI**
   
   - Построить контекст из DOM, доступных ролей и пользовательских сценариев.
   - Подключить генерацию тест-кейсов.
   - Добавить генерацию исполняемого кода Playwright.
   - Проверить трассировку от теста к исходной проверке и автоматическую валидацию.
   
   Критерий завершения: Web UI использует общий движок, но не копирует API-специфичную логику.
5. **Этап 5. Подключить SQL, Mobile UI и Security**
   
   - SQL: схема БД, диалекты, данные и проверки целостности.
   - Mobile UI: экраны, жесты, платформенные возможности и жизненный цикл приложения.
   - Security: генерация сценариев, правила допустимого исполнения и обработка доказательств.
   - После подтверждения общей архитектуры решить, нужны ли независимые пакеты.
   
   Критерий завершения: новые направления подключаются без изменений ядра, кроме обоснованных расширений контрактов.

### Что я бы проверил перед переносом

В архиве есть несколько конкретных технических рисков, которые стоит учесть\:

- `Api/README.md` и `Api/docs/PROJECT_OVERVIEW.md` описывают существующую модель и команды - их необходимо обновлять вместе с изменениями.
- `Api/tools/validate_library.py` и `select_checks.py` обращаются к структуре каталогов напрямую. После переноса необходимо централизовать конфигурацию корня каталога.
- `Api/checks/generated/` содержит кандидатов, которые не должны автоматически становиться утверждёнными проверками.

- Общая схема проверок должна оставаться совместимой с уже накопленной библиотекой; любые изменения лучше проводить с версионированием и миграционными тестами.

## 8\. Какую стратегию упаковки выбрать

На текущем этапе я бы выбрал **монорепозиторий с одним Python-пакетом и внутренними доменными модулями**\.

| Подход | Оценка для текущего проекта |
|--------|--------|
| Один пакет, модульная архитектура | Рекомендую сейчас |
| Несколько пакетов в одном репозитории | Возможный следующий этап |
| Отдельный репозиторий на каждый домен | Преждевременно |
| Отдельные микросервисы генерации | Не нужны без отдельного требования к развёртыванию и масштабированию |

При этом каталог YAML-проверок можно распространять как ресурсный набор отдельно от исполняемого Python-кода, если появится такая потребность.

Смысл не в том, чтобы навсегда объединить всё в один пакет, а в том, чтобы сначала стабилизировать границы модулей. Тогда выделение `test-library-api`, `test-library-ui` или `test-library-security` станет решением об упаковке, а не новой архитектурной перестройкой.
