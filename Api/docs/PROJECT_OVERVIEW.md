# 4. Итоговое описание проекта API Test Library

## Назначение

API Test Library — версионируемая библиотека правил/шаблонов проверок REST и gRPC API, предназначенная для отбора применимых сценариев и последующей генерации тестов. Библиотека хранит проверяемые риски и инварианты; она не является автономным тестовым раннером и не выполняет запросы к API при генерации.

## Состав репозитория

| Путь | Назначение |
|---|---|
| `schema/` | JSON Schema для записей проверок и профилей |
| `taxonomy/` | Контролируемые значения категорий, тегов и приоритетов |
| `checks/common/` | Протокольно-независимые проверки |
| `checks/rest/`, `checks/grpc/` | Проверки REST и gRPC |
| `checks/generated/` | Кандидаты, полученные из реальных контрактов |
| `profiles/` | Smoke, PR, CI, Regression, Nightly, Release и их ограничения |
| `selection-rules/` | Применимость, impact analysis и приоритизация |
| `validation/` | Правила качества библиотеки |
| `examples/` | Демонстрационные и анализируемые OpenAPI/access-model файлы |
| `tools/` | Валидация, подбор проверок, генерация покрытия и обслуживание профилей |
| `build/` | Сгенерированные отчёты и артефакты анализа; пересоздаваемые результаты |
| `docs/` | Каталог, правила, этапы и отчёты |

## Модель метаданных

- **`kind`** — характер проверки: например, `positive`, `negative`, `boundary`.
- **`category`** — предметная область, например `contract`, `validation`, `security`, `resources`.
- **`tags`** — независимые признаки для отбора.
- **`priority`** — приоритет риска P0–P3; P0 означает наиболее высокий приоритет.
- **`profiles` / run tags** — предполагаемые наборы выполнения; фактическая логика отбора описана в профилях и `tools/select_checks.py`.
- **`applies_to`, `include_if`, `exclude_if`** — условия применимости.
- **ожидаемое поведение** — контрактное, основанное на бизнес-правиле, стандартное или требующее уточнения.
- **`test_variants` и шаги** — способ развернуть инвариант в конкретные тестовые варианты.

Не следует смешивать измерения. Например, `negative` не означает `Smoke`, а `P0` не означает автоматически, что проверка безопасна или детерминирована для любого окружения.

## Рабочий процесс

1. Подготовить актуальный OpenAPI-контракт и access model.
2. Проверить полноту контракта: security, схемы, статусы, обязательность полей и правила ошибок.
3. Запустить генерацию candidate checks и отчёта покрытия.
4. Разобрать вопросы/противоречия и уточнить модель доступа с владельцем API.
5. Валидировать всю библиотеку и выбрать проверки нужного профиля.
6. Провести ревью предусловий, тестовых данных, ожидаемых результатов и cleanup.
7. Передать проверенные сценарии тестовому раннеру.
8. Публиковать отчёт: применимые, выбранные, исключённые, требующие уточнения проверки и причины.

## Границы ответственности

- Валидатор проверяет структуру и согласованность данных в пределах реализованных правил.
- Генератор создаёт кандидаты и отчёты на основании входных контрактов/моделей.
- Селектор формирует список по профилю, тегам, приоритету и детерминированности.
- Ни один из этих инструментов сам по себе не доказывает runtime-корректность API.
- Неопределённое поведение должно попасть в очередь уточнений, а не превращаться в выдуманное утверждение теста.

## Известные долги

1. Уточнить 66 вопросов из анализа реальных контрактов.
2. Устранить 20 отсутствующих security-деклараций BFF Admin API либо документально подтвердить публичность соответствующих операций.
3. Разрешить противоречие security для `onStart`.
4. Согласовать семантические отображения таксономий REST Expansion.
5. Добавить автоматические тесты генератора/селектора и контроль регрессий на фиксированных fixtures.
6. Разделить «кандидат с валидной схемой» и «сценарий проверен владельцем и готов к запуску» в отчётности.
