# Оформление багов

Пока баги ведутся файлами в репозитории `test-runs` (`bugs/`); формат подобран так, чтобы потом перенести их
в трекер без переписывания. Шаблон - [`templates/bug.md`](templates/bug.md).

## Когда заводить

- Падение проверки, причина которого - дефект продукта или документа (см. «Разбор» в
  [`running-tests.md`](running-tests.md)). Лучше завести баг о потенциальной проблеме, чем промолчать (ADR 0002).
- Ожидание не из контракта (⚠ в описании теста) - баг тоже заводится; в нём указывается источник ожидания,
  решение (чинить код или документ) принимает команда.
- Не заводить: стенд старой версии, проблемы окружения, ошибки теста, каскадные падения.

## Правила

1. **Один баг - одна проблема.** Одно и то же поведение в нескольких тестах/ручках - один баг со списком
   затронутых тестов. Разные проблемы в одном тесте - разные баги.
2. **Сначала поиск дубля** в `test-runs/bugs/README.md`: есть открытый - дополнить его (новый прогон, тест),
   а не заводить новый.
3. **Заголовок**: `<Где>: <что не так>` - коротко, без «не работает». Пример: `POST /api/auth/login: 401 без заголовка WWW-Authenticate`.
4. **Ожидание всегда с источником**: пункт контракта (`components.responses.Unauthorized`), требование
   (ОТЗ/ЧТЗ/ФТТ с ID), стандарт (RFC, OWASP), практика. Для ⚠-ожиданий прямо написать, что контракт молчит.
5. **Воспроизведение** - минимальный HTTP-запрос (метод, путь, значимые заголовки, тело) + ответ стенда,
   с **реальными** учётными данными (см. «Креды» ниже) - разработчик воспроизводит без вопросов к автору.
6. **Доказательство** - ссылка на прогон (`runs/.../report.md`) и путь теста в коллекции.
7. **Окружение** - стенд, дата, версия (если стенд её отдаёт); если стенд старше контракта - пометить
   «перепроверить на актуальной версии».
8. Текст - на русском, фактами; без предположений о причине в коде, если она не доказана.

## Классификация

| Поле | Значения |
|---|---|
| Тип | `implementation` - код; `contract` - контракт OpenAPI; `requirements` - ФТТ/ОТЗ/ЧТЗ/ПМИ; `security` - уязвимость (дополнительно к основному типу) |
| Серьёзность | `critical` - блокирует работу или уязвимость с эксплуатацией; `major` - нарушена функция/безопасность, есть обход; `minor` - отклонение от контракта/стандарта без потери функции; `trivial` - косметика |
| Приоритет | Ставит команда при разборе; при заведении - пусто |
| Статус | `new` -> `confirmed` / `rejected` (с причиной) -> `fixed` -> `verified` (прогон, где тест прошёл) / `reopened` |

## Креды

Креды тестовых стендов считаются общедоступными: на dev / test / sandbox / stage логин и пароль пишутся в баг
открыто (поле «Учётка» и воспроизведение). Причина - разработчик должен воспроизвести баг без вопросов к автору.

Исключения - **спросить пользователя, что делать с кредами**, до записи в баг:
- стенд production или есть подозрение, что это production (нет признаков dev/test/stage в адресе, реальные данные
  клиентов, `isProduction=true`);
- при запуске явно сказано скрывать пароли;
- есть сомнения.

## Хранение

- Файл: `test-runs/bugs/BUG-NNNN-<краткое-имя-латиницей>.md`, номер - следующий свободный по реестру.
- Реестр: `test-runs/bugs/README.md` - строка на баг (номер, заголовок, модуль, серьёзность, статус, первый прогон).
- В `report.md` прогона, раздел «Разбор и баги», - ссылки на баги; в баге - ссылки на прогоны.
- После перехода в трекер в баге остаётся ссылка на задачу трекера.
