# Оформление багов

Баги ведутся файлами в репозитории результатов проекта (`bugs/`, для BFF - gitlab.viiitech.ru/test/autotest/bff) по базовому шаблону [`templates/bug.md`](templates/bug.md);
для переноса в трекер - шаблоны под конкретный трекер в [`templates/trackers/`](templates/trackers/README.md)
(сейчас YouTrack). Тип и адрес трекера, префикс темы бага (по умолчанию `[AT]`) и метки (по умолчанию `Autotest`)
выбирает тот, кто запускает прогон; в трекере тема = префикс + заголовок бага.

## Когда заводить

- Падение проверки, причина которого - дефект продукта или документа (см. «Разбор» в
  [`running-tests.md`](running-tests.md)). Лучше завести баг о потенциальной проблеме, чем промолчать (ADR 0002).
- Ожидание не из контракта (⚠ в описании теста) - баг тоже заводится; в нём указывается источник ожидания,
  решение (чинить код или документ) принимает команда.
- Не заводить: стенд старой версии, проблемы окружения, ошибки теста, каскадные падения.

## Правила

1. **Один баг - одна проблема.** Типовая проблема, которая воспроизводится во многих вызовах (формат ошибок,
   заголовки безопасности, коды на всех ручках), - **один** баг с таблицей всех тестов, где она воспроизводится
   (тест, операция, прогон). Разные проблемы в одном тесте - разные баги.
2. **Сначала поиск дубля** (`python autotest.py dupes` - кандидаты по тесту, операции, записям и заголовку) в `bugs/README.md` репозитория результатов (с учётом модуля: тот же симптом в другом модуле или проекте - не дубль автоматически, а «похожий»): есть открытый - дополнить его (новый прогон, тест),
   а не заводить новый.
3. **Заголовок** - где, что не так и **суть проблемы** (чем плохо или что нарушено), чтобы по одному заголовку
   было понятно, о чём баг: `<Где>: <что не так> - <суть>`. Без «не работает» и без номера BUG-<PRJ>-NNNN.
   Пример: `POST /api/auth/login: 401 без заголовка WWW-Authenticate - клиент не узнаёт схему аутентификации (контракт, RFC 9110)`.
4. **Обоснование ожидаемого поведения** - списком, каждый пункт с **реальной ссылкой**:
   - ТЗ (ФТТ, ОТЗ, ЧТЗ, ПМИ): название, версия, раздел и ID требования, ссылка на документ (из
     `postman/docs/sources/sources.yaml`: `drive_folder` + имя файла; ссылка на файл - если известна);
   - контракт: название и версия, ссылка на опубликованную страницу с якорем операции/схемы
     (`https://pages.viiitech.ru/common/contracts/<проект>/#tag/<тег>/<METHOD><путь>`, `#model/<Схема>`) и путь в
     `api.yaml` (`components.responses.Unauthorized`);
   - RFC: номер и пункт со ссылкой на пункт (`https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5.16`);
   - прочее, если применимо: OWASP (Cheat Sheet с якорем, ASVS с номером требования), MDN, практика отрасли.
   Для ⚠-ожиданий прямо написать, что контракт молчит. Ссылки проверять перед записью: страница открывается, якорь
   существует (`id="<якорь>"` в HTML); якоря страницы контракта (Scalar, собирается в браузере) - проверять в браузере.
5. **Воспроизведение** - команда **curl** (копируется и запускается как есть: метод, полный URL, значимые
   заголовки, тело, `-i` для вывода заголовков ответа) с **реальными** учётными данными (см. «Креды» ниже), затем
   ответ стенда: строка статуса, значимые заголовки и тело. **JSON ответа - отформатированный** (отступ 2 пробела),
   не одной строкой. Для запроса с сессией - сначала curl входа (`-c cookies.txt`), затем запрос (`-b cookies.txt`).
6. **Доказательство** - ссылка на прогон (`runs/.../report.md`) и путь теста в коллекции.
7. **Окружение** - стенд, дата, версия (если стенд её отдаёт); если стенд старше контракта - пометить
   «перепроверить на актуальной версии».
8. Текст - на русском, фактами; без предположений о причине в коде, если она не доказана.

## Баги с ограничением AI (ADR 0008)

Баг по тесту `[DRAFT]` / «⚠ AI-ОГРАНИЧЕНИЕ» или по записи с `automation.ai_generation.restricted`:

- в шапке - строка `| AI-доступ | restricted |`; заголовок - нейтральный, по правилу п. 3 (где, что не так, суть), без
  сценария;
- публичные разделы (их видят ассистент и скрипты): шапка, «Где воспроизводится» (тест, операция, прогон),
  «Примечания»; остальное ассистент не читает (`autotest.py view` их скрывает);
- подробности (фактическое поведение, воспроизведение, разбор) пишет **человек** - в `bugs/restricted/BUG-<PRJ>-NNNN.md`
  или в баге внутри блока `<!-- ai-restricted:begin -->` … `<!-- ai-restricted:end -->`;
- поиск дубля - `python autotest.py dupes <BUG> [--tracker]` (локально, без LLM): `дубль` - дополнить существующий,
  `сомнение` - завести новый со строкой «Возможный дубль: BUG-…» в «Примечаниях» и попросить человека сравнить,
  `новый` - завести. Лучше лишний дубль, чем потерянный баг;
- в трекер уходят только публичные разделы и тег `ai-restricted` (`file-bugs` ставит сам); описание таких задач
  ассистент не читает (`yt.py show` скрывает, `--human` - для человека).

## Группа безопасности (ADR 0011)

Баг по тесту с меткой группы `sg-...` (метаданные теста) - строка шапки `| Группа | sg-... |`; тест нескольких групп -
через запятую. Оформляет и ищет дубли сессия этой группы (`security-groups.md`): свои баги -
`autotest.py view bugs --group <G>`, дубли - `autotest.py dupes <BUG> --group <G>` (тема бага чужой группы не
печатается - сравнивает человек). `file-bugs` ставит задаче тег группы - по нему `yt.py search --group` выбирает
задачи группы, `--skip-group` - отсеивает опасные для текущей выборки.

## Классификация

| Поле | Значения |
|---|---|
| Тип | `implementation` - код; `contract` - контракт OpenAPI; `requirements` - ФТТ/ОТЗ/ЧТЗ/ПМИ; `security` - уязвимость (дополнительно к основному типу) |
| Серьёзность | `critical` - блокирует работу или уязвимость с эксплуатацией; `major` - нарушена функция/безопасность, есть обход; `minor` - отклонение от контракта/стандарта без потери функции; `trivial` - косметика |
| Приоритет | Ставит команда при разборе; при заведении - пусто |
| Статус | `new` -> `confirmed` / `rejected` (с причиной) -> `fixed` -> `verified` (прогон, где тест прошёл) / `reopened` |

**Стенд повышает серьёзность** (решение bj, 2026-10-15). Часть проблем терпима на тестовых стендах, но в проде
их быть не должно:
- работает метод, который по контракту не реализован, удалён или устарел;
- отвечают эндпоинты вне контракта: отладочные, служебные, старые версии путей;
- в системе есть тестовые данные или тестовые учётки;
- ошибки содержат подробности: стектрейсы, версии.

Для таких багов:
- на dev / test / sandbox серьёзность ставится по шкале выше, обычно `minor`;
- на stage / prod — не ниже `major`;
- `critical` — если через это есть доступ к данным или действиям в обход прав.

В баге указываются обе оценки: `minor (на stage/prod — major)`. Так команда видит риск до выкатки. Источник
ожидания — OWASP API9:2023 Improper Inventory Management.

## Блокировка учёток

Если у стенда есть реальный лимит неудачных входов, а пути разблокировки нет (`postman/docs/project/stands.md`),
в баге, воспроизведение которого включает вход (особенно с неверным паролем), - явное предупреждение в начале
описания, чтобы проверяющий руками случайно не заблокировал учётку:

> ⚠ На стенде <адрес> учётка блокируется после <N> неудачных входов, пути разблокировки нет. Не повторяйте
> неверный вход больше <безопасный лимит> раз подряд; после неудачных попыток выполните успешный вход.

Лимит ещё не известен - так и написать («лимит не известен, не больше 5 неудачных входов подряд»).

## Креды

Креды тестовых стендов считаются общедоступными: на dev / test / sandbox / stage логин и пароль пишутся в баг
открыто (поле «Учётка» и воспроизведение). Причина - разработчик должен воспроизвести баг без вопросов к автору.

Исключения - **спросить пользователя, что делать с кредами**, до записи в баг:
- стенд production или есть подозрение, что это production (нет признаков dev/test/stage в адресе, реальные данные
  клиентов, `isProduction=true`);
- при запуске явно сказано скрывать пароли;
- есть сомнения.

## Заведение в трекер

Баги сначала оформляются в `bugs/` репозитория результатов; в трекер - **только после решения**, чтобы проблемная сборка не засорила
трекер пачкой багов. Инструмент - `python autotest.py file-bugs`; берёт баги со статусом `new` без ссылки на трекер.

| Режим | Когда | Что происходит |
|---|---|---|
| `ask` (по умолчанию) | Интерактивный запуск | Спросить пользователя: завести сразу или сначала разобраться по отчёту. Claude спрашивает сам (у него нет терминала) |
| `auto` | Пайплайн, флаг `--mode auto` / `bugs_to_tracker: auto` | Завести сразу через API трекера (токен - env `TRACKER_TOKEN`); ссылка на задачу - в баг и в отчёт |
| `links` | Пайплайн без автозаведения или ответ «разберёмся по отчёту» | Не заводить; в баг (поле «Трекер») и в отчёт (колонка «Трекер») - ссылка «Завести в трекере»: открывает форму новой задачи с темой, описанием и командой полей - завести по клику после разбора |

Режим задаётся в `.local/tracker.yaml` (`bugs_to_tracker`) или ключом (`autotest.py run --bugs-to-tracker`, `autotest.py file-bugs --mode`)
и записывается в отчёт прогона. Ссылка «Завести» ограничена длиной URL: длинное описание сокращается, полное - в баг-файле.

## Хранение

- Файл: `bugs/BUG-<PRJ>-NNNN-<краткое-имя-латиницей>.md`, номер - следующий свободный по реестру.
  `<PRJ>` - код проекта (`BFF`, `VPN13`), нумерация сквозная по проекту, модуль - поле бага. Код нужен, чтобы номер
  был однозначен между проектами; до 2026-10-19 номера были без кода (`BUG-0001` = `BUG-<PRJ>-0001`).
- Реестр: `bugs/README.md` - строка на баг (номер, заголовок, модуль, серьёзность, статус, первый прогон).
- В `report.md` прогона, раздел «Разбор и баги», - ссылки на баги; в баге - ссылки на прогоны.
- После заведения в трекер в баге (поле «Трекер») и в отчёте (колонка «Трекер») - ссылка на задачу; до заведения -
  ссылка «Завести в трекере» (режим `links`).
