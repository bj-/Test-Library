# Test-Library — API Test Library

Версионируемая библиотека шаблонов проверок для генерации API-тестов REST и gRPC (код и данные — в `Api/`); с ADR
[0006](docs/decisions/0006-ui-and-db-checks.md) — также проверки UI (web, desktop, mobile) и БД (`checks/ui/`, `checks/db/`).
Принципы, структура и формат записей — в `Api/README.md`.

## Где что лежит

- `Api/docs/` — документация самой библиотеки (обзор, план реализации, отчёты по этапам, каталог).
  Не путать с корневым `docs/` — там состояние работы и решения.
- `Api/build/` — сгенерированные отчёты покрытия.
- План реализации — `Api/docs/IMPLEMENTATION_PLAN.md`, отчёты по этапам — `Api/docs/STAGE_REPORTS.md`.

## Правила тестирования

Решение — `docs/decisions/0002-expected-behavior-sources.md`. Коротко:

- Цель — полноценное тестирование, а не проверка соответствия контракту. Не доверяем ни заказчику, ни аналитику,
  ни разработчику: контракт — лишь мнение разработчика.
- Проверки соответствия контракту обязательны, но это лишь часть набора тестов.
- Ожидание — из всех источников: ФТТ, ОТЗ, ЧТЗ, ПМИ, контракт, стандарты (RFC, OWASP), практика, здравый смысл;
  в проверке указывать источник.
- Источник молчит — проверка всё равно нужна; источники противоречат — это находка.
- Лучше завести баг о потенциальной проблеме, чем промолчать. Ожидание под фактическое поведение не подгонять.
- Библиотека содержит и проверки на ошибки передачи требований (категория `requirements`).

## Входящие идеи тестов

`Api/ideas/inbox.md` — сюда **сразу** записывается любая новая идея проверки, возникшая в любом проекте (прогон,
разбор бага, чтение контракта/ТЗ), без проверки на дубли и актуальность. Сюда же — идеи UI-тестов (web, desktop, mobile; пометка `UI`) и тестов БД/SQL
(пометка `DB`): библиотека будет расширяться на генерацию UI-тестов. Разбор inbox (в `checks/` или отказ
с причиной) — отдельной задачей. Цель — библиотека с большим количеством качественных идей.

## Запуск тестов и баги

`Process/` — общие правила процесса (ADR 0003): создание коллекции — `Process/collections.md`, запуск тестов и разбор результатов — `Process/running-tests.md`,
оформление багов — `Process/bugs.md`, шаблон — `Process/templates/bug.md`. На новой машине начинать с
«Короткого пути» в `running-tests.md`.

## Связанные репозитории

- `C:\Git\Autotest` — движок `test-engine` и проекты тестов (`projects\<КОД>\tests`, `results` — прогоны и баги).
- `postman` — коллекции, построенные по библиотеке; реальные контракты — `Api/examples/real-contracts/`.

## Общий контекст проекта

Над проектом работают несколько человек с разных машин. Локальная история и память
Claude Code между машинами **не переносятся**, поэтому всё состояние работы хранится в репозитории:

| Файл | Назначение |
|---|---|
| `docs/STATUS.md` | Текущее состояние: в работе, следующие шаги, блокеры, журнал |
| `docs/ideas.md` | Бэклог идей, ещё не взятых в работу |
| `docs/decisions/` | Принятые решения (ADR), по одному файлу на решение |

## Правила работы для Claude

- **В начале сессии** прочитать `docs/STATUS.md` (и при необходимости `docs/ideas.md`).
- **В конце значимого шага** обновить `docs/STATUS.md`: что сделано, что дальше, добавить строку в журнал
  (дата, кто/машина, кратко).
- **Принято архитектурное или процессное решение** → новый файл `docs/decisions/NNNN-краткое-название.md`
  по шаблону `docs/decisions/0000-template.md`, ссылка на него в `STATUS.md`.
- **Появилась идея, не относящаяся к текущей задаче** → добавить в `docs/ideas.md`, а не реализовывать сразу.
- Состояние проекта не сохранять в локальную память Claude — только в эти файлы.
- Изменения в `docs/` коммитить вместе с кодом, к которому они относятся.
