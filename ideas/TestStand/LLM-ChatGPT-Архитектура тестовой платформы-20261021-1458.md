Главная мысль: сейчас не нужно покупать отдельный сервер или выбирать окончательную инфраструктуру. Можно начать на имеющихся i3/i5, собрать рабочий MVP в Docker, а затем перенести его на новый стенд без переписывания генератора тестов, обработчика результатов и отчётов.

При этом важно сразу разделить три вещи\:

- **Управление** - запуск прогонов, справочники, история, баги, навигация.
- **Исполнение** - Newman сейчас, затем браузеры, мобильные устройства и нагрузочные инструменты.
- **Хранение** - отчёты, исходные данные прогонов, баги, тестовые библиотеки и артефакты.

## 1\. Какую архитектуру я предлагаю

**Пользователь / генератор тестов / CI**

Запросы на запуск, просмотр результатов, работа со справочниками

Запуски · история · поиск · справочники · баги

Это логическая схема, а не требование запускать каждый блок в отдельном контейнере. На первом этапе несколько блоков вполне могут жить в одном приложении.

**Ключевой принцип\:** генератор, исполнители и интерфейс не должны напрямую зависеть от конкретного диска, IP-адреса компьютера или локального пути к файлу. У каждого компонента должен быть определённый интерфейс взаимодействия.

Docker Compose хорошо подходит для такого старта: он позволяет описать зависимости сервисов и использовать конфигурацию в разработке, тестировании и развёртывании на одном сервере. \[[Why use Compose?](https://docs.docker.com/compose/intro/features-uses/?utm_source=chatgpt.com); [Use Compose in production](https://docs.docker.com/compose/how-tos/production/?utm_source=chatgpt.com)\]

**Что можно отложить\:** Kubernetes, отдельный кластер БД, сложную авторизацию через корпоративный SSO, отдельные микросервисы для каждого типа тестирования и тяжёлую систему мониторинга.

Оговорка: если текущий генератор написан на другом языке или уже имеет свой backend, не нужно переписывать его только ради выбранного стека. Платформа должна интегрироваться с существующим кодом через API или CLI.

## 3\. Как организовать запуск тестов

Самое важное архитектурное решение - **каждый прогон должен быть отдельной задачей, выполняемой изолированным исполнителем**\.

**1\. Создание запуска**

API принимает параметры: тестовая библиотека, версия тестов, целевое окружение, параметры запуска и инициатор.

---

**2\. Постановка в очередь**

Создаётся запись прогона со статусом `queued`\. Очередь распределяет работу между доступными исполнителями.

---

**3\. Исполнение**

Worker поднимает контейнер с нужной версией инструментов, запускает Newman и сохраняет код возврата, логи и исходный отчёт.

---

**4\. Обработка результатов**

Отдельный обработчик разбирает отчёт, связывает ошибки с тестами и известными багами, сохраняет нормализованные результаты.

---

**5\. Просмотр**

Пользователь открывает прогон, видит общую статистику, упавшие проверки, связанные баги и исходные артефакты.

### Почему не запускать Newman прямо из API

Потому что со временем появятся задачи, которые могут работать долго, зависать или потреблять много ресурсов. Если исполнитель отделён от API, можно\:

- запускать несколько прогонов параллельно;
- ограничивать количество одновременных задач;
- перезапускать упавшие исполнители;
- отправлять нагрузочные тесты на отдельную машину;
- добавлять браузерные и мобильные исполнители без перестройки основного приложения.

Для браузерной автоматизации можно будет добавить отдельные образы с Playwright или Selenium. Для мобильной - специализированные Android-эмуляторы и исполнители, которым может потребоваться доступ к устройствам. Для gRPC - отдельный профиль исполнителя с подходящими инструментами.

При этом не стоит автоматически повторять любой упавший тест: повторный запуск может изменить данные на целевом стенде или повторить нежелательную операцию. Политика повторов должна зависеть от типа задачи.

## 4\. Хранение отчётов: отделить данные от файлов

Рекомендую использовать два уровня хранения.

**PostgreSQL** - то, по чему нужно искать и фильтровать\:

- идентификатор прогона;
- дата, инициатор, окружение;
- тестовая библиотека и её версия;
- статус, длительность, количество успешных и упавших проверок;
- результаты отдельных тестов;
- ссылки на баги;
- ссылки на файлы отчёта.

**Объектное хранилище** - то, что не нужно целиком загружать в базу\:

- оригинальный JSON-отчёт Newman;
- HTML-отчёт;
- логи и диагностические данные;
- скриншоты и видео будущих UI-тестов;
- сырые результаты нагрузочных прогонов.

На первом этапе допустим файловый backend, но я бы сразу определил интерфейс вроде `ArtifactStorage.put()`, `get()`, `delete()` и `getUrl()`\. Тогда backend можно заменить на S3-совместимое хранилище, не меняя бизнес-логику приложения.

Если хочется получить S3 API уже локально, можно рассмотреть MinIO, предварительно проверив актуальные условия лицензирования и сопровождения. S3-совместимый интерфейс также доступен у облачных объектных хранилищ. \[[AWS S3 Compatible Object Storage](https://min.io/product/s3-compatibility?utm_source=chatgpt.com); [MinIO Object Storage for Linux](https://min.io/docs/minio/linux/index.html?utm_source=chatgpt.com)\]

### Как должна выглядеть навигация

**Главная страница**

Последние прогоны, процент успешных запусков, ошибки, активные задачи.

---

**История прогонов**

Фильтры по продукту, окружению, тестовой библиотеке, версии, статусу, дате и инициатору.

---

**Карточка прогона**

Сводка → список тестов → детали ошибки → известные баги → оригинальные отчёты.

---

**Каталог багов**

Поиск, история обнаружений, связь с внешним трекером, продукты и тесты.

---

**Справочники**

Библиотеки тестов, продукты, версии, известные баги, окружения и конфигурации.

Отчёт не должен существовать только как HTML-файл. HTML удобен человеку, но для поиска, аналитики и программной обработки нужна нормализованная модель результатов в БД.

## 5\. Справочники: сделать их частью API платформы

У вас есть важная особенность: справочниками пользуется не только человек, но и JS-скрипт во время обработки отчёта. Поэтому я бы не делал их просто папкой с JSON-файлами, доступных через локальный путь.

Лучше предоставить единый API, например\:

```http
GET /api/v1/test-libraries/{id}
GET /api/v1/products/{id}
GET /api/v1/known-bugs/{id}
GET /api/v1/known-bugs?productId=product-123
```

Примеры идентификаторов условные.

### Предлагаемая модель данных

| Сущность | Что хранить |
|--------|--------|
| Product | Продукт, версия, описание, ссылки |
| TestLibrary | Название, репозиторий, версия, назначение |
| TestCase | Стабильный ID теста, описание, теги |
| KnownBug | ID, продукт, описание, статус, внешний ID задачи |
| TestRun | Прогон, параметры, версия библиотеки, итоговый статус |
| TestResult | Результат отдельного теста, ошибка, длительность |
| TestRunBug | Связь обнаружения с багом и конкретным прогоном |
| Environment | Идентификатор тестового окружения и его конфигурация |

Для известных багов нужно различать как минимум\:

- **Карточку бага** - известная проблема продукта.
- **Обнаружение бага** - конкретный случай, когда тест выявил её в определённом прогоне.

Один баг может обнаруживаться сотнями прогонов, а один прогон - выявлять несколько багов. Эти связи нужно моделировать явно.

### Как сделать справочники удобными

- Человек редактирует их через веб-интерфейс.
- JS-скрипт обращается к API и получает JSON.
- Сущности имеют стабильные ID, не зависящие от названия.
- Изменения справочников версионируются или журналируются.
- В отчёте сохраняются ID и версия данных, использованных при анализе.

Последний пункт важен для воспроизводимости. Если завтра баг закроют или описание теста изменится, старый прогон не должен задним числом терять смысл.

Для небольших, редко изменяемых справочников можно использовать Git как источник первоначальных данных. Но если справочниками управляют пользователи, появляются связи, фильтрация и аудит, PostgreSQL с API будет удобнее. Не нужно поддерживать две независимые системы редактирования одних и тех же данных.

## 6\. Баги: локальная копия плюс внешний трекер

Я бы не пытался заменять ваш таск-трекер. В платформе нужна собственная база известных проблем, заточенная под поиск при анализе тестовых результатов.

Примерный сценарий\:

1. Тест упал.
2. Обработчик извлёк ошибку, тест, продукт и версию.
3. Система проверила известные баги по стабильному ID, сигнатуре ошибки и другим признакам.
4. Найденные совпадения показаны пользователю как возможные связи, а не как безусловно доказанное совпадение.
5. Если проблема новая, пользователь создаёт локальную карточку бага.
6. При необходимости карточка публикуется во внешний трекер.
7. В локальной записи сохраняются ID задачи и статус синхронизации.

Не рекомендую считать текст ошибки уникальным идентификатором бага: сообщения могут содержать динамические ID, даты, токены и другие изменяющиеся значения.

Также предусмотрите состояние «синхронизация не удалась». Если внешний трекер временно недоступен, локальная карточка и результаты прогона не должны теряться.

## 7\. Нагрузочное тестирование лучше заложить сейчас

Для нагрузочных тестов я бы начал с **k6**, если нет обязательных требований к другому инструменту. Он подходит для автоматизированных сценариев, запуска из CI и получения результатов для последующего анализа.

Но нагрузочные прогоны нужно выделить в отдельный класс задач.

| Обычный API-прогон | Нагрузочный прогон |
|--------|--------|
| Обычно ограничен по длительности | Может выполняться долго |
| Ресурсов обычно требуется немного | Может использовать почти все ресурсы исполнителя |
| Основное - pass/fail и ошибки | Важны latency, throughput, ошибки и нагрузка на систему |
| Допустимо несколько задач на одной машине | Нужны ограничения и выделенные ресурсы |
| Отчёт содержит результаты проверок | Отчёт содержит временные ряды и большие объёмы метрик |

Для нагрузочных тестов предусмотрите\:

- отдельную очередь `performance`;
- отдельные worker-ы или машины;
- лимиты CPU, памяти и числа параллельных запусков;
- хранение сырых результатов и параметров нагрузки;
- сравнение с предыдущими прогонами;
- сохранение версии сценария, версии приложения и конфигурации нагрузки.

На старте необязательно разворачивать целую платформу мониторинга. Можно сохранять результаты k6 в артефакты и строить первые сравнения на основе извлечённых метрик. Когда появится потребность в постоянных временных рядах и корреляции с метриками тестового стенда, можно добавить Prometheus и Grafana.

**Важное предупреждение\:** не запускайте нагрузочные тесты на том же компьютере, где выполняется тестируемый продукт, если хотите оценивать именно производительность продукта. Иначе измерения будут зависеть от конкуренции за ресурсы.

## 8\. Как использовать имеющиеся компьютеры

С i3/i5 и 16 ГБ памяти вполне можно начать. На первом этапе важнее понять объём отчётов, частоту запусков и параллельность, чем выбирать сервер по максимальным характеристикам.

Я бы распределил роли примерно так\:

**Компьютер № 1 - управляющий узел**

(Основной)

Docker Compose, API, веб-интерфейс, PostgreSQL, очередь задач, reverse proxy. При небольшом объёме работы можно здесь же запускать несколько Newman-задач.

---

**Компьютер № 2 - исполнитель**

Newman, затем браузерные тесты и нагрузочные прогоны. Подключается к управляющему узлу через API/очередь и отправляет результаты в централизованное хранилище.

---

**Дополнительный диск или компьютер - резервирование**

Резервные копии PostgreSQL, отчётов и конфигураций. Не считать дополнительный диск в том же компьютере полноценной резервной копией.

Если компьютер только один, сначала размещайте всё на нём. Второй узел понадобится, когда возникнет реальная потребность в параллельном исполнении или изоляции нагрузки.

По возможности используйте SSD для ОС, PostgreSQL и рабочих каталогов, а большие HDD - для архивных артефактов и резервных копий. При выборе ОС я бы предпочёл Linux без графической оболочки для серверных ролей.

При этом нужно понимать ограничение: один компьютер с Compose - не отказоустойчивый кластер. Если он выключится, перестанут работать и API, и база, и очередь. Это нормально для начального MVP при условии резервного копирования и понятной процедуры восстановления.

## 9\. Как подготовить беспроблемный переезд

Docker сам по себе не гарантирует переносимость. Её нужно обеспечить на уровне конфигурации, данных и контрактов.

Я бы зафиксировал следующие правила с первого дня.

1. **Все настройки - вне образов.** Адрес API тестового стенда, URL базы, настройки очереди, секреты и лимиты задаются через конфигурацию окружения.
2. **Не использовать локальные пути как API.** Генератор и обработчик обращаются к отчётам через сервис хранения, а не напрямую читают `/home/user/reports`\.
3. **Каждый прогон неизменяемо идентифицируется.** Сохраняются версия тестов, версия исполнителя, параметры и сведения об окружении.
4. **Схемы БД изменяются миграциями.** Не полагаться на ручное изменение таблиц и автоматическое создание схемы при старте.
5. **Отчёт имеет версию схемы.** Старые результаты должны продолжать разбираться после обновления обработчика.
6. **Исполнители не хранят единственную копию данных.** Контейнеры временные; логи и результаты отправляются в центральное хранилище.
7. **Резервные копии регулярно проверяются восстановлением.** PostgreSQL поддерживает несколько стратегий резервного копирования и восстановления, от SQL-дампов до архивирования WAL для восстановления на определённый момент времени. \[[PostgreSQL: Documentation: 18: Chapter 25. Backup and Restore](https://www.postgresql.org/docs/18/backup.html?utm_source=chatgpt.com)\]

Полезно также иметь три отдельных конфигурационных профиля: `local`, `staging` и `production`\. При переезде меняются адреса сервисов, секреты и параметры ресурсов, но не логика приложения. Подход с отдельными production-настройками поддерживается и в рекомендуемых практиках Docker Compose. \[[Use Compose in production](https://docs.docker.com/compose/how-tos/production/?utm_source=chatgpt.com)\]

Предлагаемый стек с учётом Python\:

| Компонент | Решение |
|--------|--------|
| ОС | Ubuntu Server LTS |
| Контейнеры | Docker Engine + Docker Compose |
| API | FastAPI |
| БД | PostgreSQL |
| Очередь | Redis + RQ |
| Исполнитель | Python worker + Newman в контейнере |
| Файловые артефакты | Локальный каталог с отдельным томом |

- **Newman** запускается отдельным процессом или контейнером, а не внутри HTTP-запроса.
- **Локальное хранилище** уменьшает количество компонентов на старте. Позже его можно заменить объектным хранилищем через отдельный интерфейс.

На первом этапе я бы не вводил отдельный MinIO, если объём отчётов небольшой и достаточно надёжного диска. Но интерфейс хранения стоит спроектировать сразу.

## 3\. Структура Docker Compose

Ниже - базовый каркас, который можно положить в репозиторий. Это стартовый шаблон: для реального запуска потребуются приложение, Dockerfile, health-check-и и конфигурация reverse proxy.

Я намеренно оставляю PostgreSQL и Redis во внутренней сети Compose, без публикации их портов на LAN.

```yaml

services:
  api:
    build: .
    command: uvicorn src.main:app --host 0.0.0.0 --port 8000
    env_file: .env
    depends_on:
      db:
        condition: service_healthy
      redis:
        condition: service_healthy
    volumes:
      - artifacts:/data/artifacts
    networks:
      - backend
    restart: unless-stopped

  worker:
    build: .
    command: rq worker --url redis://redis:6379/0 default
    env_file: .env
    depends_on:
      db:
        condition: service_healthy
      redis:
        condition: service_healthy
    volumes:
      - artifacts:/data/artifacts
    networks:
      - backend
    restart: unless-stopped
    init: true

  db:
    image: postgres:17
    environment:
      POSTGRES_DB: testplatform
      POSTGRES_USER: testplatform
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
    volumes:
      - postgres_data:/var/lib/postgresql/data
    networks:
      - backend
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U testplatform -d testplatform"]
      interval: 10s
      timeout: 5s
      retries: 5
    restart: unless-stopped

  redis:
    image: redis:7
    command: ["redis-server", "--appendonly", "yes"]
    volumes:
      - redis_data:/data
    networks:
      - backend
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 10s
      timeout: 3s
      retries: 5
    restart: unless-stopped

  proxy:
    image: caddy:2
    ports:
      - "${LAN_BIND_IP}:80:80"
    volumes:
      - ./deploy/Caddyfile:/etc/caddy/Caddyfile:ro
    depends_on:
      - api
    networks:
      - frontend
      - backend
    restart: unless-stopped

volumes:
  postgres_data:
  redis_data:
  artifacts:

networks:
  frontend:
  backend:
    internal: true
```

Для первого запуска нужно учесть несколько деталей.

1. Создайте `.env` из `.env.example`, задайте длинный случайный пароль и исключите `.env` из Git.
2. Задайте `LAN_BIND_IP` реальным IP управляющего компьютера в локальной сети. Не используйте `0.0.0.0`, если доступ нужен только через конкретный LAN-интерфейс.
3. В `deploy/Caddyfile` настройте проксирование на `api:8000`\. Для LAN можно начать с HTTP только в изолированной доверенной сети; если передаются секреты или доступна удалённая сеть, настройте HTTPS и аутентификацию.
4. В образе приложения должны быть установлены Python-зависимости и RQ. Запуск миграций нужно организовать отдельной командой перед обновлением приложения.
5. Версии образов PostgreSQL, Redis, Caddy и базового Python-образа необходимо фиксировать и обновлять контролируемо. Пример с PostgreSQL 17 - исходная версия для MVP, а не требование использовать именно её.
6. Для production добавьте ограничения ресурсов, логи, health-check API и проверку доступности хранилища. Разделение конфигураций через дополнительные Compose-файлы поддерживается официальной документацией Docker. \[[Use Compose in production](https://docs.docker.com/compose/how-tos/production/?utm_source=chatgpt.com); [FastAPI in Containers - Docker](https://fastapi.tiangolo.com/deployment/docker/?utm_source=chatgpt.com)\]

### Важное уточнение по исполнителю Newman

В приведённом Compose `worker` пока только запускает очередь RQ. Он ещё не запускает Newman автоматически.

Для этого нужно реализовать обработчик задания, который\:

- получает ID прогона из PostgreSQL;
- проверяет параметры и доступность тестовой коллекции;
- запускает Newman с фиксированными параметрами;
- собирает код возврата, stdout/stderr и исходный JSON-отчёт;
- сохраняет результаты и обновляет статус прогона.

В дальнейшем я бы разделил Python worker и runner с Node.js/Newman на отдельные контейнеры. Для первого MVP допустим единый образ с Python и Node.js, если вы доверяете исполняемым тестам. Не монтируйте в него Docker socket управляющего сервера: это даёт тестовому коду чрезмерные возможности.

Если коллекции тестов недоверенные, исполняйте каждый прогон в отдельном изолированном контейнере с ограничениями сети, CPU, памяти, времени и доступных секретов. При подключении удалённого исполнителя он должен отправлять артефакты в центральное хранилище по API, а не рассчитывать на общий Docker volume.

## 4\. Модель базы данных

Я бы начал с реляционной модели PostgreSQL, не пытаясь заранее построить универсальную систему для всех типов автоматизации.

Основные сущности\:

**products**

Каталог продуктов и систем

**test\_libraries → test\_cases**

Библиотеки и стабильные идентификаторы тестов

**test\_runs**

Версия тестов, окружение, исполнитель, статус и параметры

**test\_results**

Отдельные результаты проверок

**known\_bugs**

Каталог известных проблем

**run\_bugs**

Обнаружения и связи с прогонами

**artifacts**

Ссылки на файлы отчётов и диагностические данные

### Поля основных таблиц

| Таблица | Основные поля |
|--------|--------|
| `products` | `id`, `key`, `name`, `description`, `created_at` |
| `test_libraries` | `id`, `key`, `name`, `repository_url`, `created_at` |
| `test_library_versions` | `id`, `library_id`, `version`, `commit_sha`, `created_at` |
| `test_cases` | `id`, `library_id`, `external_key`, `name`, `metadata_json` |
| `environments` | `id`, `key`, `name`, `base_url`, `config_json` |
| `test_runs` | `id`, `status`, `run_type`, `library_version_id`, `environment_id`, `parameters_json`, `started_at`, `finished_at`, `initiator`, `worker_id` |
| `test_results` | `id`, `run_id`, `test_case_id`, `external_test_key`, `status`, `duration_ms`, `error_message`, `details_json` |
| `known_bugs` | `id`, `product_id`, `external_tracker`, `external_issue_key`, `title`, `status`, `fingerprint`, `details_json` |
| `run_bugs` | `id`, `run_id`, `test_result_id`, `bug_id`, `match_type`, `confidence`, `confirmed_at` |
| `artifacts` | `id`, `run_id`, `kind`, `storage_key`, `media_type`, `size_bytes`, `sha256`, `created_at` |

Это концептуальная схема. Ниже - правила, которые важнее точного набора колонок.

### Правила моделирования

**1\. Использовать UUID для основных идентификаторов.**

Тогда прогоны и результаты не зависят от последовательности записей или конкретной базы. Внешние ID задач трекера хранятся отдельно.

**2\. Версионировать тестовые библиотеки.**

Если библиотека находится в Git, для каждого прогона сохраняйте commit SHA. Если тесты генерируются динамически, дополнительно сохраняйте идентификатор или хеш сгенерированного набора.

**3\. Не привязывать результаты только к текущей версии теста.**

В `test_results` следует сохранять `external_test_key` как снимок идентификатора из входного отчёта. `test_case_id` может быть `NULL`, если тест пока не удалось сопоставить со справочником.

**4\. Сохранять сырой отчёт отдельно.**

В БД должны быть результаты, необходимые для фильтрации и аналитики, но не полный HTML или большой файл JSON. Исходный артефакт связывается через `artifacts.storage_key`\.

**5\. Разделить статус прогона и статус проверки.**

Для прогона нужны, например, `queued`, `running`, `processing`, `passed`, `failed`, `cancelled`, `error`\. Для проверки - `passed`, `failed`, `skipped`, `error`, `unknown`\. Точное различие между `failed` и `error` нужно закрепить в контракте отчётов.

**6\. Зафиксировать правила связи с багами.**

`match_type` может принимать `manual`, `exact_key`, `fingerprint` или `heuristic`\. Автоматическое совпадение должно быть объяснимым и не превращаться в подтверждённый баг без достаточных оснований.

### Минимальные ограничения целостности

- `UNIQUE(test_libraries.key)`
- `UNIQUE(test_library_versions.library_id, test_library_versions.version)`
- `UNIQUE(test_cases.library_id, test_cases.external_key)`
- `UNIQUE(known_bugs.external_tracker, known_bugs.external_issue_key)` для записей с заполненным внешним ID
- `UNIQUE(artifacts.storage_key)`
- Индексы по `test_runs.created_at`, `test_runs.status`, `test_results.run_id`, `test_results.test_case_id`, `known_bugs.fingerprint`

Для `test_runs` я бы также ввёл `idempotency_key` или аналогичный механизм, чтобы повторная отправка одного запроса не создавала несколько одинаковых прогонов.

## 5\. Контракт API

Я бы сразу закрепил минимальный API. Даже если веб-интерфейс и обработчик результатов написаны в одном приложении, они должны работать через эти же сервисные границы.

| Метод и путь | Назначение |
|--------|--------|
| `POST /api/v1/runs` | Создать прогон и поставить его в очередь |
| `GET /api/v1/runs` | История с фильтрами и пагинацией |
| `GET /api/v1/runs/{id}` | Карточка прогона |
| `GET /api/v1/runs/{id}/results` | Результаты проверок |
| `POST /api/v1/runs/{id}/artifacts` | Зарегистрировать загруженный артефакт |
| `GET /api/v1/artifacts/{id}` | Получить артефакт или ссылку на него |
| `GET /api/v1/products` | Список продуктов |
| `GET /api/v1/test-libraries` | Список тестовых библиотек |
| `GET /api/v1/known-bugs` | Поиск известных багов |
| `POST /api/v1/known-bugs` | Создать локальную карточку бага |

Для больших отчётов лучше использовать потоковую загрузку файла, а не передавать содержимое в JSON-запросе.

Для JS-скрипта в обработчике результата предусмотрите API чтения справочников и версию схемы ответа. Если скрипт работает с сотнями проверок, не заставляйте его делать отдельный HTTP-запрос для каждого теста: добавьте пакетные запросы или получение необходимых справочников одним запросом.

### Пример создания прогона

```json
{
  "library_key": "payments-api",
  "library_version": "1.4.2",
  "commit_sha": "0123456789abcdef",
  "environment_key": "staging",
  "run_type": "api",
  "parameters": {
    "collection": "collections/payments.json"
  }
}
```

Ответ должен содержать ID созданного прогона и его начальный статус. Исполнитель получает из БД не произвольную команду оболочки, а разрешённый тип задачи с проверенными параметрами.

Не храните пароли, токены и реальные секреты в `parameters_json`\. Там должны быть ссылки на разрешённые конфигурации или имена секретов, а не сами секретные значения.

## 7\. Как мигрировать на другой стенд

Главная цель - чтобы миграция была переносом состояния и конфигурации, а не новым проектом.

### Что должно переноситься

| Объект | Способ переноса |
|--------|--------|
| API и worker | Повторная сборка из Git или развёртывание зафиксированных образов |
| Структура БД | Alembic-миграции |
| Данные PostgreSQL | `pg_dump` / `pg_restore` |
| Отчёты и вложения | Копирование каталога артефактов с проверкой хешей |
| Справочники и баги | Переносятся вместе с БД |
| Секреты и настройки | Новый `.env` и конфигурация целевого окружения |
| Очередь Redis | Не переносить вслепую; перед переключением завершить или отменить активные задачи и восстановить их состояния из PostgreSQL |

PostgreSQL поддерживает логический перенос с помощью `pg_dump` и `pg_restore`, в том числе между машинами с разной архитектурой. \[[PostgreSQL: Documentation: 18: 25.1. SQL Dump](https://www.postgresql.org/docs/current/backup-dump.htm?utm_source=chatgpt.com); [PostgreSQL: Documentation: 15: pg\_dump](https://www.postgresql.org/docs/15/app-pgdump.html?utm_source=chatgpt.com)\]

### Процедура переезда

1. **Подготовка.** Развернуть целевой сервер, проверить версии образов, сеть, DNS, свободное место и доступ к тестируемому приложению.
2. **Репетиция.** Скопировать тестовую копию БД и артефактов, запустить её на новом стенде, проверить историю и открытие старых отчётов.
3. **Остановка новых запусков.** На время переключения отключить создание задач и дождаться завершения активных прогонов либо пометить их как прерванные.
4. **Финальный перенос.** Сделать итоговый дамп PostgreSQL и синхронизировать артефакты. Проверить контрольные суммы.
5. **Запуск на целевом сервере.** Применить миграции, настроить окружение, запустить API и worker, проверить статусы и доступность файлов.
6. **Приёмка.** Создать контрольный прогон, сравнить результаты с исходным окружением, проверить доступ всех пользователей в LAN.
7. **Завершение.** Переключить пользователей на новый адрес. Старую машину оставить выключенной или доступной только для чтения до окончания периода проверки.

Есть один принципиальный нюанс: не стоит просто копировать каталог PostgreSQL во время работы контейнера. Используйте штатное резервное копирование либо корректную процедуру переноса данных.
