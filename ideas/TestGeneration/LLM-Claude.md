## 2. Принципы

1. **Разделять по жизненному циклу.** Исходные документы (меняются редко, версиями), тесты (код), движок (общий
   для всех проектов), результаты (только дописываются), знания (баги, типовые дефекты, статистика) — разные места.
2. **Одна раскладка для всех проектов** — шаблон, а не договорённость. Отличия проекта — в его `project.yaml`, а не
   в структуре каталогов.
3. **Движок не копируется.** Раннер, конвертеры, экспорт Allure, работа с трекерами — один источник, версия
   фиксируется в проекте.
4. **Всё адресуется стабильными ID**, уникальными глобально: проект, модуль, требование, тест, проверка
   библиотеки, идея, прогон, баг. Связи — по ID, в обе стороны.
5. **Сначала машинный формат, потом представления.** `run.yaml` + `results.json` + `triage.yaml` — источник;
   `report.md`, Allure, матрица трассировки, протокол ПСИ, сводки — генерируются из них.
6. **Прогон неизменяем** — после завершения меняется только слой разбора (`triage.yaml` и раздел «Разбор»).
7. **Тяжёлое — не в git.** В git — то, что читает человек и диффает машина; сырые ответы и вложения — во внешнем
   хранилище со ссылкой и хешем.
8. **Каждый вывод модели проверяется другой моделью** там, где ошибка дорогая: подтверждение бага, «дубль / не дубль»,
   классификация падения, предложение фикса (идея `ideas/ResultCheck`).

## 3. Сущности и идентификаторы

| Сущность | Формат ID | Пример | Где живёт |
|---|---|---|---|
| Проект | `<PRJ>` — короткий код, латиница | `BFF`, `VPN13` | `project.yaml` |
| Модуль | `<PRJ>.<MOD>` | `BFF.ADMIN-AUTH` | `project.yaml` |
| Документ-источник | `<PRJ>.DOC.<код>` | `BFF.DOC.OTZ` | `sources/sources.yaml` |
| Требование | ID из документа, иначе `<DOC>-<номер пункта>` | `BFF.DOC.PMI-4.2.3` | `sources/requirements.yaml` |
| Проверка библиотеки | как сейчас в Test-Library | `AUTH-LOGIN-017` | Test-Library |
| Идея теста | номер inbox | `IDEA-351` | `Test-Library/Api/ideas/inbox.md` |
| Тест | `<MOD>/<путь в коллекции>` + стабильный `testId` в метаданных | `BFF.ADMIN-AUTH.T0123` | коллекция |
| Прогон | `<PRJ>-<YYYYMMDD-HHMMSS>-<набор>` | `BFF-20261019-101530-full` | хранилище результатов |
| Баг | `BUG-<PRJ>-NNNN` | `BUG-VPN13-0022` | хранилище результатов |
| Типовой дефект | `DEF-NNNN` | `DEF-0003` (nested JSON → 500) | Test-Library |

Старые `BUG-NNNN` остаются алиасами (поле `aliases` в карточке), файлы переименовываются один раз.

## 4. Раскладка

### 4.1. Уровень рабочего места

```
C:\Git\
  Test-Library/      знания: проверки по направлениям, таксономия, профили, процесс, типовые дефекты (DEF-*)
  test-engine/       движок: раннеры, конвертеры, отчёты, трекеры, генераторы (бывш. postman/tools/run + 13vpn/tools/run)
  PostmanScripts/    фреймворк проверок внутри Postman (как сейчас)
  TaskTrackers/      адаптеры трекеров (или войдут в test-engine)
  tests-<проект>/    тесты проекта (бывш. postman, 13vpn)
  results-<проект>/  прогоны и баги проекта (бывш. test-runs, 13vpn/test-runs)
  BFF_repo/ ...      исходники продукта — только чтение
```

Почему результаты отдельно от тестов: история тестов не засоряется прогонами (это уже решено в ADR 0003),
у результатов другой режим доступа (их читают разработчики и менеджеры) и другая политика хранения.
Почему результаты по проекту, а не один общий репозиторий: проекты разных отделов (13vpn — чужой отдел),
разные права доступа. Сквозные сводки по всем проектам строит движок, читая несколько `results-*`.
Альтернатива — один `test-results/<PRJ>/...`: проще, но смешивает доступы; выбрать пользователю.

### 4.2. Проект тестов `tests-<проект>/`

```
README.md  CLAUDE.md
project.yaml              код проекта, модули, связи модулей, стенды, трекер, репозитории продукта, версия движка,
                          нужные доступы (БД, логи, исходники, админ-учётки) и что из них выдано
docs/                     STATUS, ideas, decisions (как во всех проектах)
sources/
  sources.yaml            манифест: документ, роль, уровень, версия, sha256, откуда взят
  original/               исходные файлы (docx/pdf/drawio) — Git LFS или ссылка на Drive + хеш
  md/                     сжатые Markdown-копии (навык requirements-transform)
  contracts/              OpenAPI/proto/WSDL по версиям
  requirements.yaml       извлечённые требования с ID, ссылкой на место в документе и модулем
product/
  repos.yaml              репозитории продукта по модулям: url, ветки, путь к локальному клону
stands/
  <стенд>.yaml            адрес, окружение Postman, как узнать версию, путь разблокировки, доступы
tests/
  api/<модуль>/           коллекция Postman v3 — папка на ручку (каждая ручка отдельно запускаема)
  e2e/                    сценарии через несколько модулей
  ui/web|mobile|desktop/  когда появятся
  nonfunc/load|soak/      когда появятся
  security/
  requirements/           ГЕНЕРИРУЕМОЕ представление: дерево как в ПМИ/ТЗ, внутри ссылки/копии тестов
suites/                   наборы запуска: smoke, acceptance-<модуль>, regression, release, psi, destructive
traceability/             ГЕНЕРИРУЕМОЕ: матрица требование ↔ тест ↔ проверка библиотеки ↔ идея
generation/               журнал генерации: какие проверки библиотеки выбраны/отброшены и почему (для повторяемости)
```

**Роли документов** (`sources.yaml`, поле `role`): `original` (ФТТ заказчика), `derived` (ОТЗ), `detailed` (ЧТЗ
модуля), `acceptance` (ПМИ/ПСИ), `contract`, `design` (схемы, C4), `obsolete`. Названия в проектах разные — агент
при заведении проекта предлагает роли, человек подтверждает один раз. Конфликт между уровнями (ОТЗ противоречит ЧТЗ)
— отдельный артефакт `sources/conflicts.md` и вопрос аналитику, а не молчаливый выбор.

**Тесты по требованиям без дублирования.** Тест живёт один раз — у ручки (или в `e2e/`). В метаданных теста —
`requirements: [BFF.DOC.PMI-4.2.3, ...]` с пояснением «что именно проверяется из пункта». Папка
`tests/requirements/` повторяет структуру ПМИ и собирается генератором из этих ссылок (Postman v3 — копии запросов
с пометкой «generated, не править»). Исключение — сценарии ПМИ, которые являются многошаговыми и не сводятся к
ручке: они пишутся прямо в `tests/requirements/` или `e2e/` как первичные.
Требование без тестов — видно в матрице как «не покрыто» с причиной (нет доступа, не проверяемо через API, отложено).

### 4.3. Результаты `results-<проект>/`

```
runs/
  index.jsonl                         строка на прогон (машинный индекс); INDEX.md генерируется
  <YYYY>/<MM>/<RUN-ID>/
    run.yaml                          манифест прогона (см. ниже)
    results.json                      общая модель результатов (не зависит от раннера)
    triage.yaml                       разбор каждого падения: класс, баг, кто разбирал, кто перепроверил
    report.md                         генерируется из трёх файлов выше; руками — только раздел «Разбор»
    evidence/                         запрос/ответ упавших тестов (обрезано); тяжёлое — ссылкой
    allure-results/                   не в git
bugs/
  README.md                           реестр (генерируется из bug.yaml)
  BUG-<PRJ>-NNNN/
    bug.yaml                          статус, серьёзность, fingerprint, модуль, требования, тесты, трекер-ID, aliases
    bug.md                            описание для человека/трекера (шаблон как сейчас)
    occurrences.jsonl                 строка на каждый прогон, где воспроизвёлся / не воспроизвёлся
    fix.md, fix.patch                 предложение исправления (если был доступ к исходникам)
history/
  allure-history.jsonl                тренды Allure
  flaky.jsonl                         тесты, менявшие статус без изменения продукта и тестов
```

**`run.yaml`** — главное, чего сейчас не хватает:

```yaml
id: BFF-20261019-101530-full
project: BFF
modules: [BFF.ADMIN-AUTH]
kind: acceptance | regression | full-regression | release | psi | smoke | adhoc
trigger: {type: manual | command | pipeline, by: <человек/агент>, machine: ..., pipeline_url: ..., build_id: ...}
started: ...; finished: ...
suite: suites/full.yaml
scope: {profile: Regression, max_priority: P2, tags: [...], destructive: false}
stand: {name: sandbox, url: ..., environment: Sandbox, production: false, secrets: open}
product:                              # срез тестируемого продукта
  version: <что отдал /version или «не отдаёт»>
  modules:
    BFF.ADMIN-AUTH: {repo: ..., branch: dev, commit: abc123, image: sha256:..., source: <откуда узнали>}
  contract: {file: sources/contracts/admin/api.yaml, version: 0.0.1, probe: {present: 5, total: 48}}
tests: {repo: tests-bff, commit: 70b95b2, dirty: false}
engine: {version: 1.4.0, runner: newman 6.2.3}
library: {repo: Test-Library, commit: be080da}
agent: {model: claude-opus-5-5, cross_check_model: ...}   # если прогон/разбор делала модель
summary: {tests: 290, passed: 95, failed: 181, broken: 0, skipped: 14}
```

Если стенд не отдаёт версию — `product.version: unknown` и источник косвенный (коммит ветки на момент деплоя,
`contract_probe`). Отдельно — предложение команде продукта: ручка `/version` (или заголовок) с коммитом и временем
сборки; оформить как баг/улучшение один раз на проект (проверка уже есть в inbox — идея 6, `OBS-BUILD-VERSION-TRACEABLE`).

**`triage.yaml`** — классы как сейчас в Allure: `bug` (+ID), `test-defect`, `stand-lag`, `cascade` (+от чего),
`env` (стенд недоступен, учётка заблокирована), `flaky`, `unknown`. Поля `classified_by`, `verified_by` (модель или
человек). Прогон «оформлен», когда `unknown` = 0.

**Тяжёлые артефакты.** Порог (например 1 МБ на файл) и политика: в git — `run.yaml`, `results.json` (сжатый, если
велик), `triage.yaml`, `report.md`, обрезанное `evidence/`. Полный `raw/` — в Git LFS, GitLab Generic Packages или
S3/MinIO, путь и sha256 — в `run.yaml`. Хранить сырьё: последние N прогонов на модуль, все прогоны `release`/`psi`,
все прогоны, на которые ссылается баг.

### 4.4. Баги: жизненный цикл и дубли

```
draft → confirmed → filed → (fix-claimed) → verified | reopened
         ↑ перепроверка второй моделью        ↑ прогон показывает «не воспроизводится»
```

- **Fingerprint** — ключ для поиска дублей: `модуль + метод/путь (шаблон) + ID проверки + класс симптома`
  (например `status:500`, `header-missing:Strict-Transport-Security`). Новое падение сначала ищется по fingerprint в
  `bugs/`, затем в трекере (поиск по метке `Autotest` + текст), затем «похожие» — по описанию, решение «дубль?»
  перепроверяет вторая модель.
- **Повторы.** Каждый прогон дописывает `occurrences.jsonl`; если баг уже в трекере — комментарий «воспроизводится
  в RUN-ID на сборке X, curl ...», не чаще раза на сборку. «Не воспроизводится» на новой сборке → кандидат в
  `verified`, но закрывать только после повтора (защита от flaky).
- **Привязки в баге**: прогоны, тесты, требования, проверки библиотеки, идеи (`IDEA-*`), типовой дефект (`DEF-*`),
  что и зачем проверялось — уже частично есть в шаблоне, сделать обязательными полями `bug.yaml`.
- **Предложение исправления** при доступе к исходникам: место в коде (файл:строка в коммите из `run.yaml`), причина,
  патч; перепроверка второй моделью; в трекер — как комментарий «предложение», не как факт.
- **Трекеры** — адаптер на трекер (YouTrack есть, Jira/Redmine/GitLab/GitHub — по мере нужды) с тремя операциями:
  `search`, `create`, `comment/update`. Режимы `ask | auto | links` остаются.
- **Типовые дефекты (`DEF-*`) в библиотеке.** Когда одинаковый дефект находится во втором проекте — заводится
  `DEF-*` в Test-Library: описание, проверки, которые его ловят, частота. Это обратная связь для приоритета проверок
  и для генерации: «эта проверка нашла баг в 2 из 2 проектов» → P0. Конкретику проекта (адреса, креды) в
  библиотеку не переносить.

## 5. Генерация тестов

Текущий принцип (документация → выбор проверок библиотеки по правилам → коллекция) оставить, добавить:

1. **Журнал генерации** (`generation/<дата>.md|yaml`): какие источники прочитаны (с sha из `sources.yaml`), какие
   проверки библиотеки применены, какие отброшены и почему, какие идеи inbox использованы. Это делает генерацию
   повторяемой и позволяет при новой версии документа перегенерировать только затронутое (diff по `sources.yaml`).
2. **В каждом тесте** — блок метаданных (уже есть «Метаданные теста»): `testId`, что/зачем/как/почему проверяется,
   требования с цитатой пункта, проверки библиотеки, идеи, приоритет, профили, разрушающий ли, нужные доступы.
3. **Запрос доступов на этапе генерации**: генератор собирает список того, что нужно тестам (БД, логи, SSH, исходники,
   вторая учётка с другой ролью, путь разблокировки) → `project.yaml: resources` со статусом `granted | requested |
   unavailable`; тесты, которым доступа нет, генерируются со `skip` и причиной — в отчёте видно «не проверено, нет
   доступа к БД», а не тишина.
4. **Перекрёстная проверка сгенерированного**: вторая модель читает требование и тест и отвечает «тест проверяет
   то, что написано в пункте?» — расхождения в журнал генерации.
5. **E2E** — из описания связей модулей в `project.yaml` и сценарных карт/ПМИ; живут в `tests/e2e/`, в метаданных —
   список затронутых модулей, чтобы регресс по модулю включал задевающие его e2e.
6. **Другие направления** (UI, нагрузка, безопасность, SQL) — в той же раскладке `tests/<направление>/`, с тем же
   `results.json` на выходе (адаптер раннера на направление). Структура библиотеки по направлениям — идея
   `ideas/Restructuresation`.

## 6. Запуски и наборы

| Повод | Набор (`kind`) | Что входит | Где |
|---|---|---|---|
| Ручной / по команде | `adhoc`, любой набор | что указано | машина человека / агент |
| Вышел билд модуля | `acceptance` | тесты модуля по профилю PR/CI + e2e, задевающие модуль | пайплайн |
| Билд из нескольких модулей | `regression` | модули билда + их e2e | пайплайн |
| Выход на общее тестирование | `full-regression` | всё, кроме разрушающих по решению | пайплайн |
| Переход на Stage / Prod | `release` | безопасный поднабор: без разрушающих, без перебора паролей, креды маскируются | пайплайн, явное подтверждение |
| ПСИ | `psi` | дерево `tests/requirements/` по ПМИ | по запросу; результат — черновик протокола |

Пайплайн передаёт в движок `build_id`, коммиты модулей, адрес стенда → попадают в `run.yaml`. Все флаги, которые
сейчас спрашиваются интерактивно (разрушающие, лимит входов, креды, заведение в трекер), имеют значение по умолчанию
для пайплайна в `project.yaml` / наборе.

## 7. Отчёты

Все генерируются из `run.yaml` + `results.json` + `triage.yaml`:

| Отчёт | Для кого | Есть сейчас |
|---|---|---|
| `report.md` | человек, агент | да |
| Allure с severity в дереве | человек | да |
| JUnit XML | CI (зелёный/красный билд) | нет |
| **Сравнение с прошлым прогоном**: новые падения, починилось, всё ещё падает, flaky | разработчик, менеджер | нет — самое полезное из новых |
| **Матрица трассировки**: требование → тесты → статус последнего прогона | аналитик, ПСИ | нет |
| **Черновик протокола ПСИ** по пунктам ПМИ | заказчик | нет |
| Сводка по багам модуля/сборки | разработчик | частично (реестр) |
| Сводка по проектам (тренды, покрытие, открытые баги) | руководитель | нет; можно артефактом-дашбордом |

## 8. Что предложить добавить в исходные данные проекта

- Ручку/заголовок версии сборки на стендах (коммит, время) — без неё срез продукта косвенный.
- Описание стендов от команды продукта: какие модули на каком стенде, как обновляются, лимиты блокировок, путь
  разблокировки.
- Доступ на чтение к БД стенда и логам — для проверки побочных эффектов и для доказательной базы в баге.
- Доступ к трекеру на чтение (минимум) — для поиска дублей ещё до заведения.
- Список уже известных проблем / технического долга от разработчиков — меньше «новых» багов, которые не баги.
- Сценарные карты / пользовательские сценарии — основа для e2e.
- Контакт аналитика для вопросов по конфликтам требований (`sources/conflicts.md`).

## 9. Порядок внедрения

**Этап 1 — до следующего прогона (минимум, чтобы не плодить хаос):**
1. Утвердить раскладку `tests-<проект>` / `results-<проект>` и коды проектов (`BFF`, `VPN13`).

4. `triage.yaml` — единый для обоих проектов.
5. Политика тяжёлых артефактов (порог, что в git, что наружу) — хотя бы решение и `.gitignore`.
6. 13vpn — под git.
7. Существующие прогоны: дописать `run.yaml` задним числом из `report.md` скриптом, раскладку по `YYYY/MM` —
   по желанию.

**Этап 2 — движок:** вынести общий код в `test-engine`, версия в `project.yaml`; отчёт «сравнение с прошлым
прогоном»; JUnit; адаптер трекера с поиском дублей и комментариями о повторах.

**Этап 3 — требования:** `sources.yaml` с ролями, `requirements.yaml`, метаданные `requirements` в тестах,

**Этап 4 — знания:** `DEF-*` в библиотеке, обратная связь «проверка → найденные баги» в приоритеты, сводка по

**Этап 5 — новые направления** по мере появления (UI, нагрузка, безопасность) в той же раскладке.

# Часть 2. После чтения мнений других моделей

## 11. Общее у всех (консенсус — можно считать устойчивым)

- Документ — направление, а не ТЗ; исполнитель вправе менять решения с обоснованием.
- Сквозная трассировка требование → тест → прогон → баг; ID стабильные, не зависят от имён файлов.
- Тесты и результаты — раздельно; манифест прогона со срезом продукта; машинный формат первичен, Markdown/Allure —
  представления.
- Дубли багов: поиск в локальной базе и в трекере, повтор — комментарий к существующему, а не новый баг.
- Доступы запрашиваются на этапе генерации; без доступа тест не молчит, а помечен.
- Предложение исправления — при доступе к коду, отдельно от фактов.

| Предложение | Чьё | Почему нет (или не сейчас) |

## 14. Чего не увидел ни у кого (и считаю важным)

1. **Конкретный разбор текущего состояния** — у всех общая схема «с нуля»; а беспорядок уже есть и требует миграции
   (две раскладки, копии инструментов, коллизия номеров багов, рост объёма). Без Этапа 1 любая целевая архитектура
   останется на бумаге, а новый прогон добавит ещё одну раскладку.
2. **Коллизия ID багов между проектами** — практическая проблема уже сейчас (`BUG-0001` × 2).
3. **Типовые дефекты между проектами (`DEF-*`)** как обратная связь в библиотеку и приоритеты проверок — у ChatGPT
   есть «оценка пользы проверки по истории» (§19.13), но без механизма; у меня — конкретный.
4. **Журнал генерации** для повторяемости и частичной перегенерации по diff источников.
5. **Политика объёма** с цифрами: 158 МБ за два дня работы двух проектов.

## 17. Баг в нескольких проектах и модулях (замечание человека)

Один и тот же дефект может быть в нескольких проектах/модулях, и в одном его исправят, а в другом нет. Поэтому
дубль определяется **с учётом принадлежности**, а воспроизводимость ведётся по каждому месту отдельно.

- **Fingerprint включает проект и модуль**: `проект + модуль + метод/путь + ID проверки + класс симптома`. Одинаковый
  симптом в другом модуле — не дубль автоматически, а «похожий».
- **Между проектами — всегда разные баги** (`BUG-BFF-0006` и `BUG-VPN13-0022` — оба «глубокий JSON → 500»): разные
  команды, трекеры, сроки. Связь — через типовой дефект `DEF-*` в библиотеке (у дефекта — список багов по проектам).
- **Внутри проекта, разные модули:**
  - разный код (отдельные микросервисы) — отдельный баг на модуль, со ссылкой «тот же дефект в …»;
  - общий код (общая библиотека, общий шлюз/прокси) — один баг, в нём список затронутых модулей.
  Не ясно — отдельные баги со ссылкой (объединить проще, чем разделить).
- **Статус по месту**, а не только по багу — в `bug.yaml`:
  ```yaml
  affects:
    - module: BFF-Admin-Auth
      status: open | fixed-claimed | verified | reopened
      first_seen: BFF-20261012-165850-full
      last_seen: BFF-20261013-101530-full      # последний прогон, где воспроизвёлся
      last_checked: BFF-20261013-101530-full   # последний прогон, где проверялся (мог не воспроизвестись)
      fixed_in: <сборка/коммит>                # когда «не воспроизводится» подтверждено повтором
  ```
  Баг закрыт, когда закрыты все его `affects`. `occurrences.jsonl` — строка на пару (модуль, прогон).
- **Регресс**: исправленное место снова воспроизвелось — `reopened` у этого места, а не новый баг.

## 18. Рабочее место: отдельный каталог с репозиториями (вопрос 1)

Идея человека — один каталог, внутри репозитории. Предложение:

```
C:\Git\QA\                      рабочее место тестирования (сам каталог — не репозиторий)
  Test-Library\                 знания: проверки, процесс, типовые дефекты
  PostmanScripts\               фреймворк проверок внутри Postman
  test-engine\                  движок (если выносить отдельно — раздел 19)
  projects\
    BFF\
      tests\                    репозиторий тестов проекта (бывш. postman)
      results\                  репозиторий прогонов и багов (бывш. test-runs)
      archive\                  старые опытные прогоны
    VPN13\
      tests\                    бывш. 13vpn (под git)
      results\                  бывш. 13vpn/test-runs
```

Плюсы: всё, что касается тестирования, в одном месте; проект — каталог с двумя репозиториями, доступы раздельные
(VPN13 — чужой отдел); новый проект — копия шаблона. В `C:\Git` остаются служебные (`AI-Memory`, `reports`,
`skills`, `TaskTrackers`) и исходники продукта (`BFF_repo`, `stands`).

Что придётся поправить при переезде: `AI-Memory/memory/projects-map.md`, пути в `CONVENTIONS.md` / `SETUP.md`
(если там `C:\Git\<репо>`), `CLAUDE.md` проектов, относительные пути между `postman` и `test-runs` в скриптах
(`run.py` ищет соседний клон), навык `create-tests-api`. Пути к соседям вынести в настройку (`project.yaml`
или переменную окружения), а не «клон рядом».

## 19. Движок: что это и где держать (вопрос 2)

**Что входит в движок** — код, который сейчас скопирован между `postman/tools/run` и `13vpn/tools/run`:

| Часть | Сейчас | Что делает |
|---|---|---|
| Точка входа | `run.py` | Читает набор, окружение, решает про креды, разрушающие тесты, лимит входов, запускает раннер, пишет прогон |
| Конвертер | `v3_to_v21.py` | Коллекция Postman v3 (YAML из git) → JSON v2.1 для newman |
| Драйвер newman | `newman_run.js` | Запускает newman, отделяет основной запрос от вспомогательных запросов фреймворка, пишет `results.json` |
| Сверка стенда | `contract_probe.py` | Какие операции контракта есть на стенде |
| Отчёты | `allure_export.py`, генерация `report.md` / `INDEX.md` | Allure с severity, Markdown |
| Баги и трекер | `file_bugs.py`, `make_bugs.py` | Заведение в YouTrack / ссылки «Завести» |
| Генерация | `gen_collection.py`, `test_meta.py` | Сборка коллекции и метаданных тестов |

Это **не** фреймворк проверок: `PostmanScripts` выполняется внутри Postman/newman (JavaScript в коллекции), а движок —
снаружи (Python/Node): готовит запуск и обрабатывает результат.

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Отдельный репозиторий `test-engine`** | Своя версия: проект фиксирует «движок 1.4», обновление — осознанно; у движка свои тесты и история; библиотеку можно держать публичной, а движок (интеграции трекеров, адреса GitLab) — нет | Ещё один клон; правка, задевающая и библиотеку, и движок, — два коммита |
| **Внутри `Test-Library/tools`** | Один клон; движок и библиотека меняются вместе | Библиотека меняется часто (inbox — десятки коммитов в день), версия движка «размазана» по ним — фиксировать проект на версии движка неудобно; разные права доступа не сделать |
| Оставить в каждом проекте (как сейчас) | Проект самодостаточен | Копии расходятся — это и есть текущая проблема |

Рекомендация прежняя — отдельный репозиторий; но разница не критична: можно начать с `Test-Library/tools/engine`
и вынести позже — важнее убрать копии.

## 20. Сырые файлы прогонов: о чём вопрос (вопрос 3)

Полный прогон сейчас даёт (замер по последним прогонам BFF / VPN13):

| Файл | BFF | VPN13 | В git сейчас | Зачем |
|---|---|---|---|---|
| `raw/` (полный вывод раннера: все запросы и ответы) | 6.6 МБ | 5.6 МБ | да | Повторный разбор, доказательства |
| `results.json` | 2.9 МБ | 3.6 МБ | да | Источник отчётов |
| `report.md` | 1.5 МБ | 0.4 МБ | да | Для человека |
| `allure-results/` + `allure-report.html` | 16 МБ | 22 МБ | нет (пересобирается) | Отчёт Allure |

То есть ~10 МБ в git на каждый полный прогон. Git хранит все версии навсегда: при ежедневных прогонах по нескольким
модулям — гигабайты за несколько месяцев, клон на новой машине становится долгим. Вопрос — **куда класть то, что
нужно редко** (в основном `raw/`):

| Вариант | Как работает | Плюсы | Минусы |
|---|---|---|---|
| **Не хранить `raw/` в git** | В git — `results.json` (в нём уже запрос/ответ по каждому тесту), `raw/` остаётся на диске машины | Ничего настраивать не надо | Сырьё теряется (обычно не нужно — `results.json` хватает) |
| **Git LFS** | Файл в репозитории подменяется ссылкой, содержимое — на сервере GitLab, скачивается по требованию | Прозрачно для git; GitLab поддерживает | Место на сервере всё равно растёт; нужен `git lfs` на каждой машине |
| **GitLab Generic Packages** | Архив прогона загружается через API в реестр пакетов проекта GitLab, в `run.yaml` — ссылка | Не трогает историю git; GitLab уже есть | Скрипт загрузки; чистка старого — правилом или вручную |
| **Своё S3 (MinIO)** | Объектное хранилище со сроками хранения | Гибко, чистка автоматически | Нужна инфраструктура и её поддержка |

Рекомендация для старта: **`raw/` в git не класть** (`.gitignore`), `results.json` — сжатым (`results.json.gz`,
в разы меньше), отдельно — урезанный `evidence/` по упавшим тестам. Внешнее хранилище — когда появится реальная
потребность в сырье (пайплайн, ПСИ).
