### 1. Монетизация: что на самом деле продаётся

**Тезис.** «Невозможность стянуть библиотеку» технически недостижима для любого содержимого, которое уходит на сторону
клиента: API, отдающее записи, выкачивается перебором (операции × признаки). Поэтому защищать надо не файл, а то, что
файлом не является:

1. **Конвейер генерации** — контракт и ТЗ → модель операций → подбор → спецификация → коллекция → прогон → разбор →
   баги. Это знания процесса (`Process/`, промпты, генераторы, проверки качества), и они важнее статического YAML.
2. **Свежесть** — выгрузка багов из трекеров (ADR 0004, 0012) непрерывно добавляет записи и шаги. Снимок устаревает,
   подписка — нет.
3. **Полные шаги и доказательства** — `steps` (45 % объёма; варианты из реальных багов), `proofs`/RWB, словарь
   тестовых значений, правила отбора. Открытой должна быть «карта рисков», закрытой — «как именно ловить».
4. **Обратная связь с прогонов** — что реально находит баги, у каких записей высокая отдача (`metrics.md`). Это
   данные, которые копия репозитория не воспроизведёт.

**Модель: open core.**

| Открыто (сообщество, доверие, SEO) | Закрыто (сервис) |
|---|---|
| Схема записи, таксономия, профили | Полные `steps`, `expected` с вариантами, `proofs`, RWB |
| Каталог: ID, заголовок, риск, категория, протокол | Словарь тестовых значений (ADR 0009) |
| `PostmanScripts` (фреймворк проверок), формат спецификации | Структурная применимость и правила отбора (см. п. 2) |
| Срез `approved` «базовых» проверок (HTTP-семантика, валидация ввода) — как демо | Конвейер с LLM: ТЗ, исходный код, противоречия источников |
| | Поток новых записей из выгрузки багов, метрики отдачи |

**Защита закрытой части (снижает, а не исключает утечку):**

- сервис отдаёт **результат** (спецификацию или коллекцию под конкретные операции клиента), а не записи;
- лимиты по ключу и по числу операций/записей в сутки; аномалии перебора — блокировка;
- водяные знаки: у каждого клиента своя формулировка части шагов и несколько «канареечных» записей — утечка
  опознаётся;
- лицензия на открытую часть (например CC BY-NC-SA для каталога) и договор на закрытую — юридическая, а не техническая
  защита;
- AGPL у движка — оставить.

**Формы продажи (по убыванию простоты запуска):** услуга «сгенерируем и прогоним набор» (уже умеем, нужен только
договор); подписка на обновления закрытой части для своих команд; удалённый сервис (Web + API/MCP) с оплатой за
операцию или прогон; on-prem для закрытых контуров (многие заказчики не отдадут контракты и ТЗ во внешний сервис —
152-ФЗ, NDA). Для on-prem библиотека неизбежно уходит к клиенту — защита только договором и водяными знаками.

**Риск, который нужно закрыть до продажи:** «с библиотекой качественнее» подтверждено на одном проекте (BFF). Нужен
второй проект и сравнение A/B (с библиотекой / без / по готовому прогону) с измеримыми метриками: число тестов,
уникальные найденные баги, доля ложных падений.

### 2. Можно ли генерировать только скриптами и где нужен LLM

**Ответ: частично — да, и это стоит сделать, но не вместо LLM, а до него.**

Слой, который делается скриптом (детерминированно, без токенов):

1. **Модель операций из контракта** (OpenAPI/proto): метод, путь, параметры пути (ID ресурса), тело и типы полей,
   ограничения (`maxLength`, `enum`, `format`), схема авторизации, роли (access-model), пагинация, загрузка файлов,
   идемпотентность. Основа есть в `generate_coverage.py`.
2. **Структурная применимость записей** — вместо свободного текста предикаты по признакам модели:
   ```yaml
   match:
     all: [method_in: [POST, PUT, PATCH], has_body: true]
     any: [field_format: [email, uri], field_type: string]
     none: [operation_tag: health]
   ```
   Текущее `applicability.when` остаётся как пояснение для человека и LLM. Перевод 631 записи — разовая работа LLM
   партиями с проверкой скриптом и выборочной вычиткой человеком.
3. **Подбор**: операция × запись → «применимо / нет / решает LLM» (часть условий в принципе не формализуется —
   например «есть бизнес-ограничение на количество»).
4. **Генерация параметризованных тестов** для формальных категорий: HTTP-семантика, матрица методов, валидация по
   схеме (границы, типы, `enum`), AuthN-матрица, контрактные коды. Ожидание — из контракта и стандарта.

Оценка (гипотеза, проверить на BFF): по числу тестов скриптовый слой может дать 40–60 %, по ценности (найденные баги) —
заметно меньше: дорогие находки в бизнес-логике и противоречиях источников.

Где LLM **нужен** (и где тратятся токены, оправданно):

- ТЗ, ЧТЗ, ПМИ → ожидания вне контракта, требования с ID (ADR 0002);
- противоречия источников (контракт vs ТЗ vs код) — главная находка `requirements`;
- исходный код продукта → тесты на уже существующие проблемы (обработка ошибок, пропущенные проверки прав);
- решение по «серым» условиям применимости, которые не формализованы;
- бизнес-сценарии и состояния (цепочки вызовов, данные на стенде);
- разбор результатов прогона и оформление багов.

Следствие для монетизации: **скриптовый слой — бесплатный/дешёвый тариф и демо, LLM-слой — платный** (он и стоит
денег на токенах).

### 3. Экономия токенов

Главное: экономит не хранилище (БД вместо файлов), а **отбор до LLM** и **разделение записи на «для LLM» и «для
человека/трассировки»**. Хранилище вторично.

Идеи по убыванию эффекта:

1. **Скриптовый предотбор по модели операций** (п. 2). LLM видит не 631 запись, а кандидатов для операции — по оценке
   десятки, а не сотни. Без структурной применимости — грубый предотбор по протоколу, категории, `kind` и признакам
   (`has_body`, `has_id_param`) уже отсекает заметную часть (GraphQL, gRPC, websocket, UI, DB для REST-проекта).
2. **Классы операций.** Операции с одинаковым вектором признаков (например, все `GET /x/{id}` под одной ролью)
   решаются LLM один раз на класс, а не на каждую ручку.
3. **Два уровня детализации: карточка → полная запись.** Карточка — `id`, `title`, `risk` в одну строку,
   `applicability.when` (≈ 150–250 байт). LLM отбирает по карточкам, полную запись запрашивает только для отобранного.
   Поля трассировки (`references`, `proofs`, RWB, `profiles`, run-теги, `automation`, `notes` шагов с номерами inbox) в
   промпт генерации не попадают никогда.
4. **То, что сделано скриптом, LLM не пересказывать** — ему передаётся только сводка «уже покрыто: ID × операции»,
   чтобы не дублировал.
5. **Режим разницы при перегенерации** — п. 4 Process уже требует сравнить с прошлым коммитом библиотеки; автоматизировать:
   `select_checks.py --since <commit>` → только новые записи и шаги.
6. **Факты из ТЗ и кода — один раз, с кешем.** Самые большие тексты — не библиотека, а ТЗ и исходники. LLM извлекает
   из них компактную модель фактов (требование ID → утверждение → операция), результат хранится в проекте
   (`docs/sources/` уже есть) и пересчитывается только по изменённым документам (sha256 в манифесте уже есть).
   Сопоставление «факт → записи библиотеки» — по карточкам или семантическому поиску.
7. **Семантический поиск** (эмбеддинги карточек) для обратного направления: «по этому требованию какие риски из
   библиотеки?» — дополняет структурный подбор, не заменяет его.
8. **Кеширование промпта** у провайдера: неизменная часть (правила, схема, карточки) в начале контекста — повторные
   вызовы в пределах TTL дешевле. Окно не экономит, деньги — да.
9. **Мелкое:** единый язык записей (русский текст стоит больше токенов, чем английский; смешение в одной записи — худший
   вариант), без повторов в `expected`.

**Хранение и интерфейс.** Источник истины — git (ревью, история, ADR — остаётся). Сборка строит индекс (SQLite или
JSON): карточки, признаки применимости, эмбеддинги. Один и тот же индекс обслуживает:

- локально — `select_checks.py --openapi <контракт>` и **MCP-сервер** для LLM: `match(operation)`,
  `cards(ids)`, `check(id, fields)`, `search(text)`, `since(commit)`;
- удалённо — тот же MCP/HTTP API с ключом, лимитами и водяными знаками.

MCP как интерфейс удобен тем, что локальная и платная версии отличаются только адресом и ключом, а LLM-конвейер не
меняется.

## Часть 2 (после чтения LLM-ChatGPT, LLM-DeepSeec, LLM-Qwen)

Test-Library остаётся открытым, закрытой будет создаваемая система генерации.** Поэтому вопросы Части 1 п. 1–3 закрыты, а

целиком, закрыто всё, чего в ней нет.

### Что общее у всех

- Запретить копирование открытого или отдаваемого клиенту содержимого технически нельзя; лимиты и квоты лишь
  удорожают выкачивание. Монетизировать сервис, превращающий знания в результат, а не доступ к файлам.
- Перенос в БД сам по себе токены не экономит; экономит **многоступенчатый отбор**: детерминированный фильтр по признакам
  операции → короткие карточки → полные записи только для отобранного.
- Формальная часть генерации (каркас из контракта, границы, статусы, схемы, авторизация) — скриптами; LLM — требования,
  исходный код, бизнес-логика, новые проверки.
- Кеширование префикса промпта — полезно, но вторично.
- Сначала замерить (качество и стоимость), потом строить платформу.

### Что беру у других

1. **Разделение «библиотека — что проверять; индекс проекта — где и как проверять»** (ChatGPT, второй ответ). Это
   главное, чего не было у меня: основной расход токенов — не библиотека, а ТЗ, документация и исходный код проекта. У меня
   это было одной строкой (п. 3.6 «факты из ТЗ и кода с кешем»), у ChatGPT — отдельный слой: карта кода, данных,
   безопасности, требований и связи «требование → реализация → проверка → результат»; факты со ссылкой на исходник,
   версию и координаты; целевые запросы фрагментов вместо файлов; инкрементальная переиндексация.
2. **Гипотезы о дефектах из библиотеки** (ChatGPT): запись библиотеки задаёт направление поиска в коде (например, доступ
   к чужому объекту → найти обработчик → где проверка прав) → гипотеза → тест, который её подтверждает или опровергает.
   Это прямо отвечает на «тесты, ловящие уже существующие в коде проблемы».
3. **Статусы результатов анализа** (ChatGPT): подтверждённый дефект / вероятный дефект / пробел покрытия /
   неоднозначность требований. Ложится на наше (`requirements`, `needs_clarification`, «лучше баг, чем молчание»,
   ADR 0002), но различает силу доказательства.
4. **Разнообразие при отборе, а не топ-K** (ChatGPT): обязательные по правилам + ранжированные поиском + добор
   непокрытых классов риска + гипотезы LLM. **Эмбеддинги ищут кандидатов, но не решают применимость** — полностью
   согласен.
5. **Порядок поиска** (ChatGPT): метаданные → полнотекстовый → связи → векторный — по мере необходимости; PostgreSQL с
   JSONB и полнотекстовым поиском для старта сервиса. Локально — SQLite/JSON-индекс (у меня).
6. **Двухпроходная генерация «план → детализация»** (ChatGPT, Qwen): план по карточкам, детали — по выбранным; при
   пробелах повторяется только нужный этап. У Qwen первый проход — дешёвой моделью; это совпадает с нашей практикой
   дочерних сессий с другой моделью (память `child-sessions-allowed`).
7. **Офлайн-резюме записей** (Qwen) — по сути мои карточки, с уточнением: строить заранее, при сборке, и проверять
   скриптом.
8. **Метрики** (ChatGPT): стоимость качественного прогона как главная, плюс исполнимость, уникальность, доля новых
   полезных проверок, воспроизводимость повторной генерации.
9. **«Recall поиска плохо предсказывает качество генерации»** (DeepSeek): проверять отбор по итоговым тестам и найденным
   багам, а не только по полноте выборки.
10. **API сервиса** (ChatGPT): `knowledge/search` (карточки), `knowledge/resolve` (полные по ID), `plans`,
    `generations` — черновик внешнего интерфейса рядом с MCP.

### С чем не согласен

- **«Без платного движка открытая библиотека бесполезна для автотестов»** (Qwen, неявно DeepSeek). Неверно: в BFF именно
  LLM-агент общего назначения читает библиотеку и `Process/` и строит набор. Любой, у кого есть открытая библиотека и
  Claude/ChatGPT, получит заметную часть нашего качества. Ценность закрытой системы должна быть **сверх** этого: индекс
  проекта, конвейер с проверками, данные прогонов, свежесть, стоимость и время. Отсюда вопрос про `Process/` (ниже).
- **Qwen: test-engine — LLM-генератор.** Фактическая ошибка: `test-engine` — запуск, отчёты, баги; генерация сейчас —
  LLM + спецификация + `gen_collection.py` в проекте тестов.
- **Qwen: «скриптовая генерация убьёт монетизацию».** Формальная часть тестов и так легко воспроизводится; она годится
  как бесплатный уровень и демо, а платить будут за анализ требований и кода.
- **Qwen: дообучение модели вместо контекста.** Не сейчас: библиотека меняется ежедневно (выгрузка багов), дообучение её
  заморозит; датасета «спецификация → эталонный набор» нет (один проект); привязка к одной модели, а мы намеренно
  используем несколько. Вернуться, когда будут десятки проектов.
- **DeepSeek: скрипты дадут 70–80 % тестов.** Не проверено; мои 40–60 % — тоже гипотеза. Число тестов — плохая мера,
  важнее доля найденных багов. Проверять на BFF.
- **DeepSeek: «библиотека живёт только на сервере».** Противоречит решению bj — библиотека открыта.
- Ссылки DeepSeek и Qwen на внешние инструменты и проценты (IM-RACG, SWE-Pruner, «в 10 раз дешевле», «2 000 токенов на
  эндпоинт») не проверял — в план как факты не беру.

### Чего не увидел ни у кого

1. **Открыт не только корпус, но и метод.** `Process/` (порядок сборки коллекции, баги, прогоны, группы безопасности,
   тестовые значения) лежит в открытой Test-Library — это «генератор в виде инструкции» для любого агента. Навыки
   (`skills`) — в закрытом GitLab. Нужно решить, что из метода остаётся открытым.
2. **Структурной применимости нет ни у одной записи** (0 из 631). Все трое предлагают детерминированный фильтр, но без
   этого шага он работает только по грубым признакам (протокол, категория, `kind`). Это первый объём работы.
3. **Золотой набор уже есть** — подбор LLM по BFF (`docs/analysis.md` проектов). Сравнивать новый отбор с ним, а не
   строить эталон заново.
4. **Данные клиента.** Сервис получает контракты, ТЗ и исходный код заказчика — NDA, 152-ФЗ, закрытые контуры. Для
   российского корпоративного рынка on-prem может оказаться основным вариантом, а не «Enterprise-опцией».
5. **Мы сами — первый клиент.** Отбор и индекс проекта сразу уменьшают расход токенов в текущей работе (BFF, группы
   безопасности) — их стоит делать, даже если продажа не состоится.

### Идея

Три части с чёткой границей:

| Часть | Где | Доступ | Что |
|---|---|---|---|
| **Открытая библиотека** | `Test-Library` (GitHub) | открыта, растёт как сейчас | записи проверок, схема, таксономия, словарь значений, каталог; метод — по решению (вопрос 1) |
| **Исполнение** | `test-engine` (закрыт, AGPL), `PostmanScripts` (открыт) | как сейчас | прогон, отчёты, Allure, баги |
| **Система генерации** (новая) | новый приватный репозиторий | закрыта; сервис или on-prem | индекс знаний, индекс проекта, конвейер с LLM, данные прогонов, интерфейсы |

**Что продаёт система генерации** (того, чего нет в открытой библиотеке):

1. **Индекс проекта** — компактная модель контракта, требований (с ID), кода (маршруты, обработчики, проверки прав,
   модели данных) и связей «требование → реализация → проверка → результат»; факты со ссылкой на источник и версию;
   инкрементальное обновление по изменённым файлам (манифест `docs/sources/` с sha256 уже есть).
2. **Конвейер**: модель операций → отбор по библиотеке → план → детализация → проверка скриптами → спецификация →
   коллекция → прогон → разбор → баги. LLM — только на этапах интерпретации.
3. **Гипотезы о дефектах**: запись библиотеки → поиск места в коде → гипотеза → тест; статусы результата: подтверждён /
   вероятен / пробел покрытия / неоднозначность требований.
4. **Данные прогонов**: какие записи реально находят баги (отдача, `Api/mining/metrics.md`), какие дают ложные падения —
   ранжирование при отборе.
5. **Стоимость и скорость**: меньше токенов на модуль при том же или лучшем качестве.

### Скрипты и LLM

| Делает скрипт | Делает LLM |
|---|---|
| Модель операций из OpenAPI/proto (метод, путь, ID-параметры, типы и ограничения полей, авторизация, роли, пагинация, файлы) | Требования → ожидания вне контракта (ADR 0002) |
| Отбор записей по структурной применимости (`match:`), классы однотипных операций | Противоречия источников (контракт, ТЗ, код) |
| Формальные тесты: HTTP-семантика, матрица методов, границы и типы, AuthN-матрица, контрактные коды | Гипотезы о дефектах в коде, решение по «серым» условиям применимости |
| Индексация кода и документов, обход связей, выдача фрагментов | Бизнес-сценарии, цепочки вызовов, данные на стенде |
| Проверка плана и спецификации, дедупликация, покрытие | Разбор результатов, тексты багов |

### Экономия токенов

Со стороны библиотеки:

1. Предотбор скриптом по модели операций; без `match:` — грубо по протоколу, категории, `kind`, признакам операции.
2. Карточки (ID, заголовок, риск, `applicability.when` — ~150–250 байт) → полная запись только для отобранного; поля
   трассировки (`references`, `proofs`, RWB, профили, run-теги, `notes` шагов) в промпт не попадают.
3. Однотипные операции — одно решение на класс.
4. Сделанное скриптом LLM не пересказывать — только сводка «покрыто».
5. Перегенерация — только новые записи и шаги с прошлого коммита библиотеки.
6. Отбор с разнообразием: обязательные + ранжированные + добор непокрытых классов риска.

Со стороны проекта (основной расход):

7. Факты из ТЗ и кода извлекаются один раз, хранятся, пересчитываются по изменившимся источникам.
8. LLM получает доказательную базу под задачу и сама запрашивает фрагменты кода (функция, middleware, модель), а не
   файлы целиком.
9. Подтверждённые факты отделены от предположений и повторно не анализируются.

Общее: кеширование неизменного префикса промпта; черновые проходы — более дешёвой моделью.

**Хранение и интерфейс.** Источник истины библиотеки — git. Сборка строит индекс (карточки, признаки применимости, позже —
полнотекстовый и векторный поиск). Локально — SQLite/JSON и MCP-сервер (`match`, `cards`, `check`, `search`, `since`);
в сервисе — PostgreSQL (JSONB, полнотекстовый поиск) и те же операции через MCP/HTTP с ключом, лимитами и журналом.

### Что из этого следует

1. **Граница проходит по смыслу, а не по файлам:** открыто то, что описывает «что проверять» (корпус и его формат);
   закрыто то, что решает «к чему применять и как собрать» (разметка `match:`, отбор, индекс проекта, конвейер, данные
   прогонов). Разметка — отдельный слой поверх записей, по `check.id`, а не поле в открытой схеме.
2. **Свежесть библиотеки — открытая, механизм свежести — закрытый.** Результаты выгрузки багов (новые записи, шаги,
   RWB) идут в библиотеку; сборщики, промпты, сырые данные, метрики отдачи — в закрытую часть.
3. **Поток идей из проектов** (решение 6) — уже существующий `Api/ideas/inbox.md` плюс правило: в идею попадает
   обобщённый риск и шаг, без кода, названий внутренних компонентов, адресов и данных заказчика. Нужна проверка перед
   коммитом (скрипт/чек-лист), иначе граница держится на внимательности.
4. **AGPL на корпусе и внешние участники.** Как правообладатель bj может использовать библиотеку в закрытой системе.
   Но вклад сторонних авторов под AGPL этим правом не покрывается: закрытый сервис, использующий их записи по сети,
   рискует подпасть под обязанность раскрытия. Нужен CLA (соглашение участника — передача или широкая лицензия на вклад)
   до первого внешнего PR. Внутренние идеи из проектов покрыты решением 6.
5. **В открытом репозитории сейчас лежит и то, что к корпусу не относится:** `docs/` (статус с внутренними задачами),
   `ideas/` (включая эту стратегию монетизации), `Api/mining/` (механизм свежести), `Api/tools/` для отбора,
   `Process/projects.yaml` (реестр внутренних репозиториев), случайные файлы в корне (`session_results.txt`, PDF).
   Историю не переписываем (решение 7), но новое туда класть не стоит.
6. **Удаление контрактов ломает ссылки:** `Api/tools/generate_real_contract_coverage.py`, `Api/README.md`,
   `Api/docs/REAL_CONTRACTS_STAGE4.md`, `TEST_SELECTION_AND_COMMANDS.md`, `STAGE_REPORTS.md`, корневой `CLAUDE.md`
   ссылаются на `Api/examples/real-contracts/`. При реорганизации — перенести инструмент и анализ контрактов в
   закрытую часть (контракты живут в `docs/sources/` проектов тестов).

каталоги `generator/`, `mining/`, `process/`, `docs/`, `ideas/`. Проще в работе (один клон, одна история решений),
разделить позже можно. **Рекомендую его для старта.**

### Порядок переезда

1. ADR о разделении и раскладке (в закрытом репозитории; в Test-Library — короткая ссылка «почему корпус отдельно»).
2. Создать закрытый репозиторий, перенести `docs/`, `ideas/`, `Process/`, `Api/mining/`, инструменты отбора —
   **копированием с сохранением истории** (`git filter-repo --path …` в отдельный клон) либо простым переносом с
   ссылкой на последний коммит Test-Library.
3. Инвентаризация ссылок до удаления из Test-Library: `grep` по `Test-Library/Process`, `Test-Library/Api`,
   `AUTOTEST_LIBRARY` в test-engine, bff-tests, skills, AI-Memory (`CONVENTIONS.md`, память), корневых `CLAUDE.md`.
   Переключить ссылки, проверить контрольным прогоном BFF (как в ADR 0013).
4. Только после этого — удалить перенесённое из Test-Library и привести корпус к новой раскладке по направлениям.
5. CONTRIBUTING + CLA в Test-Library; правило и проверка для идей из проектов (решение 6).
6. Дальше — этапы 1–7 «Итога для исполнителя» уже в закрытом репозитории.

### Вопросы человеку (Часть 3)

1. **Имя и место закрытого репозитория:** GitHub `bj-` (приватный) или GitLab `gitlab.viiitech.ru`? От этого зависит,

2. **Один закрытый репозиторий или несколько** (генератор / выгрузка багов / процесс)? Рекомендую один для старта.
3. **`Process/`**: процесс команды (запуск, баги, трекер) — в закрытую часть; а «как писать проверку» — в открытый
   CONTRIBUTING. Так?
4. **CLA** для внешних участников — согласны? Формат (передача прав или лицензия на вклад) — на ваш выбор.
5. **История при переносе:** сохранять (`git filter-repo`) или начать закрытый репозиторий с чистого листа со ссылкой
   на коммит Test-Library?
6. **Реорганизацию корпуса по направлениям** (`ideas/Restructuresation/`) делать в этом же переезде?
