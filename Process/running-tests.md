# Запуск тестов

Короткий путь (Claude на новой машине делает именно это):

1. Рабочее место и проект - по [`workspace.md`](workspace.md): `python C:\Git\Autotest\test-engine\engine\autotest.py setup <КОД>`
   клонирует `tests` и `results` проекта из реестра [`projects.yaml`](projects.yaml); проекта нет в реестре - спросить
   у пользователя адреса; нет движка или Test-Library - спросить, откуда склонировать.
2. Проверить инструменты (раздел «Подготовка машины»).
3. Стенд и учётки тестовых стендов уже в окружении `tests/postman/environments/<Окружение>.environment.yaml`.
   Нет нужного окружения или это production - **спросить у пользователя**.
4. Выбрать или составить набор `tests/suites/<Модуль>/<набор>.yaml`; посмотреть план: `python autotest.py run <набор> --dry-run`.
5. Запустить из корня `tests`: `python autotest.py run suites/<Модуль>/<набор>.yaml --env <Окружение>` (агент -
   с переменной `AUTOTEST_AGENT=<модель>`; известна сборка - `--build`). Первым идёт tinySmoke (поле `gate` набора):
   не прошёл - билд битый, остальное не запускается.
6. Разобрать падения (раздел «Разбор»), завести баги по [`bugs.md`](bugs.md), заполнить раздел «Разбор и баги»
   в `report.md`.
7. **Спросить пользователя**, заводить ли баги в трекере сейчас или сначала разобраться по отчёту (проблемная сборка
   не должна засорять трекер): `python autotest.py file-bugs --mode auto` или `--mode links` (`bugs.md`, «Заведение в трекер»).
8. Закоммитить прогон и баги в репозиторий результатов; push - после подтверждения пользователя.

## Способы запуска

| Способ | Когда | Как | Отчёт |
|---|---|---|---|
| **newman** (основной) | Автоматический прогон, CI, без Postman | `autotest.py run --runner newman`: коллекция YAML v3 конвертируется в JSON v2.1 (`v3_to_v21.py` движка), запуск newman как библиотеки (`newman_run.js`) | Полный: запрос, ответ, проверки, вложенные вызовы фреймворка |
| **Postman CLI** | Не используется для прогонов (см. ниже) | `postman collection run <каталог коллекции> -e <env.json> -i <путь> ...` | Только консоль: `--output` доступен лишь тарифу Postman Enterprise |
| **Postman App (Runner)** | Ручная отладка одного теста | Коллекция в Local View, окружение Sandbox | Только в интерфейсе; для истории не используется |

Фреймворк `PostmanScripts` работает в newman без изменений (проверено 2026-10-12, newman 6.2.3).

Почему не Postman CLI (проверено 2026-10-12, v1.73.0, вход выполнен):
- `--output` (структурированный отчёт) - только для Postman Enterprise; без него есть лишь консольный вывод.
- Postman CLI подставляет `{{переменные}}` в **текст скрипта до выполнения**: значение берётся на момент старта
  скрипта (не видит `setVar` в том же скрипте), а значение с кавычками (JSON) ломает синтаксис - `SyntaxError`
  в `Login - N17`. Newman так не делает. Результаты двух раннеров поэтому могут расходиться.
- Запросы выполняются в порядке `-i`, а не в порядке коллекции.

| Что | Проверка | Установка (Windows) |
|---|---|---|
| Python 3 + PyYAML | `python -c "import yaml"` | `pip install pyyaml` |

Git Bash искажает пути при вызове `newman.cmd` напрямую - запускать через `autotest.py run` (движок вызывает Node сам).

## Окружение и секреты

- Окружение в git: `postman/postman/environments/<Окружение>.environment.yaml` - включая адрес и учётки тестовых
  стендов (креды стендов открыты, см. «Креды»).
- Переопределения: `postman/.local/<Окружение>.yaml` (каталог в `.gitignore`) - для production и личных учёток, плоский YAML `ключ: значение`,
  перекрывает окружение, например:
  ```yaml
  baseUrl: https://bff-admin.example.ru
  AdminAccounts: '[{"login":"...","password":"...","role":"root"}]'
  ```
  Переменные фреймворка - `PostmanScripts/README.md`.

## Креды

Креды тестовых стендов общедоступны: на dev / test / sandbox / stage они остаются в отчётах, `results.json` и багах
открытыми, чтобы разработчик воспроизводил без вопросов (правило - `bugs.md`, «Креды»).

`autotest.py run --secrets auto` (по умолчанию) определяет стенд: `isProduction=true` - production; адрес с `dev`, `test`,
`sandbox`, `stage`, `stg`, `qa`, `uat`, `demo`, `preprod`, `localhost` - не production; иначе - не опознан.
На production и неопознанном стенде запуск останавливается: **спросить пользователя**, что делать с кредами, и
запустить с `--secrets mask` (пароли и cookie сессии -> `***`) или `--secrets show`. В отчёте строка «Креды»
показывает выбранный режим.

## Блокировка учёток

Тесты входа шлют неверные пароли к настоящим учёткам стенда. Если стенд блокирует учётку после N неудачных входов,
прогон может заблокировать общую учётку.

- **Путь разблокировки** стенда (учётка, которой можно разблокировать; ручка; срок блокировки; к кому обратиться)
  описывается в проекте: `postman/docs/project/stands.md` и env `accountUnlock` окружения стенда - для людей и Claude.
- **Пути разблокировки нет** - безопасный лимит по умолчанию **5** неудачных входов подряд на учётку. При запуске
  движок предупреждает об этом и спрашивает лимит: 1 / 3 / 5 / 10 / 100 / ввод вручную (ключ `--safe-failed-logins N`;
  без терминала, например из Claude, - остановка: **спросить пользователя** и передать ключом). Лимит не превышать.
- Фреймворк (`PostmanScripts`, «Login guard») считает неудачные входы каждой учётки из `AdminAccounts` - в основном
  запросе и во вспомогательных - и по достижении лимита тихо выполняет успешный вход (сбрасывает счётчик стенда).
  `LockoutAccount` не охраняется: её блокируют тесты перебора намеренно.
- Лимит стенда известен - он в env `accountLockoutLimit` (и `accountLockoutSec`) и в описании стенда; безопасный лимит
  **строго меньше** его, с запасом на чужие ошибки входа на общем стенде (лимит 5 -> безопасный 3). Защита входит, когда
  счётчик **достигает** безопасного лимита: равный лимиту стенда уже блокирует учётку (так 2026-10-12 был заблокирован
  `root` на sandbox). С таким лимитом прогон не запускается.
- Реальный лимит есть, а пути разблокировки нет - в багах про вход **предупреждать проверяющего** (`bugs.md`).

## Разрушающие тесты

Разрушающие тесты (`needFlag("allowDestructive")`: смена пароля, блокировка учёток) запускаются **только по явному
решению**: движок спрашивает при запуске (ключ `--destructive yes|no`; без терминала - спросить пользователя).
Не запускались - в отчёте строка «Разрушающие тесты: не запускались» и раздел «Не запускались» со списком.
Запуск только их одним кликом - `run-destructive.cmd` в корне репозитория тестов (набор `suites/<Модуль>/destructive.yaml`).

## Объём прогона

Измерения библиотеки (приоритет P0-P3, профили `profiles/*.yaml`: Smoke, PR, CI, Regression, Nightly, Release,
категории, метки) переносятся в коллекцию: блок «Метаданные теста» в конце описания каждого запроса
(`autotest.py meta postman/collections/<Модуль>`). Источник - проверки библиотеки, на которые ссылается тест («Библиотека: ID»): приоритет -
самый высокий, профили и метки - объединение; для тестов без ссылок - правила модуля
(`tests/tools/specs/<Модуль>/test_meta.yaml`). Разрушающие тесты в Smoke, PR, CI не входят.

Выбор при запуске: `autotest.py run --profile <Профиль> --max-priority <P> --tag <метка>` или поля набора `profile`,
`max_priority`, `tags`; профиль добавляет свой `max_priority` из `profiles/<Профиль>.yaml`. Объём пишется в отчёт.

Группа безопасности (ADR 0011, `security-groups.md`) - метка `sg-...` в метаданных; прогон группы -
`autotest.py run <набор> --group <G>`, общий прогон делится на части по группам - `autotest.py split <каталог прогона>`.

## Трекер для багов

Тип и адрес трекера, префикс темы бага (по умолчанию `[AT]`) и метки (по умолчанию `Autotest`) выбирает тот, кто
запускает: `tests/.local/tracker.yaml` (образец - `test-engine/examples/tracker.example.yaml`) или ключи
`autotest.py run --tracker youtrack --tracker-url <адрес> --tracker-project <ключ> --bug-prefix <префикс> --bug-tag <метка>`. Выбор попадает в отчёт (строка «Трекер
для багов»); шаблоны - `templates/trackers/`. Не задан - баги только в `bugs/` репозитория результатов, трекер уточнить у пользователя.

## Наборы тестов

`tests/suites/<Модуль>/<набор>.yaml`:

```yaml
collection: BFF-Admin-Auth          # каталог в postman/collections
kind: full-regression                # вид прогона для run.yaml: smoke, acceptance, regression, full-regression, release, psi, adhoc
gate: tiny-smoke.yaml                # tinySmoke - набор, который идёт первым; не прошёл - остальное не запускается
# items: all                         # вся коллекция; only: destructive - только разрушающие; exclude: [пути, папки]
contract: docs/sources/contracts/admin/api.yaml   # контракт для сверки стенда (желательно всегда)
description: что проверяет набор
items:                               # путь запроса от корня коллекции без .request.yaml; `<папка>/` - вся папка (движок 0.7.0)
  - api/auth/login/TESTS/Pos/Login - P01 200 admin login
```

Порядок выполнения - как в коллекции (order папок и запросов), а не как в списке. В наборе указывать, нужны ли
`allowWrite` / `allowDestructive` и сколько учёток требуется.

**tinySmoke** (`tiny-smoke.yaml` модуля) - несколько быстрых позитивных тестов операций, которые есть на любом стенде
(вход, ключевая ручка, выход). Не прошёл - нет ответа или упала ключевая проверка (`gate_checks` - регулярное выражение по
именам проверок, например `'^Status code is'`): билд битый, прогон останавливается (код выхода 3). Стенд, отстающий от
контракта, битым не считается - его падения видны в отчёте.

## Отчёт о прогоне

Движок создаёт в репозитории результатов `runs/<YYYY>/<MM>/<RUN-ID>/` (RUN-ID = `<КОД>-<YYYYMMDD-HHMMSS>-<набор>`):

| Файл | Содержимое |
|---|---|
| `run.yaml` | Манифест: кто и как запустил (человек, агент, пайплайн), стенд, сборка продукта, коммиты тестов, движка и библиотеки, объём, tinySmoke, итог |
| `report.md` | Метаданные (кто, машина, раннер, стенд, креды, трекер, блокировка учёток, разрушающие тесты, коммит коллекции, команда), «Не запускались», «Стенд и контракт», итог, таблица тестов, упавшие проверки с curl для воспроизведения и отформатированным ответом, раздел «Разбор и баги» (заполняется вручную) |
| `results.json` | Те же результаты в машинно-читаемом виде (для сравнения прогонов) |
| `raw/` | Вывод раннера (консоль, исходный JSON/YAML); с `--secrets mask` - без кредов. **Не в git** |

Строка о прогоне добавляется в `runs/index.jsonl`, таблица `runs/INDEX.md` собирается из него. Каждый запрос теста
несёт заголовок `X-Request-ID: <RUN-ID>/<id теста>` - по нему запрос находится в логах стенда.

Отчёт Allure (Allure 3 на Node.js, `npm i -g allure`) движок собирает сам: `allure-report.html` в каталоге прогона -
один файл, открывается в браузере. Severity - из приоритета теста, метки - профили и метки, причины падения - категории
(стенд отстаёт от контракта, каскад, дефект), ссылки на баги и задачи трекера; тренды - `history/<Модуль>/allure-history.jsonl` (последние 20 прогонов)
(в git). HTML и `allure-results` в git не хранятся - собираются из `results.json` (`autotest.py allure <каталог прогона>`).
Код выхода: 0 - всё прошло, 1 - есть падения, 2 - прогон не состоялся, 3 - не прошёл tinySmoke.

## Стенд и контракт

Если в наборе указан `contract`, перед прогоном движок (`contract_probe.py`) проверяет, какие операции контракта есть
на стенде (стенды версию не отдают): каждой операции - запрос без авторизации; `404 Cannot <METHOD> <path>` - маршрута
нет. В отчёте - версия контракта, «есть N из M операций», список отсутствующих; в таблице тестов 🚫 - операции теста
нет на стенде, ↪🚫 - на отсутствующую операцию идёт вспомогательный запрос фреймворка (возможен каскад).
Форматы ответов сверка не проверяет - их расхождения видны в самих тестах.

## Разбор

Каждое упавшее утверждение относится к одной из причин (по ней решается, заводить ли баг):

| Причина | Признак | Действие |
|---|---|---|
| Дефект продукта | Поведение расходится с ожиданием (контракт, ТЗ, стандарт - ADR 0002) | Баг, тип `implementation` |
| Дефект документа | Реализация разумна, а контракт/ТЗ ошибается или молчит | Баг, тип `contract` / `requirements` |
| Стенд отстаёт | Отметки 🚫 / ↪🚫 в отчёте; старый формат ответа (поля не те, что в контракте) | Бага нет; отметить в разборе, перепроверить на актуальной версии |
| Окружение | Нет данных/учёток, недоступен стенд, сеть | Бага нет; исправить окружение |
| Дефект теста | Ошибка в тесте или фреймворке | Исправить тест; бага продукта нет |
| Каскад | Падение - следствие другого (например, проверка сессии через отсутствующую ручку) | Бага нет; указать первопричину |

Ожидание под фактическое поведение не подгонять (ADR 0002). Разбор записывается в `report.md` таблицей
«тест -> утверждение -> причина -> баг (ссылка на файл в `bugs/` репозитория результатов) -> трекер (ссылка на задачу, если заведена
сразу)».

Тесты безопасности разбираются по группам: одна группа - одна сессия, отчёт части `groups/<G>/report.md`
(`security-groups.md`, ADR 0011).
