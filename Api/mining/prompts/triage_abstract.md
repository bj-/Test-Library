# Промпт: триаж, абстракция и сопоставление (шаги 3–5 за один проход)

Выполняет Claude Code над файлом партии `build/mining/<batch>/batches/<name>.md`. Справочники:
`build/mining/library_index.txt` (существующие записи библиотеки) и `taxonomy/` (категории и метки).
Результат — `build/mining/<batch>/batches/<name>.out.jsonl`, одна строка JSON на каждый баг партии,
проверка — `python tools/mining/batch.py check --name <name>`.

## Задача по каждому багу

1. **Триаж.** Это дефект поведения, который можно обнаружить black-box запросами к API (REST, gRPC, GraphQL,
   WebSocket) или по ответу сервера? Если нет — `verdict: out_of_scope` и класс:
   `build` (сборка, зависимости, типы, упаковка), `ui` (интерфейс, вёрстка), `memory` (утечки, рост ресурсов),
   `perf-internal` (деградация без внешнего проявления в одном запросе), `docs` (документация, сайт),
   `framework-internal` (DI, жизненный цикл, логгер, внутренние API фреймворка без внешнего проявления),
   `usage` (ошибка настройки или использования, а не дефект), `insufficient-data` (мало данных, только ссылка,
   описание обрезано), `client-lib` (клиентские библиотеки, SDK, песочницы — не сервер),
   `other` (остальное: CLI, миграции, не баг). Плюс `reason` — одна фраза.
   Если дефект проявляется в ответах API не сразу — после перезапуска, сброса кэша, истечения срока, на другом
   экземпляре — это всё равно `api`, а не `other`.
2. **Абстракция** (только для `api`). Паттерн без привязки к продукту, по-русски:
   - `title` — суть в одной строке, как заголовок проверки;
   - `condition` — при каком условии/данных проявляется;
   - `action` — что сделать в тесте (запрос, последовательность);
   - `expected` — что должно быть; `actual` — что ломалось в реальном баге;
   - `protocol` — список из `rest`, `grpc`, `graphql`, `websocket`, `generic`;
   - `category` — одна из `taxonomy/categories.yaml`; `tags` — из группы `domain`/`quality` `taxonomy/tags.yaml`;
   - `owasp` — категория OWASP API Security Top 10:2023 (`API1`…`API10`) или `null`; `cwe` — список номеров;
   - `expected_source` — откуда ожидание: RFC/стандарт с номером, OWASP, практика, здравый смысл.
   Ожидание не додумывать сверх бага и источника. Мало данных — `verdict: out_of_scope`, класс `insufficient-data`.
3. **Сопоставление** (только для `api`) с `library_index.txt`:
   - `covered` — существующая запись проверяет ровно это; `check_id` — её ID; `variant: null`;
   - `extends` — запись есть, но баг показывает неучтённый вариант; `check_id`, `note` — почему это вариант
     записи, `variant` — новый шаг проверки в повелительной форме, как `steps[].action` записи («Отправить …»,
     «Повторить … для …»), без «Добавить вариант»; если вариант уже есть в записи или у другого бага партии —
     `variant: null` (только пруф);
   - `new` — подходящей записи нет; `check_id: null`, `note` — почему не подходит ближайшая.
   - `family` (у `api`, необязательно) — короткий ключ латиницей через дефис, общий для багов, которые
     проверяются одной матрицей вариантов: одна настройка × протоколы, один тип поля × граничные значения,
     одна операция × форматы тела, режимы развёртывания. Семейство видно по нескольким багам — ключ давать,
     когда в пачке есть похожие баги или баг явно один из ряда; иначе `null`. Семейства собираются на шаге 6
     (`cluster.py`, ADR 0012).

   Правила выбора записи (по разметке точности пилота: ошибки были в сопоставлении, не в триаже):
   - **Механизм, а не тема.** Запись выбирается по тому, что именно ломается, а не по общей области бага.
     Пример: медленный разбор без регулярных выражений (квадратичный парсер, бесконечный цикл) —
     `HARD-EXPENSIVE-OPERATION-LIMITS`; `INJ-REDOS` — только для regex. Обработчик не вызывается при массиве из
     нескольких значений — это валидация массивов, а не защитные заголовки.
   - **Только то, что есть в баге.** Способ атаки, которого нет в тексте бага или фикса, не додумывать — в том
     числе по меткам CWE: CWE говорит о классе, а не о сценарии. Детали варианта (алиасы, составные выражения,
     другие каналы) — только из бага, фикса или его тестов. Механизм не описан — запись, которая проверяет
     описанное следствие; такой нет — `new`, в `note` — «механизм не описан».
   - **Направление проверки.** Законный запрос отклоняется (позитивный баг) — не привязывать к негативной записи
     «лишнее/запрещённое отклоняется», и наоборот. Подходящей записи с тем же направлением нет — `new`.
   - **Баг из интерфейса — про запрос.** Если сервер ломается на том, что прислал интерфейс (скрытое или
     пустое поле формы, лишний параметр), это `api`: баг воспроизводится запросом. Сопоставлять его нужно по
     этому запросу (лишние и пустые поля), а не по виду поля в интерфейсе. Только вёрстка или тема без ошибки
     сервера — это `ui`.

4. **Баги без исправления** — в мета-строке бага `fix: closed-completed`: issue закрыт как выполненный, но PR или
   коммит с исправлением не привязан (ADR 0012). Отсутствие фикса не значит, что это не баг: исправление могли не
   привязать, а могли и не сделать. Вопрос триажа здесь — **хорошая ли это идея теста**: стоит ли проверять такое
   поведение black-box у любого API, а не «подтверждён ли дефект».
   - Ожидание — из стандартов (RFC, OWASP), практики и здравого смысла; `expected_source` — стандарт с номером,
     «практика» или «здравый смысл», не фикс и не мнение мейнтейнера. `actual` — что описал автор бага.
   - `out_of_scope` — по тем же классам: вопрос или ошибка настройки — `usage`, установка и сборка — `build`, мало
     данных — `insufficient-data`. Если мейнтейнер объяснил, что поведение верное, а стандарт и практика с ним
     согласны — `usage`; если стандарт против — это `api` (расхождение — находка).
   - Подтверждение разработчиком (`fix` — `pr`, `commit`, `published`) в ответ не пишется: его берут скрипты из
     пачки, и если позже у бага появится исправление, пруф станет подтверждённым сам.

5. **Идеи UI и БД/SQL** (у любого бага, и `api`, и `out_of_scope`). Библиотека будет расширяться на UI-тесты
   (web, desktop, mobile) и проверки БД, поэтому такие идеи тоже собираются — поле `ideas`, список (пусто — `[]`):
   - `mark` — `UI` (для всех платформ), `UI web`, `UI desktop`, `UI mobile` или `DB`;
   - `text` — проверка одной строкой, без привязки к продукту, как строка inbox.
   `UI` — что проверить в интерфейсе: вёрстка, формы, навигация, состояния экранов, доступность, поведение
   клиента при ошибках сервера. `DB` — схема, ограничения, миграции, процедуры, триггеры, запросы и индексы,
   согласованность данных в БД. Источник — только то, что есть в баге; API-паттерн сюда не дублировать.

## Формат строки

```json
{"id": "owner/repo#123", "verdict": "api", "oos_class": null, "reason": "…",
 "pattern": {"title": "…", "condition": "…", "action": "…", "expected": "…", "actual": "…",
             "protocol": ["rest"], "category": "validation", "tags": ["validation"],
             "owasp": null, "cwe": [], "expected_source": "RFC 9110 §8.3"},
 "match": {"type": "extends", "check_id": "INJ-REDOS", "note": "…",
           "variant": "Отправить в поле даты строку с длинной дробной частью секунд"},
 "family": null,
 "ideas": [{"mark": "DB", "text": "Миграция добавляет NOT NULL-колонку в таблицу с данными без значения по умолчанию"}]}
```

Для `new`: `check_id` и `variant` — `null`. Для `out_of_scope`: `pattern`, `match` и `family` — `null`, `ideas` — как у `api`.
