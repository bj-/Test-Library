# Создание коллекции тестов API

Общие правила сборки коллекции Postman для любого проекта: из чего собирается, как устроена, какие тесты обязательны,
как не навредить стенду. Обобщено из модулей `postman/BFF-Admin-Auth` и `13vpn/13vpn-API` (2026-10). Правила проекта
(фреймворк, флаги, учётки) - в его `docs/` со ссылкой сюда. Ожидания - [ADR 0002](../docs/decisions/0002-expected-behavior-sources.md),
запуск - [`running-tests.md`](running-tests.md), баги - [`bugs.md`](bugs.md).

## 1. Порядок работы

0. **Обновить исходную документацию и проанализировать источники - при каждой генерации и перегенерации**, если
   источник известен (контракт по url, папка ТЗ на Drive, `/api/doc` стенда):
   - **сверить Drive** с прошлым снимком (`docs/sources/drive-inventory.yaml`): новые, изменённые, перемещённые,
     пропавшие файлы и файлы в корзине; нет ли рядом новой версии (номер в имени, «(Заказчик)», Google-документ);
     содержимое могло измениться без смены номера - сверять дату и sha256;
   - **корзина или пропажа документа - сигнал неактуальности**: искать замену и спросить пользователя; тесты по нему -
     «основа под вопросом»;
   - **форматы одного документа** (Google-документ, командный и клиентский docx) не считать копиями - сверять;
     расхождение - находка, главную версию определяют пользователь и аналитик;
   - **документы, на которые ссылается код продукта** (grep по исходникам: названия ТЗ, префиксы ID требований), но
     которых нет в источниках, - предупреждение: разработчик может работать по другому документу;
   - **документация разработки** (репозиторий команды: TS, GTS, FR) - исходный документ: импорт в
     `docs/sources/dev-docs/` (запись `git`: клон, ветка, метка - хеш дерева), проверка новой версии перед генерацией и
     прогоном; клон разработки - только чтение (`fetch`). Сверить её с актуальными ЧТЗ по модулю; расхождения - баги
     `requirements` (ADR 0002, п. 7);
   - скачать актуальные версии, обновить копии и манифест (версия, полный путь, ссылка на файл, дата изменения,
     отметка сверки), изменения (`git diff`) учесть в тестах;
   - **до генерации показать пользователю отчёт об источниках** (`docs/modules/<Модуль>/sources-check.md`): документ,
     версия, ссылка, где лежит, изменился ли, подозрительные копии, вердикт доверия (доверять / с оговорками / не
     доверять). По документу «не доверять» генерацию не начинать без решения пользователя.
1. **Разбор документации** - `docs/analysis.md` проекта: что за система и какой сервис на стенде, источники и их вес
   (контракт, ТЗ, wiki, схемы), требования не из контракта (с ID), найденное при чтении (дефекты контракта и ТЗ -
   кандидаты в баги), объём тестов и что не покрыто и почему. Оригиналы - как получены (`srcDoc/`), для чтения -
   текстовые копии и выжимка контракта в Markdown.
2. **Сверка со стендом до тестов**: какой адрес у API (у SPA - из бандла), вход учёткой, какие операции контракта есть,
   роль учётки, какие данные есть на стенде. Расхождения документа и стенда - находки.
3. **Решения пользователя до первого запуска** (спросить сразу, одним вопросом): безопасный лимит неудачных входов
   (если правила блокировки неизвестны), какие записи разрешены, проводить ли разрушающие тесты. Записать в ADR проекта
   и в `docs/project/stands.md`.
4. **Подбор проверок из библиотеки - при каждой генерации и перегенерации.** Перед этим `git pull` клона
   `Test-Library`: работать по последней версии, чтобы набор проверок модуля был максимально полным и актуальным.
   Пройти все записи `approved` в `Api/checks/` (обзор - `Api/docs/CATALOG.md`), применимые к модулю по протоколу
   (`rest`, `grpc`, `graphql`, `websocket` и `generic`), категории и тегам, - и **все их шаги**: шаг - отдельный вариант
   проверки, часто из реального бага (`proofs`). Применимое - в спецификацию, в описании теста - «Библиотека: ID».
   В `docs/analysis.md` - коммит библиотеки, по которому подбирали, и неприменимые записи с причиной (одной строкой на
   группу, например «нет GraphQL»). При перегенерации - сравнить с прошлым коммитом библиотеки: новые записи и шаги.
   Проверки, которых нет в библиотеке, но которые нужны модулю, - тесты плюс идеи в `Api/ideas/inbox.md`.
5. **Спецификация -> генератор -> коллекция.** Тесты описываются в спецификации (`tools/specs/<Коллекция>/`), коллекция
   генерируется; руками сгенерированное не править.
   **Записи с `test_data`** (тестовые значения по ссылке, ADR 0009, `Process/test-data.md`): значения не открывать
   (словарь `Api/test-data/` закрыт; состав наборов - публичный индекс `Api/taxonomy/test-data-index.yaml`); в запросе
   спецификации `{{td}}` на месте значения и `td_each(Req(...), "TDS-…")` - тест на каждое значение набора; генератор
   сам добавляет `test("notExecuted")`; предупреждения генератора «⚠ тестовые значения» - исправить до прогона. Значения
   со спецсимволами - в теле или заголовке, не в query. Прогон - через newman (`autotest.py run`): движок подставляет
   значения и меняет их в результатах на `[TD-…]`.
6. **Отладочный прогон** (smoke) -> исправить фреймворк и тесты -> **полный прогон** -> разбор -> баги -> отчёт Allure.

## 2. Формат и расположение (Postman v3, Local Mode)

- Коллекция - YAML v3: `postman/collections/<Коллекция>/`, окружения - `postman/environments/*.environment.yaml`.
  В `postman/` - только артефакты Postman (код, документация, экспорт - вне её).
- `.postman/resources.yaml` - **в корне проекта**; в Postman открывать корень, не вложенные папки (иначе Postman создаёт
  свои `.postman` и пустые каркасы). Коллекции и окружения из `postman/` подхватываются сами; в `localResources` - только
  ресурсы вне `postman/` (контракт), иначе дубли.
- **JSON-коллекций и окружений в проекте не держать**: Local Mode требует v3 YAML («Upgrade files» создаёт копии).
  Для newman коллекция конвертируется во временный JSON v2.1 при запуске.
- **Скрипты уровня коллекции - тип `http:beforeRequest` / `http:afterResponse`**; у запросов - `beforeRequest` /
  `afterResponse`. С неверным типом приложение молча не показывает коллекцию, линтер и newman ошибки не видят.
- Длинные значения (схемы контракта в переменной) - многострочными, без строк в десятки тысяч символов.
- Имена папок и файлов - без `\ / : * ? " < > |` и без `-` на конце (линтер FMT019).
- После генерации: `postman collection lint <каталог>` - 0 ошибок; `postman collection list` из корня - коллекция видна.
  Это не гарантирует, что её покажет приложение: при первой сборке проверить и в Postman.
  Не видна - бисекция пробными коллекциями (одна папка запросов + части `definition.yaml`).

## 3. Структура коллекции

| Папка | Назначение |
|---|---|
| `00 Setup` | Вход, подбор данных стенда в переменные (провайдер, пользователь, подписка, ...), создание своих тестовых объектов |
| `<Область>/<операция>` | Тесты операции: позитивы, негативы, роли; одна папка - одна ручка или связанный набор |
| `Public`, `Mobile`, ... | Ручки других ролей и без авторизации |
| `SECURITY` | Сводные проверки: матрица AuthN по всем ручкам, матрица ролей, CORS, заголовки, секреты фронтенда, перебор |
| `<Объект> lifecycle` | Удаление и жизненный цикл тестовых объектов (после всех тестов, которым они нужны) |
| `99 Cleanup` | Уборка всех своих тестовых объектов, в т.ч. созданных по ошибке негативами |

Порядок папок - порядок выполнения: подготовка раньше потребителей, удаление - после.

## 4. Тест

- **Имя**: `<Операция> - <ID> <код> <суть>`, ID: `P01` позитив, `N01` негатив, `A01` авторизация, `R01` роль,
  `S01` безопасность/заголовки, `B01` перебор. Имя уникально в коллекции (по нему баги ссылаются на тест).
- **Описание** (генерируется из спецификации, строки в этом порядке):
  - **Проверяет** - что делает запрос и что утверждается (коды, поля, побочные эффекты);
  - **Зачем** - какой риск ловит тест, чем грозит дефект;
  - **Основа** - источники ожидания с версией и пунктом (ТЗ, контракт, RFC, OWASP, практика, здравый смысл); `⚠` -
    ожидание не из контракта; исходники и сгенерированная из них документация (`/api/doc`) - мнение разработчика,
    как и контракт: подсказка, что пробовать, но не основание ожидания (ADR 0002);
  - **Идеи** - ID, из которых сформирован тест: записи библиотеки (строка `Библиотека: ID, ...` - по ней движок ставит
    метаданные), шаги из реальных багов (`RWB-NNNN`), идеи inbox (`inbox №N`), требования (ID из ТЗ/ПМИ), прежний
    тест, который заменён (`был: <имя>`); тест без единого ID - только с пояснением, почему;
  - в конце - строка метаданных (приоритет `P0`-`P3`, метки, флаги).
- **Скрипты** - только вызовы фреймворка проекта (`utils.bind(...)`, `test(...)`), без прямых `pm.test` / `pm.sendRequest`
  в запросах; сложная проверка - функция фреймворка.
- **Проверки ответа**: код; формат ошибки по контракту (код + тело + `type`); тело по схеме контракта; значения полей
  (эхо запроса, согласованность); время ответа - мягкий порог с ⚠.
- **Заготовки `[DRAFT]`** (ADR 0008): тест по записи с `automation.ai_generation.restricted` - имя `[DRAFT] <имя>`,
  в описании - записи, путь к подробностям (`Test-Library/Api/restricted/<ID>.md`, только для человека) и ручные
  проверки; запись без теста - заготовка в папке `99 Manual (DRAFT)` (запрос не отправляется). Ставит генератор, сценарии
  к таким тестам ассистент не дописывает; чек-лист ручных проверок - `python autotest.py manual sync`.
- Ожидание под фактическое поведение не подгонять. Если тест не может различить исходы без запрещённой записи - расширить
  ожидание с пояснением в описании, а не делать вид, что проверено.

## 5. Обязательный набор тестов

Минимум для любого модуля; полный набор - из библиотеки (п. 1.4).

На **каждую ручку с авторизацией** - матрица AuthN (в `SECURITY`): без заголовка, `Bearer ` пустой, мусор, подделанная
подпись, подмена claim (роль) без переподписи, `alg=none`, refresh вместо access, чужая схема (Basic), без схемы
(для cookie-сессий - аналогичная матрица по cookie). Позитивный контроль: схема в нижнем регистре принимается.

На **каждую роль** - чужая роль на ручках другой роли -> 403 (тело заведомо неполное: при отсутствии проверки роли
придёт 400, а не действие).

**Список с пагинацией**: первая страница (схема, `page`, `pageSize`, не больше `limit`, `totalCount` >= элементов),
граница `limit`=1, страница за концом (пустой список), без обязательных параметров, `limit` 0 / max+1 / не число /
дробный, `page` -1, поиск: пустой / max+1 / граница max / спецсимволы; каждый фильтр - позитив (все элементы ему
удовлетворяют **и результат не пуст, если данные есть**) и значение вне enum -> 400.

**Карточка**: существующий объект (схема, id совпадает), без параметра, не UUID, случайный UUID -> 404, инъекция -> не 500.

**Создание / изменение**: позитив с проверкой эхо и последующим чтением; уникальность (в т.ч. без учёта регистра email);
каждое ограничение схемы на границе и за ней; пустое тело; битый JSON; лишние поля (mass assignment); недопустимые
значения бизнес-правил (из ТЗ).

**Вход и токены**: позитив (схема, срок жизни, роль в токене = роль в ответе), неверный пароль, неизвестный логин -
**та же ошибка** (без перечисления), валидация, инъекции SQL/NoSQL, огромное тело, тип тела не JSON (urlencoded),
`Cache-Control: no-store`; refresh - позитив, повтор старого refresh после ротации, мусор, access вместо refresh,
refresh другой роли; токен удалённой учётки не действует.

**Сводные**: согласованность агрегатов (дашборд = totalCount списков), данных между ручками (публичная витрина = админка,
валюта цен = currency), CORS (чужой Origin не отражается, preflight), заголовки безопасности, нет `X-Powered-By`,
неизвестный маршрут без стека, глубокий JSON -> не 500, секреты в публичном бандле фронтенда, ограничение перебора
(пароль, коды доступа) - на своей учётке.

## 6. Безопасность стенда

- **Флаги** на пишущие и разрушающие тесты (`need("<флаг>")` во фреймворке, env `flags`): без флага - пропуск с причиной,
  в отчёте - раздел «Не запускались». Разрушающие - только по явному решению пользователя, с возвратом состояния и
  проверкой возврата.
- **Негативы без риска записи**: если запись запрещена - негативы на изменение шлются на случайный UUID (не найдено - не
  записано) или с пустым / битым телом; позитивы и рискованные негативы (дубль имени, при дефекте создающий объект) -
  под флагом.
- **Свои объекты**: префикс `AT-` / `at-` + id прогона в имени и email; поиск созданного - по списку, если create не
  возвращает id; уборка в `99 Cleanup` по префиксу.
- **Чужие объекты не трогать**: не создавать объект с email существующего пользователя (может конвертировать учётку), не
  выключать общие сущности (провайдер) без флага.
- **Учётка стенда**: Login guard фреймворка - неудачных входов подряд не больше безопасного лимита, затем тихий успешный
  вход; перебор - только на своей тестовой учётке.

## 7. Документирование

- **`README.md` в корне проекта - обязательно** (для человека, открывшего проект впервые): что это и зачем (система,
  API и версия контракта, цель тестирования, стенд); что где лежит (дерево каталогов с пояснениями); как запускать
  (что установить, команды прогона, где результат и отчёт Allure, как открыть в Postman, что делать после изменения
  тестов и после разбора прогона); ссылки на документы внутри проекта (разбор документации, правила коллекции, стенд,
  STATUS, реестр багов, история прогонов) и на общие правила `Test-Library/Process/`. Подробности - ссылками, не копией.
  Обновлять при изменении структуры, команд запуска или стенда. Шаблон - `AI-Memory/templates/project/README.md`.
- Коллекция (прогон): описание = ручное вступление + автоматическая сводка, которую пишет генератор:
  - статистика: тесты (всего, по папкам/ручкам, позитивы/негативы/безопасность), проверки (вызовы `test(...)` и
    раскрытые матрицы), тесты под флагами (пишущие, разрушающие), расчётное время прогона, применённые записи и шаги
    библиотеки (из них - из реальных багов), тесты с ожиданием `⚠`;
  - **на какой документации собран набор**: каждый документ с версией, а если версии нет - с названием и датой
    последнего изменения исходного документа (у источника, не дата импорта); коммит библиотеки; ревизия стенда, по
    которой сверялись.
  Наборы `suites/` - то же в поле `description` набора (кратко: число тестов и ссылка на сводку коллекции).
- Проект: `CLAUDE.md` (правила для Claude: как генерировать, проверять, запускать), `docs/analysis.md`,
  `docs/project/stands.md`, ADR решений по объёму и безопасности.
- Новая идея проверки - сразу в `Api/ideas/inbox.md`.
