# 0011. Группы проверок безопасности: группа = отдельная сессия на всех этапах

- **Статус:** принято
- **Дата:** 2026-10-23
- **Участники:** bj, Claude

## Контекст

Изоляция ADR [0008](0008-ai-restricted-isolation.md) (закрытые подробности) и [0009](0009-test-data-by-reference.md)
(тестовые значения по ссылке) убрала большую часть остановок фильтра безопасности ассистента, но они всё ещё бывают:
2026-10-21 генерацию спецификации BFF-Mobile-Auth остановила тема «вход и сессии». Сессия держит в контексте сразу
всё про безопасность модуля (токены, роли, инъекции, коды входа), и одна остановка обрывает работу целиком: теряется
и то, что фильтр не трогает. Сессия группы, наоборот, не должна видеть подробности чужих групп, иначе изоляция теряется.

Подход ADR 0009 «описание отдельно, тестовые данные отдельно» себя оправдал, его сохраняем.

## Решение

1. **Группы** - `Api/taxonomy/security-groups.yaml`: `sg-token`, `sg-session`, `sg-login`, `sg-authz`, `sg-injection`,
   `sg-privacy`, `sg-hardening` и `sg-restricted` (стоп-темы), у каждой риск остановки. В группу попадает запись из
   `checks/security/`, категории `security` или с меткой `security`.
2. **Группу назначает скрипт** (`Api/tools/security_groups.py index`) по правилам (id, затем метки, первое
   совпадение); запись с флагом `ai_generation.restricted` или совпадением со стоп-темой - в `sg-restricted`, даже без
   флага (флаг по-прежнему ставит человек). Поле записи `security_group` - только если правила ошибаются. Индекс
   `taxonomy/security-groups-index.yaml` проверяет `validate_library.py`.
3. **Группа протягивается через все этапы** - одной меткой `sg-...`:
   - тест - метка в метаданных (`autotest.py meta` берёт из индекса по записям «Библиотека:»);
   - прогон - `autotest.py run --group sg-...` (то же, что `--tag`), группы теста - в `results.json` (`groups`);
     общий прогон делится скриптом `autotest.py split <прогон>` -> `groups/<группа>/report.md`;
   - баг - поле шапки `Группа`; тег задачи в трекере - тот же (`file-bugs`);
   - чтение - `autotest.py view --group`, `yt.py search --group / --skip-group`, `yt.py show --group`
     (у задачи чужой группы описание скрыто), `export_for_llm.py --group`;
   - дубли - `autotest.py dupes --group`: сравнение со всеми багами, но тема бага чужой группы не печатается -
     совпадение сравнивает человек.
4. **Одна группа - одна сессия** на каждом этапе (генерация, разбор, баги, дубли): сессия читает только записи,
   тесты, отчёт и баги своей группы. Порядок и промпты - `Process/security-groups.md`. Тестовые значения - по-прежнему
   по ссылке `TD-…` (ADR 0009), их сессия группы тоже не читает.
5. **Исполнитель группы** (поле `executor`, решение bj 2026-10-23): у каждой группы задано **логическое** имя
   исполнителя, конкретная модель - в таблице `executors` того же файла (в группах модель не зашита):
   - `self` - основная сессия (низкий риск остановки: `sg-authz`, `sg-privacy`, `sg-hardening`);
   - `child` - дочерняя сессия `claude -p --model <executors.child.model>` (по умолчанию работы по группам идут так),
     запускает основная (память `child-sessions-allowed`); для групп, где фильтр останавливает основную сессию
     (`sg-token`, `sg-session`, `sg-login`, `sg-injection`). Модель с низким фильтром сегодня - `claude-opus-4-8`:
     если по итогам первой сессии `sg-token` она не ловит блоки, вся генерация и тесты безопасности - на неё;
   - `human` - только человек (`sg-restricted`).
   Исполнитель - обход ограничения в рамках изоляции, не повторение остановленного фрагмента.
6. **Модель не зашита, предусмотрены другие семейства Claude и сторонние/локальные LLM** (решение bj 2026-10-23):
   доступные модели меняются (4.8 когда-нибудь выведут, «более старой» станет модель с фильтром, например 5.5). Тогда
   правится только `executors.child.model`. Модель с низким фильтром может быть и другого семейства Claude - Sonnet
   или Haiku, в том числе старой версии (`claude-sonnet-*`, `claude-haiku-*`): их перебираем первыми через тот же
   `claude -p --model`. Только если подходящей модели Claude нет - группа идёт через `executors.external`: выгрузка
   `export_for_llm.py --group` во внешнюю/локальную модель без доступа к репозиторию (кандидаты
   `executors.external.targets`: локальный Qwen для простой рутины, затем ChatGPT и др.), ответ проверяет скрипт и
   подставляет дочерняя сессия (как сбор значений inj-a, ADR 0009). Остановка дочерней (`on_filter_stop: external`)
   ведёт туда же.
7. **Остановка фильтра в группе** - сказать пользователю, что сделано и что нет; тему - в стоп-темы, записи - под
   флаг (решение человека); остальные группы продолжаются.

## Альтернативы

- Одна сессия на модуль (как было) - остановка обрывает всё, контекст держит все темы сразу.
- Группы папками коллекции - конфликтует с ADR [0010](0010-collection-per-contract.md) (тест лежит в папке своей
  ручки); метка в метаданных выбирает тесты не хуже и не меняет дерево.
- Ставить группу руками в каждой записи - 290 записей, расходится при правке правил; явное поле оставлено для
  исключений.

## Последствия

- Больше сессий: на модуль с проверками безопасности - до 7 сессий на этап; зато каждая короче и остановка теряет
  одну группу.
- Тест нескольких групп попадает в отчёт каждой группы, его падение разбирают обе сессии - баг заводит первая,
  вторая находит дубль.
- Совпадения с багами чужих групп и закрытыми багами сравнивает человек.
- Метки `sg-...` появляются в метаданных тестов после `autotest.py meta`; прогоны до этого делятся по текущей
  коллекции (с предупреждением).
