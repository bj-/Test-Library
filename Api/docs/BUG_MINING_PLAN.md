# План: пополнение библиотеки идеями из открытых баг-трекеров

_2026-10-13. Решения — в ADR [0004](../../docs/decisions/0004-bug-tracker-mining.md)._

## Цель и что считаем результатом

Расширить библиотеку проверками, основанными на **реальных дефектах**, найденных тестировщиками и пользователями
чужих API-продуктов. Результат — не выгрузка тысяч багов, а:

1. **Новые записи в `checks/`**: паттерны дефектов, которых в библиотеке нет.
2. **Подкрепление существующих записей**: если паттерн уже есть, запись получает пруф (метку и ссылку на
   трассировку, см. ниже) и новые `test_variants`/`expected`, если баг показывает неучтённый вариант. Число
   подтверждающих багов служит аргументом для `risk.likelihood`.
3. **Карта пробелов**: по каким категориям таксономии реальных багов много, а проверок мало.

Ориентир на первую итерацию — после пилота **+50–100 новых записей и +100–200 подтверждений** у существующих.
Реальные цифры даст пилот.

## Главные принципы

- **Паттерн, а не баг.** Из бага извлекаем абстракцию «условие → действие → ожидание → что ломалось», без
  привязки к продукту. Пример: «элемент удалён между запросами страниц → пагинация пропускает или дублирует запись».
- **В библиотеку — только то, что видно снаружи через API.** Библиотека описывает black-box проверки API. Баги
  сборки, интерфейса, утечки памяти и прочее без внешнего проявления в библиотеку сейчас не идут, но **не
  выбрасываются**: на триаже они получают класс и сохраняются в отдельную корзину (см. «Развитие»).
- **Фикс-PR с тестом ценнее текста issue.** В тесте видны точный сценарий и ожидание. Берём diff тестовых файлов.
- **Пруф без шума.** Происхождение идеи в обычной работе не важно, но на вопрос «да как такое возможно?» должен
  быть ответ. В записи — только метка и ID трассировки; источники — в отдельном файле (см. «Трассировка»).
- **Человек утверждает.** LLM сортирует, абстрагирует и сопоставляет. В `checks/` кандидат попадает как `draft`,
  статус `approved` ставит только человек (так же, как для `checks/generated/`).
- **Сырые данные — вне git.** Тексты чужих issue не коммитим (объём, лицензии, ToS). В git попадают конфиг
  источников, скрипты, промпты, кандидаты и трассировка (ссылки и краткая суть, без копий текстов).

## Конвейер

```
sources.yaml → [1 сбор] → raw/*.jsonl → [2 фильтр] → [3 триаж] → [4 абстракция]
   → [5 сопоставление с библиотекой] → [6 кластеризация] → ideas/mined/<batch>.md → [7 ревью человеком]
   → checks/** (draft → approved) + traceability/real-world-bugs.yaml
```

| Шаг | Что делает | Вход → выход | Кто выполняет |
|---|---|---|---|
| 1. Сбор | Закрытые баги по меткам и ключевым словам, связанный PR, имена и diff тестовых файлов | `sources.yaml` → `build/mining/raw/<source>.jsonl` | Python: `gh api graphql`, JIRA REST (JQL), Launchpad API, GitLab API, GHSA API |
| 2. Фильтр | Только fixed или со смёрженным PR; без question/feature/docs; дедуп по URL; обрезка длинных тел | raw → `filtered.jsonl` | Python, без LLM |
| 3. Триаж | «Дефект поведения API, видимый снаружи?» да/нет; для «нет» — класс (`build`, `ui`, `memory`, `perf-internal`, `docs`, `framework-internal`, `usage`, `insufficient-data`, `client-lib`, `other`) | filtered → `triaged.jsonl`, `out-of-scope.jsonl` | Claude Code, партиями |
| 4. Абстракция | Паттерн: условие, действие, ожидание, фактическое поведение, протокол, `category` и `tags` из таксономии, OWASP API / CWE, источник ожидания (RFC, стандарт, здравый смысл) | triaged → `patterns.jsonl` | Claude Code, партиями |
| 5. Сопоставление | Ближайшая существующая запись: `covered` (только пруф), `extends` (новый вариант к записи X), `new` | patterns + `docs/CATALOG.md` → `matched.jsonl` | Claude Code, партиями |
| 6. Кластеризация | Склейка `new`-паттернов в уникальные идеи, подсчёт подтверждающих багов | matched → `Api/ideas/mined/<batch>.md` | Claude Code + ручная проверка |
| 7. Ревью | Человек принимает идею (новая запись `draft`), дополняет существующую или отклоняет с причиной; принятым назначаются ID трассировки. Пруфы к существующим записям (`covered`/`extends`) принимаются списком | candidates → `checks/**`, `traceability/` | человек, затем `assign_profiles` / `validate_library` / `build_catalog` |

Каждый шаг идемпотентен и хранит результат по ID бага, поэтому прерванную партию можно продолжить с того же места,
а повторный запуск не расходует лимит заново. Инкрементальное обновление делается по дате закрытия, начиная с
последней выгрузки.

## LLM и бюджет лимита

- Шаги 3–6 выполняет **Claude Code партиями**, без отдельного ключа Claude API. Скрипты шагов 1–2 и сборка
  промптов и результатов — Python; LLM получает готовую партию (jsonl) и пишет ответ в файл заданного формата.
- **Лимит: не больше 5 % недельного лимита Claude в день** на всю работу по выгрузке (на все машины вместе).
- Claude не видит свой недельный лимит напрямую, поэтому работаем так:
  1. **Калибровка.** Перед первой партией человек смотрит `/usage`, затем прогоняется пробная партия на 20 багов,
     и человек снова смотрит `/usage`. Отсюда — «% недельного лимита на 100 багов» для каждого шага.
  2. **Дневная норма** = 5 % / (расход на 1 баг) с запасом 20 %. Размер партии подбирается под норму.
  3. **Журнал расхода** — `Api/mining/budget.md` (в git, чтобы видели все машины): дата, машина, шаг, партия,
     число багов, `/usage` до и после. Перед партией Claude проверяет сумму за сегодня и не начинает партию, если
     она не уложится в норму.
  4. Перекалибровка — при смене модели или промптов, а также если фактический расход отклонился от расчётного
     больше чем на 30 %.
- Экономия: триаж (шаг 3) — более лёгкой моделью; в промпт идут только обрезанные тексты и нужная часть
  таксономии или каталога.

## Трассировка на источники

- **Метка `real-world-bug`** в `taxonomy/tags.yaml` (новая группа `origin`). Ставится записи, если идея основана
  на реальном баге или подтверждена им.
- **ID трассировки в `references`**: `Real-world bug: RWB-0001` (в духе существующих `Contract: …`). У записи
  может быть несколько ID.
- **Файл трассировки** `Api/traceability/real-world-bugs.yaml`. Обычные инструменты (`select_checks`,
  `build_catalog`, генераторы) его не читают; он нужен, только чтобы найти пруфы для руководства. Запись:

  ```yaml
  RWB-0001:
    pattern: Пагинация пропускает запись, удалённую между запросами страниц
    checks: [REST-PAGINATION-STABLE-ORDER]
    batch: pilot
    bugs:
      - url: https://github.com/<org>/<repo>/issues/123
        fix: https://github.com/<org>/<repo>/pull/456
        product: <продукт>
        closed: 2025-03-01
        summary: Краткая суть своими словами (без копии текста issue)
  ```
- `validate_library.py` получает одну дополнительную проверку: каждый `RWB-*` из `references` существует в файле
  трассировки, а у записи с таким ID стоит метка `real-world-bug`.

### Пруфы для уже реализованных идей

Если найденный баг совпал с записью, которая уже есть в библиотеке (`covered` или `extends`), запись **обновляется
и получает пруф**, даже если её идея придумана без реальных багов:

1. В записи ставится метка `real-world-bug` и в `references` добавляется `Real-world bug: RWB-NNNN`.
2. Если у записи уже есть `RWB-*` с тем же паттерном, новый баг дописывается в `bugs` этого RWB, а не создаёт
   новый ID.
3. Статус записи не меняется: `approved` остаётся `approved`. Для `extends` дополнительно добавляется вариант
   в `test_variants` или `expected`.
4. В `ideas/mined/<batch>.md` такие совпадения идут отдельным разделом «Пруфы к существующим» (запись, RWB,
   баг, почему совпадает). Человек просматривает список и принимает его целиком или вычёркивает неверные
   совпадения, после чего пруфы применяются скриптом `apply_proofs.py`.

Ещё одна метрика — **доля записей библиотеки с пруфами**, по категориям: она показывает, какие идеи пока держатся
только на теории.

## Источники

### Пилот: под наш стек

Наши продукты — BFF на NestJS/Express (формат ошибок `statusCode/message/error`, `Cannot GET`), cookie-сессии,
мобильный API со входом по коду.

| Источник | Почему | Фильтр |
|---|---|---|
| `nestjs/nest`, `expressjs/express`, `expressjs/body-parser`, `expressjs/session`, `jshttp/cookie` | Парсинг тел, cookie, сессии, коды ошибок: прямо наши находки (BUG-BFF-0002…0008) | closed + label bug, связанный PR |
| `keycloak/keycloak` | Аутентификация, токены, сессии, logout, brute-force detection | label `kind/bug`, area `authentication`/`oidc` |
| `strapi/strapi`, `directus/directus` | Node-продукты, где API и есть продукт: фильтры, пагинация, права, mass assignment | closed bug + PR |
| GitHub Security Advisories, ecosystem npm | Уязвимости с CWE: BOLA, mass assignment, prototype pollution, ReDoS, SSRF | `ecosystem:npm`, CWE из списка OWASP API Top 10 |

Объём пилота — **300–500 багов** после фильтра.

### Масштабирование (после пилота, по выходу идей на источник)

- GitHub, продукты-API: Kubernetes (`kind/bug` + `area/apiserver`), GitLab (`type::bug` + `api`), Grafana,
  Mattermost, Supabase/PostgREST, Hasura, Appwrite, Kong, Traefik.
- Фреймворки: FastAPI, Django REST Framework, Spring Framework/Boot (web, security).
- Apache JIRA: Kafka REST, CXF, Camel, Solr (JQL `type = Bug AND resolution = Fixed AND text ~ "REST"`).
- Launchpad: OpenStack Nova/Keystone/Neutron (пагинация, квоты, микроверсии).
- gRPC: `grpc/grpc-*`, `grpc-gateway` — для раздела `checks/grpc/` (сейчас 33 записи).
- GraphQL: `graphql-js`, Apollo Server, Hasura — для раздела `checks/graphql/` (10 записей).
- HackerOne Hacktivity: только вручную или через официальный API в рамках ToS, без скрейпинга; для логики
  авторизации.

## Метрики пилота

- **Выход идей:** сколько уникальных `new`-паттернов приходится на 100 собранных багов по каждому источнику.
  По этому показателю решаем, какие источники масштабировать.
- **Точность триажа и абстракции:** доля верных решений LLM на ручной выборке.
- **Доля принятых на ревью:** `new` → `draft` / всего кандидатов.
- **Покрытие пруфами:** сколько существующих записей получили пруфы; доля записей с `real-world-bug` по категориям.
- **Распределение по категориям:** где больше всего реальных багов и где у нас меньше всего записей.
- **Стоимость:** % недельного лимита на 100 багов, по шагам.
- **Корзина вне области:** сколько багов и какого класса (`build`, `ui`, `memory`, …) отложено.

## Риски

| Риск | Мера |
|---|---|
| Шум: вопросы, фичи, документация | Жёсткий фильтр (fixed + PR) и триаж «виден ли снаружи через API» |
| Банальные идеи, которые уже есть в библиотеке | Шаг 5 превращает их в пруфы существующих записей, и это тоже полезный результат |
| Галлюцинации LLM в абстракции | У каждого паттерна ссылка на баг; на ревью человек сверяет с исходником; промпт запрещает додумывать ожидание без источника |
| Перерасход лимита Claude | Калибровка, дневная норма 5 %, журнал `budget.md`, проверка перед каждой партией |
| Перегрузка серверов источников, бан | Бережная нагрузка (`politeness` в `mining/sources.yaml`): только последовательные запросы с паузой, резерв 20 % лимита, соблюдение `Retry-After`, нарастающая пауза на 403/429/5xx, кэш без повторных скачиваний, `User-Agent` проекта (`mining/README.md`) |
| ToS и лицензии | Храним абстракции, ссылки и краткую суть своими словами; сырьё не коммитим; HackerOne только по ToS |
| Утечка внутренних данных | В промпты идут только публичные баги и наша таксономия, без наших контрактов и кредов |

## Развитие: что пока отбрасываем, но сохраняем

Сейчас в библиотеку не идут дефекты, которые нельзя проверить black-box запросами к API:

| Класс | Примеры | Что нужно, чтобы контролировать |
|---|---|---|
| `build` | Сборка, зависимости, упаковка, совместимость версий рантайма | Проверки артефакта и пайплайна сборки (SBOM, `npm audit`, версии рантайма в образе) |
| `ui` | Отрисовка, вёрстка, поведение клиента | UI-автотесты (Playwright и т. п.) — отдельная библиотека или раздел |
| `memory` | Утечки памяти, рост дескрипторов и соединений | Длительные прогоны с метриками процесса (RSS, heap, fd, пул соединений) — доступ к мониторингу стенда |
| `perf-internal` | Деградация без внешнего проявления в одном запросе | Нагрузочные и soak-прогоны с метриками (`postman performance run`, Prometheus) |

Такие баги не выбрасываются: на триаже они получают класс и сохраняются в
`build/mining/<batch>/out-of-scope.jsonl`, а их число по классам попадает в `REPORT.md`. Когда появится
возможность контролировать класс (доступ к метрикам стенда, UI-тесты, проверки сборки), корзину можно разобрать
тем же конвейером (шаги 4–7) без повторной выгрузки. Раздел библиотеки под такие проверки (`kind`, профили,
требования к инфраструктуре) нужно будет спроектировать отдельно. Идея записана в `docs/ideas.md`.
