# Руководство по организации процесса автоматизированного тестирования и управления качеством

> **Важное примечание для модели-исполнителя:**  
> Настоящий документ **не является строгим техническим заданием** или списком договорённостей. Это структурированное описание идей, рекомендаций и предложений по построению системы генерации, хранения и выполнения тестов, а также сопутствующих процессов. При реализации допускается и приветствуется расширение, уточнение и улучшение описанных подходов. Все формулировки следует рассматривать как руководство к действию, а не как жёсткие ограничения. Приоритет – достижение целей, указанных ниже, с использованием наиболее эффективных решений.

---

## 1. Цели и побочные цели

**Основная цель:** полностью исключить человека из процесса тестирования (стремление к полностью автоматическому циклу: генерация тестов → запуск → анализ → заведение багов → предложение фиксов).

**Побочная цель:** исключить разработчика из процесса рассмотрения и фиксации багов или, как минимум, подготавливать исчерпывающую документацию по обнаруженным проблемам, достаточную для автоматической или полуавтоматической обработки агентами.

---

## 2. Исходные данные и контекст

- **Библиотека тестов** – приложена к проекту (доступна локально и по ссылке: https://github.com/bj-/Test-Library). Тесно взаимодействует с фреймворком https://github.com/bj-/PostmanScripts/, который выполняет проверки.
- **Проект с модулями** – произвольное количество модулей, которые могут взаимодействовать между собой (требуются E2E-тесты).
- **Документация** – может включать:
  - ФТТ (Функциональные технические требования) – исходные требования заказчика;
  - ОТЗ (Общее техническое задание) – переработанные требования;
  - ЧТЗ (Частные технические требования) – детализация по модулям;
  - ПМИ (Программа и методика испытаний);
  - ПСИ (Приёмо-сдаточные испытания) и протоколы.
  - Названия и структура документов могут различаться; необходимо автоматически определять категорию документа (исходный, переработанный, требования к проекту/модулю).
- **Способы запуска тестов:**
  - вручную;
  - автоматически по команде;
  - из пайплайна (CI/CD):
    - приёмочные тесты после сборки;
    - регрессия после сборки с несколькими модулями;
    - общее регрессионное тестирование при выходе билда на общее тестирование, при переходе на Stage и Prod.
- **Виды тестов** (список может быть расширен):
  - API: REST, gRPC, SOAP;
  - UI: Mobile, Web, Desktop;
  - Нефункциональные: нагрузка, стабильность (высокая нагрузка, длительная работа);
  - Безопасность / pentest.

## 3. Общая архитектура решения

Предлагается построить систему, состоящую из следующих компонентов:

1. **Генератор тестов** – на основе документации, исходного кода и библиотеки тестов создаёт тестовые сценарии, коллекции Postman и другие артефакты. Должен уметь запрашивать у пользователя недостающие доступы (БД, серверы, исходный код) на этапе генерации.
2. **Хранилище тестов** – структурированный репозиторий (Git) с тестами, организованными по требованиям и модулям.
3. **Оркестратор запуска** – управляет запуском тестов (вручную, по команде, из пайплайна), конфигурирует стенды, переменные окружения.
4. **Анализатор результатов** – обрабатывает отчёты, выявляет баги, проверяет на дубли, формирует описания для трекера.
5. **Интеграция с трекером** – автоматическое создание/обновление багов в Jira, Youtrack, Redmine, Git и др.
6. **Хранилище артефактов** – отчёты, срезы продукта, логи, скриншоты, локальные копии багов.
7. **База знаний идей** – каталог идей тестирования с ID, описанием, ссылками на требования и сгенерированные тесты.

Все компоненты должны быть максимально автономны и управляться агентом (LLM).

## 4. Структура проекта для тестирования

Рекомендуется следующая структура каталогов (может быть адаптирована):

```
/project-testing/
├── docs/                     # Исходная документация
│   ├── initial/              # ФТТ и аналогичные исходные требования
│   ├── processed/            # ОТЗ и переработанные требования
│   ├── modules/              # ЧТЗ по модулям
│   ├── pmi/                  # ПМИ
│   └── psi/                  # ПСИ и протоколы
├── tests/                    # Сгенерированные тесты
│   ├── by_requirements/      # Тесты, привязанные к пунктам требований
│   │   ├── <document_name>/  # Например, ОТЗ_раздел_1
│   │   │   ├── test_001.md   # Описание теста + ссылка на требование
│   │   │   └── ...
│   │   └── ...
│   ├── by_modules/           # Тесты по модулям
│   │   ├── module_A/
│   │   └── module_B/
│   ├── e2e/                  # End-to-End тесты
│   ├── nonfunctional/        # Нагрузка, стабильность, безопасность
│   └── postman_collections/  # Коллекции Postman по ручкам
├── config/                   # Конфигурации стендов, доступы (секреты – в защищённом хранилище)
├── reports/                  # Отчёты о запусках
│   ├── <date>_<run_id>/
│   │   ├── report.md
│   │   ├── allure/
│   │   └── logs/
├── artifacts/                # Срезы продукта, артефакты тестирования
│   ├── builds/               # Срезы тестируемого продукта на момент генерации/запуска
│   └── test_data/
├── bugs/                     # Локальные копии багов (если трекер недоступен)
└── ideas/                    # База идей тестирования (ID, описание, ссылки)
```

**Принципы организации тестов:**
- Каждый тест должен иметь описание: что проверяется, зачем, как, почему выбран такой подход.
- Обязательная обратная ссылка на ID идеи и на пункт требования (или сценарий).
- Для API-тестов – коллекции Postman, хранимые в Git, с возможностью точечного запуска.
- Структура тестов должна повторять структуру документации, чтобы при ПСИ/проверке соответствия можно было легко найти нужный тест.

## 5. Процесс генерации тестов

1. **Анализ документации:** автоматически определять тип документа (ФТТ, ОТЗ, ЧТЗ, ПМИ, ПСИ) и извлекать требования. Для каждого требования создавать запись в базе идей.
2. **Анализ исходного кода (при наличии доступа):** выявлять эндпоинты, модули, зависимости для генерации API- и E2E-тестов.
3. **Использование библиотеки тестов:** применять существующие шаблоны и проверки из Test-Library и PostmanScripts, расширяя их при необходимости.
4. **Генерация тестовых сценариев:**
   - для каждого требования – минимум один тест (позитивный и, где применимо, негативный);
   - для каждой ручки API – коллекция Postman с проверками;
   - для модулей – интеграционные тесты;
   - для взаимодействия модулей – E2E-тесты;
   - нефункциональные тесты – по необходимости (нагрузка, безопасность).
5. **Запрос доступов:** если для теста нужны БД, сервер, исходный код или другие ресурсы, агент должен сформулировать запрос пользователю ещё на этапе генерации. Полученные данные включаются в конфигурацию стенда и в описание теста.
6. **Документирование теста:** в описании указывать ID идеи, ссылку на требование, что и как проверяется, ожидаемый результат.

---

## 6. Запуск тестов и отчётность

**Способы запуска:**
- Ручной (через интерфейс или команду).
- Автоматический по триггеру (например, webhook).
- Из пайплайна CI/CD (приёмочные, регрессионные, общие).

**Хранение отчётов:**
- Основные форматы: `.md` (читаемый текст) и Allure (детальные результаты).
- Дополнительно: JUnit XML, HTML-отчёты для интеграции с CI.
- Все отчёты сохраняются в `/reports/<date>_<run_id>/` с метаданными: список запущенных тестов, окружение, срез продукта, ссылки на баги.
- Для каждого запуска сохраняется срез тестируемого продукта (хеш коммита, версия сборки) в `/artifacts/builds/`.

**Анализ результатов:**
- Автоматическое сравнение с предыдущими запусками для выявления новых падений.
- Классификация ошибок (функциональные, инфраструктурные, нестабильные тесты).
- Формирование выжимки для заведения багов.

## 7. Управление багами

**Интеграция с трекерами:** Jira, Youtrack, Redmine, Git (Issues) и др. – в зависимости от используемой в компании/команде системы.

**Автоматическое заведение бага:**
- Поиск дублей: перед созданием нового бага проверять существующие в трекере и в локальной базе ранее найденных багов (по тексту ошибки, стеку, тесту).
- Если баг уже существует – добавлять комментарий с ссылкой на новый прогон и тест, подтверждающий воспроизведение.
- В описание бага включать:
  - ссылку на прогон и тест;
  - ID идеи и описание того, что, зачем и как тестировали;
  - шаги воспроизведения, ожидаемый и фактический результат;
  - вложения (логи, скриншоты, отчёты);
  - при наличии доступа к исходному коду – предложение по исправлению (патч или описание).

**Локальное хранение:** если трекер недоступен, сохранять баги в `/bugs/` в структурированном виде (JSON + Markdown) с возможностью последующей синхронизации.

## 8. Дополнительные идеи по улучшению

- **Автоматическое определение необходимых доступов:** на основе анализа тестов и документации агент формирует список требуемых ресурсов (БД, URL стендов, учётные данные) и запрашивает их у пользователя.
- **Использование AI для анализа кода:** для генерации более точных тестов и предложений по исправлению багов.
- **Тестовые срезы (test slices):** формирование минимального набора тестов для быстрой проверки конкретного изменения (например, по затронутым модулям).
- **Метрики качества:** отслеживание покрытия требований тестами, количества найденных/исправленных багов, стабильности тестов.
- **Самообучение системы:** накопление статистики по эффективности идей и тестов, автоматическая корректировка приоритетов.
- **Интеграция с системами мониторинга:** автоматическое создание багов на основе алертов из production.
- **Поддержка версионирования тестов:** при изменении требований – автоматическое обновление связанных тестов с сохранением истории.

---

## 9. Заключение

Предложенная организация процесса направлена на создание самоуправляемой системы тестирования, минимизирующей участие человека. Документ носит рекомендательный характер: модель-исполнитель может расширять структуру, добавлять новые компоненты и оптимизировать процессы, руководствуясь целями и здравым смыслом. Главное – обеспечить прослеживаемость требований, автоматическую генерацию и выполнение тестов, а также исчерпывающую документацию для автоматического устранения дефектов.
