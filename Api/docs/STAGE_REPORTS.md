# 3. Отчёты по этапам

Дата фиксации состояния архива: 2026-10-09. Цифры ниже относятся к содержимому предоставленного архива и локальным запускам; они не означают выполнение тестов против целевого API.

## Этап 1 — базовая библиотека и схема

**Результат:** структура `schema/`, `taxonomy/`, `checks/`, `profiles/`, `selection-rules/`, `validation/` и скрипт `tools/validate_library.py`.

**Текущее подтверждение:** встроенный валидатор запускается с JSON Schema; итоговая проверка текущего архива показывает 152 записи, 152 уникальных ID, 6 профилей и 0 ошибок.

**Ограничение:** успешная структурная валидация не доказывает корректность ожиданий или готовность сценария к исполнению.

## Этап 2 — расширение REST-каталога

**Результат:** каталог типовых REST-проверок и документация `REST_CATALOG.md`, `REST_EXPANSION_COMPATIBILITY.md`, `VALIDATION_REPORT_REST_EXPANSION.md`.

**Зафиксированный результат интеграции:** в отчёте этапа расширения указано 57 добавленных шаблонов; библиотека после интеграции — 71 проверка без ошибок встроенного валидатора. В актуальном архиве далее добавлены дополнительные проверки, поэтому общий текущий счётчик выше.

**Выявленные проблемы:** исходный формат требовал адаптации к верхнеуровневому `checks`, элементы `steps` должны быть объектами с `action`, поле `status: draft` не разрешалось схемой, часть категорий/тегов отсутствовала в текущей таксономии. Семантические отображения описаны и требуют согласования.

## Этап 3 — модель и проверки безопасности

**Результат:** `SECURITY_ACCESS_CONTROL_MATRIX.md`, `SECURITY_PROFILE_SELECTION.md`, `SECURITY_STAGE3_VALIDATION.md` и дополнительные security checks.

**Подход:** раздельно рассматриваются аутентификация, авторизация, владение ресурсом, изоляция tenant и роли/scopes. Для запрещённых мутаций проверяется отсутствие изменения состояния. Профили выбирают проверки по назначению и риску, а не по одной лишь positive/negative-метке.

**Ограничение:** статус-коды и точная политика отказа должны задаваться контрактом/политикой API.

## Этап 4 — генератор кандидатов

**Результат:** `tools/generate_coverage.py`, матрица покрытия и отчёты в `build/coverage/`; инструкция `COVERAGE_GENERATOR_STAGE4.md`.

**Проверка на синтетическом примере:** в `STAGE4_VALIDATION.md` зафиксировано 3 найденных операции, 17 сгенерированных кандидатов, 17 уникальных ID, 0 ошибок JSON Schema, 0 неизвестных тегов/профилей, 0 неразрешённых вопросов и 0 противоречий.

**Ограничение:** это smoke-проверка генератора на примере, а не проверка работающего сервиса.

## Этап 5 — анализ контрактов проекта

**Входы:** `examples/real-contracts/bff-admin-api.openapi.yaml`, `examples/real-contracts/mobile-client-api.openapi.yaml` и access models рядом с ними.

**Результат актуального отчёта:**

- 35 операций в двух контрактах;
- 48 сгенерированных кандидатов с уникальными ID;
- 66 пунктов, требующих уточнения;
- 20 операций BFF Admin API без явной security-декларации;
- 1 противоречие в описании/политике security.

**Ключевые находки:** для BFF Admin API отсутствие `security` в OpenAPI не доказывает ни публичность, ни защищённость операции. Для `onStart` пустая альтернатива security допускает анонимный доступ, тогда как описание говорит об отказе при отсутствующем/невалидном `api-key`. Требуется решение владельца API.

Подробности и список кандидатов: `build/real-contract-coverage/REAL_CONTRACT_COVERAGE_REPORT.md`, `operation_inventory.json`, `clarification_questions.json`.

```bash
python tools/validate_library.py .
```

```text

JSON Schema validation: enabled
Errors: 0
```

Отбор по профилю проверяется отдельно; он не заменяет проверку библиотеки:

```bash
python tools/select_checks.py . Smoke
python tools/select_checks.py . CI
python tools/select_checks.py . Regression
```
