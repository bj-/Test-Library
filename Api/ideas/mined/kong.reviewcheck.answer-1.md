## Разбить, объединить, исключить

- **Идея 2:** сузить текущую запись до `Host` с явным портом. `Content-Type` и `Content-Length` не подтверждены данным багом и, если нужны, должны быть отдельными проверками с собственными источниками ожиданий.
- **Идея 3:** не принимать в общем API-каталоге; при наличии отдельного профиля для API gateways можно сохранить как проверку совместимости заголовков с middleware/plugin lifecycle.
- **Идея 4:** не объединять с №8: первая — приоритет/наследование конфигурации, вторая — применимость критериев маршрутизации к протоколу. В шаблоне №4 отделить подтверждённое issue переопределение route-level от расширения про удаление и fallback.
- **Идея 9:** держать отдельно от `HTTP-REQUEST-SMUGGLING`, потому что направление сообщения принципиально важно: request framing и response framing — разные проверяемые риски.
- **Идея 10:** не склеивать с `SEC-AUTHN-MALFORMED`: валидные credentials со спецсимволами — позитивная проверка разбора, malformed credentials — негативная.
- **Не про обычный внешний API в строгом смысле:** №3 (внутренний plugin hook/response lifecycle) и №11 (worker/process model). №7 также требует доступа к логам/телеметрии, поэтому это API + observability, а не только проверка HTTP-ответа.

## Общий вывод

Главный риск кластеризации — смешение универсального HTTP/API-инварианта с особенностями внутренней архитектуры Kong (№3 и №11), а также объединение нескольких независимых заголовочных свойств в одной идее (№2). Большинство остальных паттернов можно сохранить как отдельные правила генерации проверок, если явно описать наблюдаемый результат, необходимые стендовые условия и источник ожидаемого поведения.
