# 1\. Открытая библиотека и платный генератор

## 1.1. Как разделить продукт

## Open Test Knowledge Base

Публичная часть

- Базовые тестовые сценарии и шаблоны.
- Таксономия уязвимостей и техник проверки.
- Открытые схемы, форматы, правила и метаданные.
- Примеры использования и контрибьюторская модель.

API, поиск, версионирование, адаптация

## Paid Generation Engine

Коммерческая часть

- Анализ OpenAPI и фактического поведения API.
- Поиск релевантных знаний под конкретную ручку.
- Планирование покрытия и генерация новых сценариев.
- LLM-адаптация, валидация и устранение дубликатов.
- Формирование готового прогона и отчёта.

## Test Runner

Исполнение

- HTTP-запросы, подготовка данных и последовательности.
- Проверки статусов, схем, инвариантов и бизнес-правил.
- Сбор результатов, доказательств и метрик покрытия.

Я бы предусмотрел и самостоятельное использование открытой библиотеки: разработчик может скачать её и запускать доступные сценарии. Это полезно для распространения продукта и привлечения контрибьюторов.

Но платный генератор должен предоставлять ценность, которую библиотека сама по себе не даёт: контекстный подбор, планирование покрытия, адаптацию под контракт, новые сценарии, проверку исполнимости и оптимизацию прогона.

## 1.2. Можно ли запретить локальное копирование библиотеки?

**Если библиотека публично доступна в виде скачиваемых файлов, гарантировать невозможность её локального копирования нельзя.** Лицензия может регулировать использование и распространение, но не может технически предотвратить копирование доступных данных.

Есть три варианта.

| Модель | Что получает пользователь | Защита коммерческой ценности |
|--------|--------|--------|
| Полностью открытая библиотека | Все файлы и сценарии | Генератор, сервис, интеграции, обновления |
| Открытое ядро + закрытые дополнения | Базовые знания; премиальные наборы доступны через сервис | Закрытые данные и алгоритмы остаются на сервере |
| Публичный API без выгрузки полного корпуса | Запросы к знаниям и результаты подбора | Серверный корпус, квоты, авторизация, контроль массового извлечения |

Для твоей задачи я бы выбрал **гибридную модель**\:

- Открыть базовую библиотеку, форматы, таксономию и часть сценариев.
- Хранить расширенные знания, премиальные сценарии и внутренние связи на сервере.
- Предоставлять через API только необходимые для текущей задачи фрагменты.
- Монетизировать генерацию, а не просто выдачу результатов поиска.
- Добавить платные возможности для команд: история прогонов, регрессионное тестирование, интеграции, аудит покрытия и управление политиками.

Здесь есть важный нюанс: даже если API возвращает только нужные фрагменты, клиент может постепенно собрать значительную часть корпуса. Поэтому нужны ограничения частоты, квоты, обнаружение массового извлечения и разделение открытых и закрытых данных. Но это повышает стоимость извлечения, а не делает его невозможным.

Если принципиально важно не отдавать ценные знания пользователю, держать их нужно на сервере и возвращать только результат их применения - насколько это позволяет задача.

## 1.3. Web + API - как я бы организовал доступ к библиотеке

Да, это перспективная модель. Но я бы не делал API простым прокси, который возвращает содержимое файлов. Нужен **сервис знаний для генерации тестов**\.

**1\. API клиента**

OpenAPI, описание API, ограничения доступа, известные роли, бизнес-контекст, цель тестирования.

---

**2\. Retrieval / Knowledge API**

Находит применимые тестовые идеи, техники, шаблоны, предусловия, требования к доказательствам и зависимости.

---

**3\. Генератор**

LLM превращает найденные знания в конкретные сценарии под выбранные endpoint'ы.

---

**4\. Проверка и сборка**

Скрипты проверяют схему, обязательные поля, зависимости, безопасность исполнения и полноту покрытия.

---

**5\. Результат**

Исполнимый прогон, карта покрытия, объяснение выбора проверок и отчёт с доказательствами.

### Какие API нужны в первой версии

Я бы разделил интерфейсы на четыре группы\:

| Интерфейс | Назначение |
|--------|--------|
| `POST /v1/knowledge/search` | Найти знания по endpoint, параметрам, операциям и классам риска |
| `POST /v1/knowledge/resolve` | Получить полные данные выбранных элементов по ID |
| `POST /v1/plans` | Создать план тестирования с заданными целями и ограничениями |
| `POST /v1/generations` | Запустить генерацию и получить идентификатор задачи |

Позже можно добавить версионирование корпуса, получение отчётов, управление проектами, оценку качества сценариев и обратную связь о результатах исполнения.

Ключевой принцип: поиск возвращает короткие карточки знаний, а полное содержимое загружается только для отобранных элементов. При этом каждый элемент должен иметь стабильный ID, версию, происхождение и связи с другими элементами.

## 1.4. Может ли библиотека генерировать тесты только скриптами?

**Да, но нужно разделить генерацию сценариев и генерацию тестовой логики.** Скриптовый движок способен построить значительную часть прогона без LLM, если знания библиотеки структурированы.

Например, библиотека может содержать декларативный шаблон проверки авторизации\:

```yaml
id: authorization.missing_credentials
applies_to:
  - authenticated_endpoint

setup:
  identity: valid_user

mutation:
  credentials: remove

assertions:
  - response.status_in: [401, 403]
  - response.does_not_leak_sensitive_data: true
```

Это иллюстративный формат, а не окончательная схема библиотеки. Реальная проверка должна учитывать контракт конкретного API: например, некоторые публичные ручки закономерно работают без авторизации.

Движок может автоматически\:

- определить, какие шаблоны подходят к ручке;
- создать варианты запросов;
- подставить валидные и граничные значения;
- выполнить HTTP-запросы;
- проверить статусы, схемы и заданные инварианты;
- объединить результаты и сформировать отчёт;
- вычислить покрытие по классам проверок.

Однако не все задачи сводятся к шаблонам.

| Задача | Скрипты | LLM |
|--------|--------|--------|
| Подстановка параметров и генерация граничных значений | Отлично | Обычно не нужна |
| Проверка статусов, схем и инвариантов | Отлично | Не нужна |
| Выбор подходящего шаблона по структурированным признакам | Отлично | Не обязательна |
| Выявление неочевидных рисков в описании API | Ограниченно | Полезна |
| Вывод вероятных бизнес-правил из документации | Ограниченно | Полезна |
| Создание сценария из нескольких зависимых операций | Возможно при формальных правилах | Полезна при неоднозначности |
| Придумывание новой проверки, отсутствующей в библиотеке | Только по заранее заданным алгоритмам | Особенно полезна |
| Проверка фактического результата запроса | Отлично для формализуемых утверждений | Нужна для сложной семантической оценки, но не всегда |

### Где именно нужна LLM

Я бы использовал LLM в трёх точках.

**1\. Анализ и планирование.** Модель интерпретирует API, находит неоднозначности, предлагает гипотезы рисков и выбирает цели проверки.

**2\. Адаптация знаний.** Модель превращает найденный шаблон в конкретный сценарий с нужными полями, предусловиями, последовательностью операций и ожидаемым поведением.

**3\. Исследование пробелов.** После построения первоначального плана модель анализирует непокрытые риски и предлагает дополнительные проверки, которых нет в готовых шаблонах.

Всё остальное по возможности нужно выполнять детерминированным кодом.

Это позволит сократить стоимость генерации, повысить воспроизводимость, проще отлаживать ошибки и измерять качество результата.

Особенно важно не отдавать модели право самостоятельно придумывать ожидаемый статус или считать предположение об авторизации доказанным фактом. Такие решения должны сопровождаться основанием: контрактом, явным правилом, известным поведением либо маркированной гипотезой.

# 2\. Как сократить контекст LLM и потребление токенов

Здесь я бы менял не столько способ хранения файлов, сколько сам процесс генерации.

**Хранить библиотеку в БД и отдавать нужные знания через API - правильное направление. Но одного переноса в БД недостаточно. Нужна система многоступенчатого отбора знаний, которая не загружает в контекст модели ничего лишнего.**

По структуре предоставленного архива уже видны артефакты, на которых можно строить такую систему: сгенерированные проверки, матрицы покрытия, отчёты и результаты обработки источников. Их необязательно каждый раз заново передавать LLM - многие из них можно использовать как данные для индексации, поиска и детерминированных проверок.

## 2.1. Главная идея: библиотека - это не контекст, а база знаний

Не стоит давать модели весь корпус и просить разобраться в нём. Лучше последовательно сужать задачу.

**Этап 1. Полная база знаний**

Все сценарии, идеи, техники, примеры, метаданные и связи. Хранятся на сервере, индексируются отдельно.

**Этап 2. Детерминированная фильтрация**

Метод HTTP, тип параметров, наличие авторизации, идентификаторы ресурсов, типы данных, поддерживаемые механизмы проверки.

**Этап 3. Ранжирование и подбор**

Поиск по метаданным, ключевым словам, семантической близости и связям между знаниями.

**Этап 4. Компактный контекст**

Модель получает описание конкретной операции, релевантные карточки знаний, выбранные полные шаблоны и правила формирования результата.

Такой процесс называют retrieval-augmented generation (RAG), но в данном случае я бы строил не просто RAG по документам, а **гибридный поиск по структурированной библиотеке тестовых знаний**\.

## 2.2. Что именно хранить в БД

Не рекомендую хранить библиотеку исключительно как большие текстовые документы или как набор векторных эмбеддингов. Лучше использовать несколько уровней данных.

| Сущность | Что хранит | Зачем |
|--------|--------|--------|
| `KnowledgeItem` | ID, тип, название, краткое описание, версия, происхождение | Каталог и управление знаниями |
| `ApplicabilityRule` | Условия применимости к API и ограничения | Быстрый отбор без LLM |
| `TestTemplate` | Структурированный сценарий или алгоритм проверки | Повторное использование |
| `PayloadTemplate` | Ссылка на данные для тестирования, тип и правила применения | Отделение тестовой логики от значений |
| `Dependency` | Связи между знаниями и обязательные предусловия | Сборка сложных сценариев |
| `Assertion` | Условия успешной проверки и способ получения доказательств | Воспроизводимая оценка результата |
| `CoverageMapping` | Связь сценариев с целями, рисками и классами проверок | Контроль полноты |
| `ExecutionEvidence` | Результаты прогонов, подтверждённые выводы, ограничения | Улучшение последующих генераций |

Не все сущности обязательно должны быть отдельными таблицами. Это логическая модель, которую можно реализовать в реляционной БД с JSON-полями для гибких структур.

Для начала достаточно PostgreSQL с JSONB и полнотекстовым поиском. Векторный поиск можно добавить, когда появятся реальные задачи, которые не удаётся решить фильтрами и текстовым поиском.

Важный принцип: **эмбеддинги помогают найти кандидатов, но не должны решать, применим ли тест технически**\. Для этого нужны формальные условия.

## 2.3. Как отбирать тесты для конкретной ручки

Предположим, генератор получает описание\:

`GET /projects/{projectId}`

Вместо загрузки всей библиотеки он формирует профиль операции\:

```json
{
  "method": "GET",
  "resource": "project",
  "path_parameters": ["projectId"],
  "authentication": "required",
  "resource_identifier": true,
  "security_goals": [
    "authentication",
    "authorization",
    "resource_ownership",
    "tenant_isolation"
  ]
}
```

Это условный пример: признаки авторизации и разделения арендаторов должны подтверждаться контрактом или конфигурацией проекта, а не выводиться только из имени ручки.

Далее система выполняет отбор\:

1. Фильтрует знания по типу операции и поддерживаемым условиям.
2. Находит проверки доступа, владения ресурсом и изоляции арендаторов.
3. Подтягивает обязательные предусловия: учётные записи, роли, объекты и отношения между ними.
4. Проверяет, какие сценарии уже существуют для аналогичных операций.
5. Добавляет небольшой набор смежных проверок, чтобы не упустить риски.
6. Передаёт LLM краткие карточки и полные описания только выбранных шаблонов.

Например, модель может получить 12 карточек по 50 токенов, а затем полное описание 4 выбранных шаблонов по 200 токенов. Это около 1 400 токенов на знания, не считая самого контракта, инструкций и формата ответа.

Это лишь иллюстрация, а не обещание конкретной экономии: фактический результат зависит от размера шаблонов, числа кандидатов и сложности операции.

### Почему нельзя просто брать топ-5 результатов поиска

Семантический поиск может вернуть пять почти одинаковых сценариев авторизации и пропустить проверку изоляции арендаторов.

Поэтому отбор должен учитывать не только релевантность, но и разнообразие покрытия.

Я бы использовал комбинированную стратегию\:

- **Обязательные проверки** - определяются правилами применимости.
- **Ранжируемые проверки** - выбираются поиском.
- **Проверки на разнообразие** - добавляются для непокрытых классов риска.
- **Дополнительные гипотезы LLM** - исследуют оставшиеся пробелы.

В итоге генератор оптимизирует не количество переданных шаблонов, а качество покрытия при заданном бюджете токенов.

## 2.4. Не загружать все знания сразу: двухпроходная генерация

Я бы особенно рекомендовал разделить планирование и детализацию.

(Проход 1) **Планирование**

LLM получает\:

- контракт API и краткое описание проекта;
- компактные карточки найденных знаний;
- цели тестирования и ограничения;
- карту уже покрытых рисков.

Результат: план проверок, список необходимых шаблонов и выявленные пробелы.

(Проход 2) **Генерация**

Для каждого выбранного набора проверок подгружаются\:

- полные шаблоны;
- только необходимые зависимости;
- применимые правила и ограничения;
- требования к формату результата.

Результат: конкретные исполнимые сценарии.

**Детерминированная проверка**

Сценарии валидируются, дубликаты удаляются, покрытие пересчитывается. Если обнаружены пробелы, повторяется только нужный этап, а не вся генерация.

Для крупных API можно пойти ещё дальше: сначала классифицировать все операции, затем строить планы для групп однотипных ручек, а после - детализировать только уникальные случаи.

Например, если 30 ручек используют один и тот же механизм авторизации, не нужно заново генерировать всю логику проверки авторизации для каждой из них. Достаточно одного переиспользуемого алгоритма и индивидуальной конфигурации для каждой операции.

# 3\. Дополнительные способы сократить расходы

Кроме переноса библиотеки в БД, я бы внедрил следующие оптимизации.

**1\. Краткие карточки знаний**

Для поиска хранить компактное представление: ID, назначение, условия применимости, тип проверки, риски и ссылки на зависимости. Полное описание передавать только после выбора.

**2\. Повторное использование шаблонов**

Генерировать универсальную логику один раз и передавать только различия между ручками: параметры, роли, тип ресурса, предусловия и ожидаемые правила.

**3\. Разделение контекста на уровни**

Постоянные инструкции, профиль проекта, контракт операции, выбранные знания и история генерации должны быть разными логическими блоками. Не повторять полную библиотеку в каждом запросе.

**4\. Дедупликация до вызова LLM**

Удалять повторяющиеся знания, эквивалентные сценарии и уже покрытые комбинации ещё до формирования контекста. При этом не объединять проверки, которые различаются значимыми условиями доступа или ожидаемым поведением.

**5\. Инкрементальная генерация**

При изменении одного endpoint пересчитывать только затронутые планы и проверки. При обновлении библиотеки инвалидировать кэш по версии изменившихся знаний, а не очищать весь кэш.

**6\. Кэширование результатов подбора**

Кэшировать результаты поиска по отпечатку контракта, целей тестирования, версии библиотеки и конфигурации. Не кэшировать как универсальные факты предположения, зависящие от конкретного приложения.

**7\. Контроль токенов и качества**

Для каждого этапа измерять токены, стоимость, время, число найденных знаний, долю применимых сценариев, дубликаты и итоговое покрытие. Это позволит оптимизировать не просто цену, а стоимость качественного прогона.

Отдельно стоит использовать возможности кэширования префиксов контекста, если выбранная модель и API их поддерживают. Но это дополнительная оптимизация: она не заменяет сокращение самих входных данных.

## 3\. Как использовать библиотеку для поиска уже существующих проблем

Здесь я вижу два самостоятельных направления генерации.

**А. Проверки соответствия требованиям**

Система выясняет, что должна делать реализация, сравнивает это с кодом и генерирует тесты на подтверждение ожидаемого поведения.

**Б. Проверки гипотез о дефектах**

Библиотека предлагает известные классы ошибок, LLM находит соответствующие участки кода, формулирует гипотезу и создаёт сценарий, который должен подтвердить или опровергнуть её.

Например, библиотека содержит идею проверки доступа к чужому объекту.

1. Индекс показывает, что endpoint принимает `projectId`\.
2. LLM находит обработчик и путь получения проекта.
3. По графу вызовов выясняется, где выполняется проверка прав.
4. Модель обнаруживает потенциальный риск: объект извлекается по ID, но в доступном фрагменте не видно проверки принадлежности пользователю.
5. Генератор создаёт сценарий с двумя пользователями и двумя проектами.
6. Исполнение проверяет, может ли первый пользователь прочитать проект второго.

При этом отсутствие проверки в одном фрагменте кода — ещё не доказательство дефекта. Она может выполняться в middleware, общей политике доступа или другом вызываемом компоненте. Поэтому нужны анализ зависимостей и дополнительное чтение кода.

## 4\. Как сократить токены именно на интеллектуальном анализе

Я бы применил четыре механизма.

**1\. Индексировать код один раз, анализировать многократно.**

При каждом новом прогоне не просить LLM заново разбирать весь репозиторий. Изменившиеся файлы переиндексируются, а карта зависимостей обновляется инкрементально.

**2\. Хранить результаты анализа как проверяемые факты.**

Например: «маршрут использует middleware X», «функция Y вызывает запрос Z», «требование R связано с операцией O». Каждый факт должен иметь ссылку на исходник, версию и координаты фрагмента.

**3\. Использовать библиотеку для определения направления поиска.**

Вместо передачи всех знаний LLM получает компактную карточку известного класса ошибки, после чего система находит соответствующие участки проекта. Полные инструкции и связанные сценарии загружаются лишь для выбранных гипотез.

**4\. Делать целевые запросы к исходникам.**

Модель может запросить вызываемую функцию, схему данных или реализацию middleware. Система возвращает нужные фрагменты с ограниченным окном контекста, а не весь файл или репозиторий целиком.

Дополнительно стоит отделять подтверждённые факты от предположений и сохранять уже проверенные выводы, чтобы не повторять анализ при генерации каждого следующего теста.

## 5\. Важный нюанс: не всякую проблему нужно превращать в тест

Я бы предусмотрел разные статусы результатов анализа\:

- **Подтверждённый дефект** — проблема воспроизводится или доказана надёжным анализом.
- **Вероятный дефект** — есть конкретная гипотеза и обоснование, но не хватает доказательств.
- **Пробел тестового покрытия** — риск существует, но признаков дефекта в коде пока не обнаружено.
- **Неоднозначность требований** — невозможно однозначно определить правильное поведение.
