# 2. План реализации

План отражает логику развития библиотеки. Статус этапов приведён в `STAGE_REPORTS.md` и не означает, что все сгенерированные сценарии готовы к исполнению.

| Этап | Задача | Результат / критерий приёмки |
|---|---|---|
| 1. Основа каталога | Определить формат проверки, схему, таксономии, профили и валидатор | Все записи проходят JSON Schema и контроль ссылочной целостности |
| 2. REST-каталог | Расширить базовое покрытие REST-сценариями | Добавлены типовые проверки контракта, валидации, ресурсов, пагинации, устойчивости и безопасности; семантические сопоставления документированы |
| 3. Безопасность | Сформировать матрицу AuthN/AuthZ/ownership/tenant/roles-scopes | Проверки доступа разделены по рискам, мутации проверяют отсутствие побочных эффектов, неизвестные политики не домысливаются |
| 4. Генерация покрытия | Генерировать кандидаты из OpenAPI и access model | Выходные проверки, матрица операций/измерений и отчёт формируются повторяемо; ошибки схемы и неизвестные значения отслеживаются |
| 5. Реальные контракты | Применить генератор к демонстрационным контрактам проекта | Инвентаризация операций, candidate checks, список вопросов и противоречий сохранены в `build/real-contract-coverage/` |
| 6. Подбор по профилю | Отбирать проверки по тегам, приоритету и детерминированности | Выборка воспроизводима, причина отбора объяснима через профиль и метаданные |
| 7. Документирование и CI | Зафиксировать команды, ограничения и критерии ревью | README и отчёты поддерживают локальный запуск и проверку изменений |

## Рекомендуемый порядок дальнейших работ

1. Согласовать все вопросы из `build/real-contract-coverage/clarification_questions.json` с владельцами API.
2. Исправить OpenAPI security gaps и противоречие `onStart` в контракте/описании после решения владельца.
3. Проверить семантические отображения таксономий REST Expansion; при необходимости расширить словари осознанно.
4. Уточнить JSON Schema и валидатор: проверять не только структуру, но и неизвестные профили, категории, теги, приоритеты и уникальность ID.
5. Добавить тесты самого генератора/валидатора и golden fixtures для стабильности результатов.
6. Согласовать формат отчёта о покрытии и пороги для PR/CI/Release.
7. Только после ревью кандидатов подключать их к реальному тестовому раннеру и тестовой среде.
