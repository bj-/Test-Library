# 0003. Запуск тестов, отчёты о прогонах и баги

- **Статус:** принято
- **Дата:** 2026-10-12
- **Участники:** bj, Claude

## Контекст

Первый прогон коллекции `BFF-Admin-Auth` на стенде. Нужно было решить: чем запускать (в том числе без Postman),
где хранить отчёты для истории, как оформлять баги и где держать правила, чтобы на любой машине порядок был один.

## Решение

1. **Раннеры.** Основной - newman (без Postman): коллекция YAML v3 из git конвертируется в JSON v2.1 скриптом
   `postman/tools/run/v3_to_v21.py`, newman запускается как библиотека (`newman_run.js`), чтобы отделить основной
   запрос от `pm.sendRequest` фреймворка. Postman CLI для прогонов не используется (см. «Альтернативы»).
   Единая точка входа - `postman/tools/run/run.py`, наборы тестов - `postman/tools/run/suites/`.
2. **Креды.** Стенд и учётки тестовых стендов - в окружении Postman в git; production и личные - в `postman/.local/` (не в git). Креды тестовых стендов (dev ... stage)
   общедоступны и пишутся в отчёты и баги открыто - разработчик воспроизводит без вопросов. Production, подозрение
   на него или явная просьба скрывать - спросить пользователя; `run.py --secrets mask` заменяет их на `***`.
3. **Отчёты** - отдельный репозиторий `test-runs` (`runs/<Модуль>/<дата>_<набор>_<раннер>/`: `report.md`,
   `results.json`, `raw/`; история - `INDEX.md`). Тесты и результаты не смешиваются; прогон ссылается на коммит коллекции.
4. **Баги** - файлами в `test-runs/bugs/` по базовому шаблону и правилам из `Test-Library/Process/`: заголовок с сутью
   проблемы, curl для воспроизведения, отформатированный JSON, обоснование с реальными ссылками (ТЗ, контракт, RFC),
   типовая проблема - один баг на все вызовы. Для переноса - шаблоны трекеров `Process/templates/trackers/<трекер>/`
   (сейчас YouTrack); тип и адрес трекера, префикс темы (`[AT]`) и метки (`Autotest`) выбирает запускающий
   (`.local/tracker.yaml` или ключи `run.py`).
5. **Сверка стенда с контрактом** - перед каждым прогоном (`contract_probe.py`), результат - в отчёте: стенды
   версию не отдают, а без сверки падения из-за старой версии не отличить от дефектов.
6. **Блокировка учёток и разрушающие тесты.** Путь разблокировки стенда описывается в проекте; без него -
   безопасный лимит неудачных входов (по умолчанию 5, выбор при запуске), фреймворк по достижении лимита делает
   успешный вход. Разрушающие тесты - только по явному решению при запуске; не запускались - явно в отчёте;
   запуск только их - одним кликом (`run-destructive.cmd`).
7. **Правила процесса** (запуск, разбор, баги) - в `Test-Library/Process/`, общие для всех проектов.

## Альтернативы

- Postman CLI: `--output` только в Postman Enterprise (иначе лишь консоль); подставляет `{{переменные}}` в текст
  скрипта до выполнения - фреймворк получает устаревшие значения, JSON-значения ломают синтаксис; порядок - по `-i`.
- JSON-отчёт newman (`-r json`): вызовы `pm.sendRequest` попадают в него отдельными выполнениями и подменяют
  основной запрос - отказались в пользу своего драйвера на событиях newman.
- Отчёты в репозитории `postman` - засоряют историю тестов; Claude Docs/артефакты - вне git, нет диффов.
- Баги сразу в трекере - формат ещё не отработан; файлы переносятся в трекер без переписывания.

## Последствия

- На машине нужны Python + PyYAML, Node.js и newman (Postman CLI - по желанию).
- Конвертер поддерживает только используемые в коллекциях конструкции; неизвестный ключ - ошибка, а не потеря.
- Отчёт строится по общей модели результатов - раннеры взаимозаменяемы, прогоны сравнимы.
